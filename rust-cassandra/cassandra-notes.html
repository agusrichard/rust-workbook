1. What is Cassandra?

Apache Cassandra is a distributed NoSQL database. "Distributed" means your data does not live on one machine. It is spread across many machines (called nodes) that work together as one database (called a cluster).

It was built at Facebook around 2008 to power inbox search, then open-sourced and became an Apache project. Its design borrows from two famous systems:

  • Amazon Dynamo: how data is spread across machines and kept available.
  • Google Bigtable: how data is stored on disk (rows grouped together, fast writes).

You talk to Cassandra using CQL (Cassandra Query Language). It looks a lot like SQL, which makes it easy to start with, but it behaves quite differently underneath. There are no joins, and how you query is limited by how you design your tables.

One-sentence summary: Cassandra is a database that spreads data across many equal machines, keeps several copies of everything, never has a single point of failure, and is extremely fast at writes.

2. Why would I use it?

  • It doesn't go down. There is no "main" server. If a node dies, the others keep serving requests.
  • It scales horizontally. Need more capacity? Add more nodes. Throughput grows roughly in a straight line as you add machines.
  • Writes are very fast. A write is basically "append to a log + update memory". No disk seeking, no locking.
  • Multi-datacenter support is built in. You can keep copies of your data in different regions (e.g. US and Europe) out of the box.

The price you pay for this: less flexible queries, and (by default) eventual consistency. We will cover both.

3. The cluster: a ring of equal nodes

In many databases, one server is the "leader" and others follow. Cassandra is different: every node is equal (this is called a peer-to-peer or masterless design). Any node can accept any read or write.

How does Cassandra know where data lives?

Every row has a partition key (for example user_id). Cassandra runs that key through a hash function, which turns it into a big number called a token. Picture all possible tokens arranged in a circle, the ring. Each node owns some ranges on that ring. The row goes to whichever node owns its token. 

                 Node A
              (tokens 0-24)
            .-''''''''''-.
          /                \
   Node D |                 | Node B
  (75-99) |      RING       | (25-49)
          \                /
            '-..........-'
                 Node C
              (tokens 50-74)

  hash("user_42") = 37   -->  lands on Node B
  hash("user_7")  = 81   -->  lands on Node D

(Real tokens are huge 64-bit numbers, and each node actually owns many small ranges, called virtual nodes or vnodes, so data spreads evenly. The idea stays the same.)

The coordinator

Your app can send a request to any node. That node becomes the coordinator for that request. It figures out which nodes hold the data, forwards the request to them, and returns the answer to you. Smart drivers usually send the request straight to a node that holds the data, saving a hop.

Gossip

How do nodes know who is alive? Every second, each node chats with a few others and swaps news ("Node C is up, Node D seems down"). This is called the gossip protocol. News spreads quickly through the whole cluster, with no central registry needed.

4. Replication: keeping copies

Storing each row on just one node would be risky. Lose that node, lose the data. So Cassandra stores several copies, called replicas. How many copies is the replication factor (RF).

With RF = 3, the row goes to the node that owns its token, plus the next two nodes clockwise around the ring. 

  hash("user_42") lands on Node B

  RF = 3  -->  copies stored on  Node B, Node C, Node D

You set replication per keyspace (a keyspace is like a "database" in SQL terms):

-- Simple: fine for local testing, single datacenter
CREATE KEYSPACE shop
  WITH replication = {'class': 'SimpleStrategy', 'replication_factor': 3};

-- Production: lets you set copies per datacenter
CREATE KEYSPACE shop
  WITH replication = {'class': 'NetworkTopologyStrategy', 'us_east': 3, 'eu_west': 3};
Rule of thumb: RF = 3 is the common choice in production. It survives one node failing while still allowing majority (quorum) reads and writes.

5. Consistency levels: you choose the trade-off

Since there are several copies, a question comes up: when I write, how many replicas must confirm before I call it a success? And when I read, how many replicas must I ask? Cassandra lets you choose this per query. This is called tunable consistency.

LevelMeaning (with RF = 3)Trade-off
ONE1 replica must respondFastest, most available, but may read stale data
QUORUMA majority must respond (2 of 3)Good balance of speed and correctness
LOCAL_QUORUMA majority within the local datacenterLike QUORUM, but avoids slow cross-region trips. Very common in production.
ALLAll 3 replicas must respondStrongest, but fails if any single replica is down

The magic formula

If (replicas written) + (replicas read) > RF, your read is guaranteed to see the latest write, because the read set and the write set must overlap on at least one node. 

  RF = 3
  Write at QUORUM (2) + Read at QUORUM (2) = 4  > 3   -->  always see latest data
  Write at ONE    (1) + Read at ONE    (1) = 2  <= 3  -->  might see old data

How stale copies get fixed

Replicas can drift apart (a node was down during a write, for example). Cassandra repairs them in three ways:

  • Hinted handoff: if a replica is down, the coordinator keeps a "hint" (a note of the missed write) and replays it when the node returns.
  • Read repair: when a read notices replicas disagree, the newest value is written back to the stale ones.
  • Anti-entropy repair: an operator runs nodetool repair regularly to compare and sync all data between replicas.

When two writes conflict, Cassandra keeps the one with the newest timestamp. This is called last write wins.

6. How writes and reads work inside a node

The write path (why writes are so fast)

  1. Commit log: the write is appended to a log file on disk. Appending is cheap, and it means the data survives a crash.
  2. Memtable: the write is also put into an in-memory, sorted table.
  3. Done! The node replies "OK". No reading, no searching, no updating files in place.
  4. Flush (later): when the memtable gets full, it is written to disk as an SSTable (Sorted String Table). SSTables are immutable: once written, never changed.
  5. Compaction (later): over time many SSTables pile up. A background process merges them, keeps the newest version of each row, and drops deleted data.
  write --> [ commit log (disk, append) ]
        --> [ memtable  (memory)      ] --flush--> [ SSTable ] [ SSTable ] [ SSTable ]
                                                         \________ compaction ________/
                                                                       |
                                                                  [ SSTable ]
Key insight: in Cassandra, an UPDATE is just another write with a newer timestamp, and a DELETE is also a write (a marker called a tombstone). Nothing is changed in place.

The read path

A read may need to look in the memtable and several SSTables, then merge the results by timestamp. To avoid opening every file, Cassandra uses helpers:

  • Bloom filter: a tiny in-memory structure that quickly answers "this SSTable definitely does not have that key", so it can be skipped.
  • Partition index / summary: tells Cassandra where in the file the partition starts.
  • Caches: optional key and row caches for hot data.

This is why reads are generally slower than writes, and why compaction matters: fewer SSTables means faster reads.

7. The data model: keyspaces, tables, keys

CassandraRough SQL equivalent
ClusterThe whole database server setup
KeyspaceDatabase / schema (also sets replication)
TableTable
PartitionA group of rows stored together on the same nodes (no direct SQL equivalent)
RowRow

The primary key has two parts

This is the most important concept in Cassandra:

CREATE TABLE messages_by_room (
  room_id    text,
  sent_at    timestamp,
  message_id uuid,
  author     text,
  body       text,
  PRIMARY KEY ((room_id), sent_at, message_id)
) WITH CLUSTERING ORDER BY (sent_at DESC, message_id ASC);
  • Partition key: (room_id), inside the inner parentheses. It decides which nodes store the data. All rows with the same room_id live together in one partition.
  • Clustering columns: sent_at, message_id. They decide the sort order of rows inside the partition. Here, messages in a room are stored newest-first.

Think of it like a filing cabinet:

  Partition key     = which drawer        (room "rust-lovers")
  Clustering columns = order of folders    (sorted by time, newest first)
  Row               = one folder          (one message)

Because rows in a partition are stored together and already sorted, a query like "give me the latest 50 messages in room X" is one fast, sequential read from one place.

The partition key can have several columns, e.g. PRIMARY KEY ((sensor_id, day), reading_time). This is a common trick to stop a partition from growing forever (one partition per sensor per day).

8. Data modeling: design around your queries

In SQL you usually design tables around your entities (users, orders, products), normalize them, and use joins to answer any question later. Cassandra flips this around.

Golden rule: start from the queries your app needs, then build one table per query.

Principles

  1. List your queries first. "Get user by email", "Get orders for a user, newest first", and so on.
  2. Each query should hit one partition. Pick the partition key so the answer lives in one place.
  3. Duplicate data on purpose. Storing the same data in several tables is normal and expected (this is called denormalization). Disk is cheap; cross-node lookups are expensive.
  4. No joins. If you need data together, store it together.
  5. Keep partitions a reasonable size. A common guideline is under ~100 MB and ~100,000 rows per partition. Split with a time bucket if needed.
  6. Spread load evenly. Avoid a partition key where one value gets most of the traffic (a "hot partition").

Example: a tiny shop

Queries we need:

  • Q1: Find a user by email
  • Q2: List a user's orders, newest first
-- Q1
CREATE TABLE users_by_email (
  email   text PRIMARY KEY,
  user_id uuid,
  name    text
);

-- Q2
CREATE TABLE orders_by_user (
  user_id    uuid,
  ordered_at timestamp,
  order_id   uuid,
  total      decimal,
  status     text,
  PRIMARY KEY ((user_id), ordered_at, order_id)
) WITH CLUSTERING ORDER BY (ordered_at DESC, order_id ASC);
-- Both are single-partition, fast queries:
SELECT * FROM users_by_email WHERE email = 'ana@example.com';
SELECT * FROM orders_by_user WHERE user_id = 5b6f... LIMIT 20;

Need "orders by status" too? You would create a third table, orders_by_status, and write each order to both tables. Writes are cheap, so this is fine.

What you can and cannot filter on

  • You must provide the full partition key (with = or IN).
  • You can filter clustering columns in order, left to right, with a range only on the last one you use.
  • Filtering on a regular (non-key) column is rejected unless you add ALLOW FILTERING, which usually means "scan a lot of data". Avoid it in production.

9. CQL cheat sheet

-- Keyspace
CREATE KEYSPACE demo WITH replication = {'class': 'SimpleStrategy', 'replication_factor': 1};
USE demo;

-- Table
CREATE TABLE users (
  user_id uuid PRIMARY KEY,
  name    text,
  email   text,
  tags    set<text>
);

-- Insert (note: INSERT and UPDATE are both "upserts")
INSERT INTO users (user_id, name, email, tags)
VALUES (uuid(), 'Ana', 'ana@example.com', {'admin'});

-- Insert that expires after 1 hour (TTL in seconds)
INSERT INTO users (user_id, name) VALUES (uuid(), 'Temp') USING TTL 3600;

-- Update
UPDATE users SET name = 'Ana Maria' WHERE user_id = 1f2e...;

-- Add to a collection
UPDATE users SET tags = tags + {'beta'} WHERE user_id = 1f2e...;

-- Delete a row (or just one column)
DELETE FROM users WHERE user_id = 1f2e...;
DELETE email FROM users WHERE user_id = 1f2e...;

-- Only insert if it does not exist (lightweight transaction, slower)
INSERT INTO users_by_email (email, user_id, name)
VALUES ('ana@example.com', 1f2e..., 'Ana') IF NOT EXISTS;

-- Counters live in their own tables
CREATE TABLE page_views (page text PRIMARY KEY, views counter);
UPDATE page_views SET views = views + 1 WHERE page = '/home';

-- Batch: keep several tables in sync (atomic, not a speed trick)
BEGIN BATCH
  INSERT INTO orders_by_user   (...) VALUES (...);
  INSERT INTO orders_by_status (...) VALUES (...);
APPLY BATCH;

-- Set consistency level inside cqlsh
CONSISTENCY QUORUM;

10. Common gotchas

Tombstones. A delete writes a marker instead of removing data. Tombstones are kept for gc_grace_seconds (10 days by default) so all replicas learn about the delete. Lots of deletes in one partition (for example using a table as a queue) make reads slow, because Cassandra has to skip over all those markers.
Large or unbounded partitions. A partition key like country or status puts huge amounts of data in one place. Add a bucket (like a day or month) to the partition key.
Thinking in SQL. No joins, no ad-hoc queries, no foreign keys. If a new query appears, you usually need a new table.
Secondary indexes and ALLOW FILTERING. They exist, but can query many nodes at once and get slow at scale. (Cassandra 5.0 adds Storage-Attached Indexes, SAI, which are much better, but query-first table design is still the default approach.)
Lightweight transactions (IF ...) use a consensus protocol (Paxos) and take several round trips. Use them only where you truly need "check then write", like claiming a unique username.
Batches are not for speed. A batch across many partitions puts extra work on the coordinator. Use batches to keep denormalized tables in sync, not to bulk-load data.

11. When to use it (and when not to)

Great fit

  • Huge write volume: event logs, IoT sensor data, metrics, activity feeds
  • Time-series data (data naturally partitioned by device/user + time)
  • Apps that must stay up even when machines or whole datacenters fail
  • Data spread across multiple regions
  • Access patterns you know in advance

Poor fit

  • Small datasets that fit easily on one machine. PostgreSQL will be simpler.
  • Lots of ad-hoc queries, reporting, or analytics with joins and aggregates
  • Strong multi-row transactions (e.g. moving money between accounts atomically)
  • Workloads with heavy deletes or queue-like behavior

Quick comparison

PostgreSQL (typical SQL)Cassandra
ScalingMostly vertical (bigger machine) + read replicasHorizontal (more machines)
ArchitecturePrimary + replicasAll nodes equal
QueriesFlexible, joins, ad-hocFixed by table design, no joins
ConsistencyStrong, ACID transactionsTunable, eventual by default
Schema designModel entities, normalizeModel queries, denormalize
Best atGeneral-purpose, relational dataMassive writes, high availability

12. Try it yourself

The quickest way to play with Cassandra is Docker:

# Start a single node (takes ~30-60 seconds to be ready)
docker run --name cassandra -d -p 9042:9042 cassandra:5.0

# Check it is up (look for "UN" = Up/Normal)
docker exec -it cassandra nodetool status

# Open the CQL shell
docker exec -it cassandra cqlsh

Then paste the examples from the cheat sheet above.

From Rust: the scylla crate is a popular async driver that also works with Apache Cassandra (it speaks the same CQL protocol on port 9042).

Exercises to cement the ideas

  1. Create a keyspace and the messages_by_room table. Insert a few messages and read the latest 10 for one room.
  2. Try SELECT * FROM messages_by_room WHERE author = 'ana'; and read the error. Why is it rejected?
  3. Design tables for a URL shortener: "look up the long URL by short code" and "list a user's links, newest first".
  4. Insert a row with USING TTL 30 and watch it disappear.
  5. Use IF NOT EXISTS to make sure a username can only be claimed once.

The five things to remember

  1. All nodes are equal. No single point of failure.
  2. The partition key decides where data lives; clustering columns decide its order.
  3. Design one table per query, and duplicate data freely.
  4. Consistency is a per-query choice. QUORUM reads plus QUORUM writes gives you up-to-date reads.
  5. Writes are appends. Updates and deletes are just newer writes, cleaned up later by compaction.

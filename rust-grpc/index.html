01 · Start here

The mental model

Suppose one program needs product information owned by another program. With gRPC, the calling program writes code that looks like a local method call:

Rust client code
let response = client
    .get_product(GetProductRequest { id: "p-42".into() })
    .await?;

It is not actually local. Generated client code serializes the request, sends it over the network, waits for the remote service, decodes the response, and returns either data or a gRPC status.

Your Rust code
Generated client
HTTP/2 network
Generated server
Your service logic
gRPC is a contract-first way for programs to call each other. The contract says which operations exist and exactly what data crosses the boundary.

The “local call” feeling is convenient, but remember the network: calls may be slow, duplicated, rejected, or interrupted. Proficiency with gRPC is mostly learning to design for those facts.

02 · Background

Why gRPC exists

RPC means Remote Procedure Call. The idea predates gRPC: define an operation, generate a client proxy, and hide repetitive networking details. Google developed the internal system Stubby; gRPC brought similar ideas to an open, cross-language ecosystem in 2015.

gRPC commonly combines three pieces:

  • Protocol Buffers describe services and messages in a language-neutral .proto file.
  • Code generation turns that contract into typed client and server interfaces.
  • HTTP/2 transports framed binary messages, multiplexes concurrent calls on a connection, and supports long-lived streams.

gRPC and JSON/REST solve overlapping problems

QuestiongRPCTypical JSON/REST API
ContractExplicit schema and service methodsOften OpenAPI, sometimes convention only
PayloadCompact binary Protobuf by defaultHuman-readable JSON
StreamingNative in both directionsUsually needs SSE or WebSocket
Browser useNeeds gRPC-Web or a gatewayNative and simple
Debugging by eyeNeeds schema-aware toolsEasy with curl and browser tools
Best fitInternal services, typed polyglot systems, real-time streamsPublic/browser APIs and resource-oriented interfaces

Rule of thumb: choose gRPC because its typed contracts, code generation, or streaming help your system—not merely because binary sounds faster. A system can expose gRPC internally and JSON externally through a gateway.

03 · Vocabulary

The building blocks

Service

A named collection of remote methods, such as Inventory.

Message

A typed request or response encoded with Protobuf.

Client / stub

Generated code that exposes remote methods to the caller.

Channel

A logical connection to a server. In tonic, channels are cheap to clone and can carry concurrent calls.

Metadata

Key/value call context: authorization, trace IDs, locale, and similar data—not business payload.

Status

The structured outcome: a code such as NOT_FOUND plus a safe description and optional details.

Deadline

The maximum time the client is willing to wait for the entire RPC.

Interceptor / layer

Reusable behavior around calls, such as authentication, tracing, or rate limiting.

Protocol Buffer basics

product.proto
syntax = "proto3";

package shop.v1;

message Product {
  string id = 1;
  string name = 2;
  int32 stock = 3;
}

message GetProductRequest {
  string id = 1;
}

The numbers (= 1, = 2) are wire identities, not positions. Once released, do not change or reuse them. Field names are for people; field numbers are what make old and new programs understand each other.

  • Scalar fields have defaults in proto3: an absent string reads as "", an absent integer as 0.
  • Use optional when “not supplied” must differ from the default value.
  • Use repeated for a list, map<K,V> for a map, and oneof when exactly one variant should be present.
  • Prefer explicit domain messages over an unstructured map.

04 · Method design

The four RPC shapes

1 → 1

Unary

One request, one response. Use it for “get product,” “create order,” or most ordinary operations.

rpc Get(A) returns (B);
1 → ∞

Server streaming

One request, many responses. Use it for live stock changes, logs, or a large result consumed incrementally.

rpc Watch(A) returns (stream B);
∞ → 1

Client streaming

Many requests, one response. Use it for chunks, sensor batches, or incremental upload.

rpc Upload(stream A) returns (B);
∞ ↔ ∞

Bidirectional

Both sides stream independently. Use it for collaboration, chat, or control sessions.

rpc Sync(stream A) returns (stream B);
Start unary. Streaming adds lifecycle, backpressure, cancellation, reconnect, and partial-progress questions. Choose it when the use case truly benefits.

Messages stay ordered within one stream. Separate RPCs are independent; do not assume ordering between them.

The Rust gRPC stack

tonic uses Rust’s async model: awaiting a network operation pauses the task without blocking the OS thread. Generated messages are ordinary Rust structs; generated clients have async methods; generated servers define traits that your application implements.

06 · Hands-on workshop

Build a small inventory API

Our real-world example answers: “What product is this, and how many are in stock?” It deliberately keeps storage in memory so the gRPC parts remain visible.

1. Target project shape

Directory tree
rust-grpc/

2. Add dependencies

Install protoc first (brew install protobuf on macOS, or your operating system’s equivalent), then run:

Terminal
cargo add tonic --features transport
cargo add tonic-prost prost
cargo add tokio --features macros,rt-multi-thread
cargo add --build tonic-prost-build

These commands let Cargo select compatible current versions. This guide targets the tonic 0.14 API family.

3. Write the contract

proto/inventory.proto
syntax = "proto3";

package inventory.v1;

service Inventory {
  rpc GetProduct(GetProductRequest) returns (Product);
}

message GetProductRequest {
  string id = 1;
}

message Product {
  string id = 1;
  string name = 2;
  int32 stock = 3;
}

4. Generate Rust code at build time

build.rs
fn main() -> Result<(), Box<dyn std::error::Error>> {
    tonic_prost_build::compile_protos("proto/inventory.proto")?;
    println!("cargo:rerun-if-changed=proto/inventory.proto");
    Ok(())
}

Cargo runs this build script before compiling your crate. Generated files go into Cargo’s build output directory; tonic::include_proto! includes them without checking generated code into source control.

5. Implement the server

src/main.rs
use std::collections::HashMap;
use tonic::{transport::Server, Request, Response, Status};

pub mod inventory {
    tonic::include_proto!("inventory.v1");
}

use inventory::{
    inventory_server::{Inventory, InventoryServer},
    GetProductRequest, Product,
};

#[derive(Debug, Default)]
struct InventoryService {
    products: HashMap<String, Product>,
}

#[tonic::async_trait]
impl Inventory for InventoryService {
    async fn get_product(
        &self,
        request: Request<GetProductRequest>,
    ) -> Result<Response<Product>, Status> {
        let id = request.into_inner().id;

        if id.trim().is_empty() {
            return Err(Status::invalid_argument("product id is required"));
        }

        let product = self.products
            .get(&id)
            .cloned()
            .ok_or_else(|| Status::not_found("product does not exist"))?;

        Ok(Response::new(product))
    }
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let mut products = HashMap::new();
    products.insert(
        "p-42".into(),
        Product {
            id: "p-42".into(),
            name: "Mechanical Keyboard".into(),
            stock: 12,
        },
    );

    let address = "[::1]:50051".parse()?;
    let service = InventoryService { products };

    println!("Inventory server listening on {address}");
    Server::builder()
        .add_service(InventoryServer::new(service))
        .serve(address)
        .await?;

    Ok(())
}

Request<T> holds the message plus metadata and transport context. Response<T> can also carry metadata. Status is the typed failure path.

6. Write the client

src/bin/client.rs
use std::time::Duration;
use tonic::Request;

pub mod inventory {
    tonic::include_proto!("inventory.v1");
}

use inventory::{inventory_client::InventoryClient, GetProductRequest};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let mut client = InventoryClient::connect("http://[::1]:50051").await?;

    let mut request = Request::new(GetProductRequest {
        id: "p-42".into(),
    });
    request.set_timeout(Duration::from_secs(2));

    let product = client.get_product(request).await?.into_inner();
    println!("{}: {} in stock", product.name, product.stock);

    Ok(())
}

07 · Second example

Add live stock updates

A checkout screen may need changes as they happen. Server streaming fits: one subscription request produces many updates.

Add to inventory.proto
service Inventory {
  rpc GetProduct(GetProductRequest) returns (Product);
  rpc WatchStock(WatchStockRequest) returns (stream StockUpdate);
}

message WatchStockRequest { string product_id = 1; }
message StockUpdate {
  string product_id = 1;
  int32 stock = 2;
}

After rebuilding, the generated trait requires an associated stream type and a method. A simple implementation can send values over a Tokio channel:

Core server-streaming pattern
use std::pin::Pin;
use tokio_stream::{wrappers::ReceiverStream, Stream};

type StockStream = Pin<
    Box<dyn Stream<Item = Result<StockUpdate, Status>> + Send>
>;

// Inside `impl Inventory for InventoryService`:
type WatchStockStream = StockStream;

async fn watch_stock(
    &self,
    request: Request<WatchStockRequest>,
) -> Result<Response<Self::WatchStockStream>, Status> {
    let product_id = request.into_inner().product_id;
    let (tx, rx) = tokio::sync::mpsc::channel(8);

    tokio::spawn(async move {
        for stock in [12, 11, 10] {
            let update = StockUpdate { product_id: product_id.clone(), stock };
            if tx.send(Ok(update)).await.is_err() {
                break; // Client disconnected; stop producing work.
            }
        }
    });

    Ok(Response::new(Box::pin(ReceiverStream::new(rx))))
}

This snippet also needs cargo add tokio-stream. The channel capacity of 8 creates backpressure: if the network consumer falls behind, producers eventually wait instead of growing memory without limit.

Client consumption
let response = client
    .watch_stock(WatchStockRequest { product_id: "p-42".into() })
    .await?;
let mut updates = response.into_inner();

while let Some(update) = updates.message().await? {
    println!("{} now has {}", update.product_id, update.stock);
}

Questions every stream must answer

  • When does it end, and who may cancel it?
  • What happens when a consumer is slow?
  • How will a reconnect resume—sequence number, cursor, or full snapshot?
  • Can an item be delivered again, and is the consumer safe against duplicates?
  • What is the maximum message size and rate?

08 · Network reality

Failures, deadlines, and cancellation

A Rust Result maps naturally to gRPC: success becomes a response; failure becomes tonic::Status. Choose the most specific code a caller can act on.

CodeUse it whenInventory example
INVALID_ARGUMENTThe input is invalid regardless of server stateEmpty or malformed product ID
NOT_FOUNDThe requested entity is absentUnknown product
ALREADY_EXISTSA create conflicts with an existing entityDuplicate SKU
FAILED_PRECONDITIONCurrent state prevents the operationOrdering a discontinued item
UNAUTHENTICATEDIdentity is missing or invalidExpired token
PERMISSION_DENIEDIdentity is known but lacks accessShopper tries an admin method
RESOURCE_EXHAUSTEDA quota or capacity is exhaustedRate limit reached
UNAVAILABLETemporary service/network failureDependency is briefly offline
INTERNALUnexpected invariant or server bugCorrupt internal state

Deadlines are part of correctness

Without a deadline, work can outlive the user request and consume resources indefinitely. Set one at the outer client and propagate the remaining budget through downstream calls.

A timeout is local; a deadline is end-to-end intent. “This attempt may take 200 ms” is different from “the user’s entire operation has 200 ms left.”

When a caller disappears or its deadline expires, stop database work and spawned tasks where possible. Returning a response after cancellation only wastes resources.

Retries require idempotency

A failed call may have reached the server even if the response never reached the client. Reads are commonly safe to retry. Mutations need deliberate semantics:

  • Use a client-generated idempotency key for operations such as “create payment.”
  • Store the key with the result so a duplicate request returns the original result.
  • Retry only transient codes such as UNAVAILABLE, with exponential backoff and jitter.
  • Keep retries inside the original deadline and cap the number of attempts.

09 · Security

Apply authentication and authorization

Security is a sequence of separate decisions. TLS protects the connection. Authentication establishes who is calling. Authorization decides what that identity may do. A secure service normally needs all three.

Client + credential
TLS or mTLS
Authenticate
Authorize
Run handler

Authentication

“This caller is user u-123 from tenant t-7.” Validate a token or client certificate and create a trusted identity.

Authorization

“User u-123 may read this product but may not adjust its stock.” Evaluate permissions against both the method and resource.

The common production pattern

  1. Encrypt the channel. Use TLS for every connection outside local development. Use mutual TLS when services must authenticate each other.
  2. Obtain an access token. A user-facing client normally signs in through an OAuth 2.0/OpenID Connect identity provider and receives a short-lived access token.
  3. Attach the credential. Send the token in gRPC metadata using the standard authorization: Bearer … entry.
  4. Authenticate centrally. An interceptor or Tower middleware validates the credential once and stores a typed Principal in request extensions.
  5. Authorize close to the data. The handler checks scopes or roles, then checks ownership, tenant, or other resource attributes.

1. Send an access token from the client

Attach authorization metadata
use tonic::{metadata::MetadataValue, Request};

let mut request = Request::new(GetProductRequest {
    id: "p-42".into(),
});

let value = format!("Bearer {access_token}")
    .parse::<MetadataValue<_>>()?;

request.metadata_mut().insert("authorization", value);
let response = client.get_product(request).await?;

A bearer token is usable by whoever possesses it, so never send one over an unencrypted channel or write it to logs. Use an access token intended for this API—not an ID token intended only to describe a login.

2. Authenticate in a tonic interceptor

The interceptor below shows the boundary. The fictional verify_access_token represents a maintained JWT/OIDC library configured for your identity provider.

Server authentication boundary
use tonic::{Request, Status};

#[derive(Clone, Debug)]
struct Principal {
    subject: String,
    tenant_id: String,
    permissions: Vec<String>,
}

fn authenticate(
    mut request: Request<()>,
) -> Result<Request<()>, Status> {
    let header = request
        .metadata()
        .get("authorization")
        .ok_or_else(|| Status::unauthenticated("access token required"))?
        .to_str()
        .map_err(|_| Status::unauthenticated("invalid authorization metadata"))?;

    let token = header
        .strip_prefix("Bearer ")
        .ok_or_else(|| Status::unauthenticated("bearer token required"))?;

    let claims = verify_access_token(token)
        .map_err(|_| Status::unauthenticated("invalid access token"))?;

    request.extensions_mut().insert(Principal {
        subject: claims.subject,
        tenant_id: claims.tenant_id,
        permissions: claims.permissions,
    });

    Ok(request)
}

Register it around the generated service:

Apply the interceptor
let inventory = InventoryServer::with_interceptor(
    InventoryService::new(),
    authenticate,
);

Server::builder()
    .add_service(inventory)
    .serve(address)
    .await?;

Token validation must check the signature, trusted issuer (iss), expected audience (aud), expiration (exp), allowed algorithm, and any required claims. Cache signing keys and refresh them safely; do not fetch keys from the identity provider during every request. A tonic interceptor is synchronous, so use Tower middleware when authentication requires asynchronous work or access to the response.

3. Authorize the operation and its resource

Authorization in a service method
async fn adjust_stock(
    &self,
    request: Request<AdjustStockRequest>,
) -> Result<Response<Product>, Status> {
    let principal = request
        .extensions()
        .get::<Principal>()
        .cloned()
        .ok_or_else(|| Status::unauthenticated("identity missing"))?;

    if !principal.permissions.iter().any(|p| p == "inventory:write") {
        return Err(Status::permission_denied("write permission required"));
    }

    let input = request.into_inner();
    let product = self.repository
        .find(&input.product_id)
        .await
        .map_err(|_| Status::internal("repository lookup failed"))?;

    // Object-level authorization prevents cross-tenant access.
    if product.tenant_id != principal.tenant_id {
        return Err(Status::permission_denied("product belongs to another tenant"));
    }

    let updated = self.repository
        .adjust(product, input.change)
        .await
        .map_err(|_| Status::internal("stock update failed"))?;
    Ok(Response::new(updated))
}
Checking only the RPC method is not enough. A caller allowed to read one account must not be able to read every account by changing an ID. Always enforce resource ownership or tenant boundaries after loading the resource.

4. Configure TLS and optional mTLS

Enable a current tonic TLS backend, for example cargo add tonic --features transport,tls-ring, and configure the server identity:

TLS server configuration
use tonic::transport::{Identity, Server, ServerTlsConfig};

let cert = std::fs::read("server.pem")?;
let key = std::fs::read("server.key")?;
let identity = Identity::from_pem(cert, key);

Server::builder()
    .tls_config(ServerTlsConfig::new().identity(identity))?
    .add_service(inventory)
    .serve(address)
    .await?;

For service-to-service mTLS, require certificates signed by your client certificate authority:

Add client-certificate verification
use tonic::transport::Certificate;

let client_ca = std::fs::read("client-ca.pem")?;
let tls = ServerTlsConfig::new()
    .identity(identity)
    .client_ca_root(Certificate::from_pem(client_ca));

Server::builder()
    .tls_config(tls)?
    .add_service(inventory)
    .serve(address)
    .await?;

Choose an authorization model

ModelExampleGood fit
Roles (RBAC)admin, viewerSmall systems with stable job functions
Permissions/scopesinventory:read, inventory:writePrecise API capabilities and OAuth tokens
Attributes (ABAC)Tenant, owner, region, or resource stateMulti-tenant or context-sensitive rules
RelationshipsOwner, member, editor, parent organizationSharing and collaboration products

A practical default combines scopes for coarse permission with tenant or ownership checks for the resource. Move policy evaluation into a dedicated policy component when rules become numerous or shared across services.

Gateway trust boundaries

A trusted gateway may validate external tokens and forward identity to internal services. If you use this pattern, prevent direct public access to the services, protect gateway-to-service traffic with mTLS or signed internal tokens, and strip user-supplied identity headers before inserting trusted ones. Never trust an arbitrary x-user-id received from the public network.

OutcomegRPC status
Credential is missing, malformed, invalid, or expiredUNAUTHENTICATED
Identity is valid but lacks permissionPERMISSION_DENIED
Authorized caller requests an entity that does not existNOT_FOUND

Security checklist

  • TLS is enabled and certificate verification is not disabled.
  • Access tokens have a short lifetime and the correct API audience.
  • Signature, issuer, audience, expiry, and algorithm are validated.
  • Authentication creates a typed principal; handlers do not trust raw headers.
  • Both method permission and object/tenant access are enforced.
  • Tokens, passwords, private keys, and sensitive payloads are never logged.
  • Authentication failures and sensitive mutations are audited without recording secrets.

10 · Operating the service

Production readiness

Observability

Instrument each RPC with:

  • Metrics: request count, latency histogram, status code, in-flight calls, and stream duration.
  • Traces: propagate trace context in metadata and create a span around each method.
  • Logs: method, safe entity identifiers, duration, and status—not entire sensitive payloads.

Watch p50, p95, and p99 latency. An average can hide the slow requests users notice.

Resource control

  • Limit inbound/outbound message sizes and validate repeated-field counts.
  • Bound concurrency and stream/channel buffers.
  • Apply per-client rate limits and global load shedding.
  • Reuse channels; do not open a fresh HTTP/2 connection for every call.
  • Configure keepalive carefully—aggressive pings can overload peers or proxies.
  • Gracefully stop accepting work, let short calls finish, then cancel at a shutdown deadline.

Deployment path

Confirm that every proxy, ingress, and load balancer in the path supports gRPC over HTTP/2. Add the standard gRPC health service for load balancers and orchestration. Reflection is extremely useful for internal debugging, but expose it deliberately.

11 · Compatibility

Evolve the API without breaking callers

Distributed programs do not upgrade at the same instant. For a while, old clients talk to new servers and new clients talk to old servers. Protobuf supports this well if you follow its rules.

Usually safe

  • Add a new field with a new number.
  • Add a new method.
  • Add a new enum value when consumers handle unknown values.
  • Rename a field in binary-only use, though it may break JSON/text users.

Dangerous

  • Change an existing field number.
  • Reuse a deleted field number.
  • Change a field to an incompatible type.
  • Change meaning while keeping the same shape.
Reserve removed fields
message Product {
  reserved 4;
  reserved "legacy_category";

  string id = 1;
  string name = 2;
  int32 stock = 3;
  optional string description = 5;
}

Use a versioned package such as inventory.v1. Introduce v2 only for a genuinely incompatible redesign, and operate both versions during migration. Compatibility checks belong in CI—tools such as Buf can detect breaking schema changes.

12 · Confidence

Testing and debugging

  1. Unit-test domain logic separately from gRPC. Plain functions are fast and easy to exercise.
  2. Test the service implementation by constructing Request<T> directly and asserting the response or status.
  3. Run an integration test with a server on an ephemeral port and a generated client. This covers encoding, routing, and transport.
  4. Check the contract in CI for formatting and backward compatibility.
  5. Test unhappy paths: invalid data, missing auth, deadlines, disconnects, slow streams, oversized messages, and graceful shutdown.
Direct service test sketch
#[tokio::test]
async fn unknown_product_is_not_found() {
    let service = InventoryService::default();
    let request = Request::new(GetProductRequest { id: "missing".into() });

    let status = service.get_product(request).await.unwrap_err();
    assert_eq!(status.code(), tonic::Code::NotFound);
}

For manual inspection, use a schema-aware client such as grpcurl or grpcui. Server reflection lets these tools discover contracts; without reflection, pass the .proto files explicitly.

“My generated module cannot be found.”
Ensure the string in tonic::include_proto!("inventory.v1") exactly matches the proto package. Also check that build.rs ran successfully.
“The build cannot find protoc.”
Install the Protocol Buffer compiler and verify protoc --version works in the same environment that runs Cargo.
“The client reports UNIMPLEMENTED.”
Usually the method path or deployed service version differs. Confirm package, service, method, and that the correct server build is running.
“It works locally but not through the proxy.”
Verify end-to-end HTTP/2 and gRPC support, TLS/ALPN configuration, idle timeouts, maximum body size, and whether the proxy supports long-lived streams.

13 · Working judgment

A design checklist

Before shipping a method, answer these questions:

Contract

Are names precise? Is presence meaningful? Are units explicit? Are fields bounded?

RPC shape

Does unary suffice? If streaming, how does it end, resume, and apply backpressure?

Failure

Which status codes can occur? What can callers retry? Is mutation idempotent?

Time

What deadline should callers use? Is cancellation propagated to dependencies?

Security

How are peer identity, authorization, TLS, secrets, and sensitive fields handled?

Operations

Are there limits, health checks, graceful shutdown, metrics, tracing, and compatibility checks?

The most common mistakes

  • Treating a network call as if it cannot partially fail.
  • Omitting deadlines and allowing unbounded work.
  • Retrying writes without idempotency.
  • Using INTERNAL for every domain error.
  • Making one giant message or one never-ending unbounded stream.
  • Changing or reusing Protobuf field numbers.
  • Logging whole requests that contain credentials or personal data.
  • Assuming browsers and every HTTP proxy speak native gRPC.

14 · Make it stick

A practical learning path

  1. Run the unary inventory example and inspect the generated documentation with cargo doc --open.
  2. Add ListProducts with pagination: page_size and opaque page_token.
  3. Add AdjustStock. Validate inputs and decide how to prevent duplicate adjustments.
  4. Add WatchStock; disconnect the client halfway through and verify the producer stops.
  5. Add an authorization interceptor and a two-second client deadline.
  6. Add tracing, a health endpoint, graceful shutdown, and an integration test.
  7. Make a safe schema change, then deliberately try a breaking field-number change and let CI catch it.

Quick knowledge check

A client calls AdjustStock. The server commits the change, but the response is lost. Should the client blindly retry?

Second answer. The caller cannot know whether the server committed. A blind retry could adjust stock twice. Use a stable operation ID and return the stored result for duplicates.
You are proficient when you can explain not only how to make a call, but also what happens when it is slow, duplicated, cancelled, incompatible, or observed in production.

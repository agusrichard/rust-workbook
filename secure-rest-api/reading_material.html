How authentication works in a real web app

1 · Start with the architecture

Authentication is a goal, not a single design

Every design must establish who the user is and carry that identity safely across requests. The right mechanism depends on the shape and risk of the application.

Two questions that are easy to mix up

Authentication asks how the user proves their identity—for example, a password, passkey, or OpenID Connect provider. Session architecture asks how the application remembers and uses that identity on later requests—for example, a session cookie, a BFF, or access tokens.

“Sign in with Google,” an enterprise identity provider, and your own email/password screen answer the first question. The five patterns below answer the second. They can be combined: an application can use OpenID Connect for sign-in and then keep its own server-side cookie session.

A quick decision guide
  • One website and one same-domain API: start with a server-side cookie session.
  • Business or personal-data application using OAuth: prefer a Backend-for-Frontend.
  • The browser must call several APIs directly: consider a token-mediating backend.
  • No backend component is possible: use Authorization Code with PKCE in the browser and accept the larger attack surface.
  • Web and mobile clients share the API: access tokens can provide a consistent API boundary, while each client stores credentials differently.

1. Server-side cookie session

Best simple default

The browser receives a random session ID in an HttpOnly cookie. The server uses that ID to load the user’s session from Redis or a database. React never receives an access or refresh token.

React→ cookie →Rust API→ lookup →Session store
Use it for
A first-party frontend and API on the same site or behind the same gateway.
Choose it when
You want the smallest secure design and do not need the browser to carry credentials to unrelated APIs.
Browser holds
Only an opaque HttpOnly session cookie.
Main trade-off
The server must store and look up session state. Cookie-authenticated routes require CSRF protection.

2. Access token plus refresh cookie

Learning track A

React keeps a short-lived access token in memory and sends it directly to APIs. A rotating refresh token stays in an HttpOnly cookie and is used only by authentication endpoints.

React + access token→Rust APIs↔ refresh cookie ↔Auth service
Use it for
A separate SPA and API, several APIs accepting the same bearer token, or web and mobile clients sharing an API.
Choose it when
Direct browser-to-API calls and a token-based API boundary are valuable enough to justify extra lifecycle logic.
Browser holds
An access token in memory and an unreadable refresh cookie.
Main trade-off
Malicious JavaScript can read the current access token. Rotation, expiry, CORS, CSP, and CSRF controls must all be correct.

3. Backend-for-Frontend (BFF)

Learning track B

A small backend is dedicated to the React application. It stores OAuth access and refresh tokens on the server. React sends only its session cookie to the BFF, and the BFF forwards requests to downstream APIs with the correct access token.

React→ session cookie →BFF→ access token →APIs
Use it for
Business software, financial or health-related workflows, and applications handling valuable personal data.
Choose it when
Keeping all OAuth tokens out of JavaScript matters more than operating an additional proxy layer.
Browser holds
Only an HttpOnly session cookie.
Main trade-off
Every API request passes through the BFF, adding infrastructure, latency, capacity, and proxy-security responsibilities.

4. Token-mediating backend

Middle ground

The backend performs the OAuth login and safely retains the refresh token. It gives React a short-lived access token, which React then uses to call resource APIs directly.

Token backend→ access token →React→APIs
Use it for
Large downloads, streaming, or high-volume APIs where proxying every response through a BFF is impractical.
Choose it when
You need direct API calls but want refresh tokens and OAuth client credentials to remain server-side.
Browser holds
A short-lived access token, but not the refresh token.
Main trade-off
Access tokens are still exposed to browser JavaScript. Check whether a full BFF is feasible first.

5. Browser-only OAuth client

Use with care

React performs the OAuth Authorization Code flow with PKCE and receives tokens directly from the identity provider. There is no application backend helping with token management.

React↔ code + PKCE ↔Identity provider→ token →APIs
Use it for
Static public clients, lower-risk applications, prototypes, or environments where a backend cannot be deployed.
Choose it when
The operational simplicity is worth exposing the token lifecycle to the browser.
Browser holds
Access tokens and, if issued, refresh tokens. Rotation or sender-constraining is required for refresh tokens.
Main trade-off
The largest browser attack surface. It is not recommended for sensitive business applications or applications handling personal data.

Patterns to avoid in new browser applications

  • OAuth Implicit flow: use Authorization Code with PKCE instead.
  • Resource Owner Password Credentials grant: do not collect an identity provider’s password in the SPA.
  • Long-lived tokens in localStorage: malicious JavaScript can read and export them.
  • A shared OAuth client secret inside React: code shipped to browsers cannot keep a secret.

The question to keep asking

Who is the OAuth or authentication client? In pattern A, the React application actively handles an access token. In pattern B, the Rust BFF is the OAuth client and React only knows about its application session.

3 · Pattern A

Access token + refresh cookie

This pattern gives the browser a short-lived credential for direct API calls while keeping the longer-lived credential out of JavaScript.

The mental model

The access token is the API pass. The refresh cookie is the way to ask for a new pass. React can read the first one, but cannot read the second one.

What each credential does

Access tokenRefresh token
PurposeCall protected endpointsObtain a new access token
Typical lifetimeMinutesDays or weeks
Browser locationJavaScript memoryHttpOnly cookie
Sent withAuthorization: Bearer …Only /auth/* routes
Server storageUsually verified without storageStore a hash or session record
Why memory instead of localStorage?

Any JavaScript running in the page can read localStorage. Keeping the access token in memory reduces persistence after a reload, but it does not make the token invisible to malicious JavaScript. XSS prevention and a strong Content Security Policy still matter.

3A · Pattern A request flow

From password sign-in to sign-out

Here is the complete lifecycle when the Rust authentication service owns the user accounts, React calls the API directly, and the database records refresh-token rotation.

Three kinds of state work together

The users row proves the password at sign-in. The short-lived access token proves the user’s identity to API endpoints and usually requires no database lookup. The auth_sessions and refresh_tokens rows control the longer-lived login, including rotation, reuse detection, and logout.

The minimal database model

Table or credentialImportant fieldsResponsibility
usersid, password_hashFinds the account and verifies the submitted password with Argon2id.
auth_sessionsid, user_id, expires_at, revoked_atRepresents one login on one browser or device. Its id is also the refresh-token family identifier.
refresh_tokenssession_id, token_hash, consumed_atKeeps the rotation history. Exactly one unconsumed token should exist for an active session.
Access tokensub, iss, aud, iat, exp, token typeLives briefly in React memory and is normally verified cryptographically rather than stored in the database.

The refresh cookie contains a cryptographically random secret. The database stores only a SHA-256 hash of that secret. Hashing the cookie value produces the lookup value, while a database leak does not reveal the credential that the browser can submit.

  1. React submits the credentials

    React sends the email and password over HTTPS. Rust loads the users row and verifies the submitted password against password_hash. A failure returns the same generic response whether the account or password was wrong.

    POST /auth/login

  2. Rust creates the database-backed login

    Inside a transaction, Rust inserts one auth_sessions row and generates refresh token A. It stores SHA-256(A) in refresh_tokens with the new session ID and consumed_at = NULL. The raw token A is never stored in the database.

  3. Rust returns the two credentials differently

    Rust returns a short-lived access token in JSON and sets raw refresh token A as a Secure, HttpOnly cookie restricted to the authentication routes. React keeps the access token only in memory; browser JavaScript cannot read the refresh cookie.

  4. React calls protected endpoints

    React places the access token in the Authorization header. Rust verifies its signature, algorithm, expiry, issuer, audience, and token type before the endpoint runs. This normally needs no session-table lookup, but the endpoint must still authorize the user’s requested action.

    GET /api/me

  5. The access token expires

    After a few minutes, the access token becomes invalid and the API returns 401 Unauthorized. React starts one refresh operation; concurrent failed requests share it rather than each rotating the cookie independently.

  6. Rust validates token A against the database

    React calls the refresh endpoint and the browser automatically sends token A. Rust hashes it, starts a database transaction, and loads its refresh_tokens row together with the parent auth_sessions row. The session must be unexpired and not revoked, and the token must have consumed_at = NULL.

    POST /auth/refresh

  7. Rust rotates A into B atomically

    In the same transaction, Rust sets token A’s consumed_at, generates token B, and inserts SHA-256(B) with the same session_id. After commit, the response replaces the cookie with raw token B and returns a new access token. Either every database change succeeds or none does.

  8. A consumed token reveals possible theft

    If token A is presented again, its row is still available but consumed_at is already set. Rust treats that reuse as compromise and sets auth_sessions.revoked_at. Because A and B share the same session, the new token B is rejected too.

  9. The user signs out

    Rust identifies the session through the refresh token and sets auth_sessions.revoked_at. It expires the cookie, and React removes the access token from memory. All refresh tokens under that session become unusable, while other device sessions remain signed in.

    POST /auth/logout

How rotation changes the database

The session row is stable. Rotation appends token history underneath it.

Why consumed tokens remain in the database

Deleting token A immediately would make a later copy look merely unknown. Retaining its hash and consumed_at lets Rust distinguish an invalid token from reuse of a credential that was previously valid. Old token rows can be removed when their parent session is safely past expiration.

Logout and access-token lifetime

Revoking the database session immediately stops refresh, but a stateless access token may remain valid until its short exp time. Applications that require immediate access-token revocation can include a session ID claim and check session state on each request, usually through a cache, at the cost of making validation stateful.

3B · Pattern A security boundary

React carries proof; Rust makes the decision

The browser may present a token, but it never decides whether that token is valid or whether the user may perform an action.

Authentication

Rust verifies the password and token signature, then determines which user the token represents.

Authorization

Each endpoint checks whether that user may read or change the requested resource.

Session continuity

The refresh endpoint rotates the protected refresh token and restores a short-lived access token.

What Rust must verify on every access token

  • The cryptographic signature and the expected signing algorithm.
  • The expiration time, issuer, audience, and any required token type.
  • The scopes or permissions required by the endpoint.

Do not accept a token merely because it can be decoded. JWT contents are readable by design; trust comes from successful validation against the expected keys and claims.

3C · Pattern A code

Rust issues tokens; React sends them

These examples show only the authentication boundary. Database functions and JWT helpers are represented by clearly named functions so the main flow stays easy to see.

Rust: define the routes

Public authentication routes create or end sessions. Middleware protects the application route.

api/src/main.rsAxum
use axum::{middleware, routing::{get, post}, Router};

let protected_routes = Router::new()

  • /auth/login must work before the user is authenticated.
  • /api/me runs only after the middleware accepts an access token.

Rust: sign in and set the refresh cookie

The backend verifies the password, creates both tokens, and returns them through different channels.

api/src/auth.rsLogin handler
use axum::{extract::State, response::IntoResponse, Json};
use axum_extra::extract::cookie::{Cookie, CookieJar, SameSite};
use serde::{Deserialize, Serialize};
use time::Duration;

#[derive(Deserialize)]
struct LoginBody {
    email: String,
    password: String,
}

#[derive(Serialize)]
struct TokenBody {
    access_token: String,
}

async fn login(
    State(state): State<AppState>,
    jar: CookieJar,
    Json(body): Json<LoginBody>,
) -> Result<impl IntoResponse, ApiError> {
    let user = state.users.find_by_email(&body.email).await?
        .ok_or(ApiError::InvalidCredentials)?;

    // Compare the password with its stored Argon2id hash.
    verify_password(&body.password, &user.password_hash).await?;

    let access_token = state.jwt
        .issue_access_token(user.id, Duration::minutes(10))?;

    // Store only a hash of this token in the database.
    let refresh_token = state.sessions.create(user.id).await?;

    let cookie = Cookie::build(("refresh", refresh_token))
        .path("/auth")
        .http_only(true)
        .secure(true)
        .same_site(SameSite::Lax)
        .max_age(Duration::days(14))
        .build();

    Ok((jar.add(cookie), Json(TokenBody { access_token })))
}
  • HttpOnly prevents JavaScript from reading the cookie.
  • Secure tells the browser to send it only over HTTPS.
  • SameSite=Lax helps reduce cross-site request forgery for a same-site application.

Rust: issue a short-lived access token

The JWT service creates an access token with a narrow lifetime and claims that the API can validate explicitly.

api/src/jwt.rsJWT signing
use jsonwebtoken::{encode, Algorithm, EncodingKey, Header};
use serde::{Deserialize, Serialize};
use time::{Duration, OffsetDateTime};

#[derive(Debug, Serialize, Deserialize)]
struct AccessTokenClaims {
    sub: String,
    iss: String,
    aud: String,
    iat: i64,
    exp: i64,
    token_use: String,
}

struct JwtService {
    encoding_key: EncodingKey,
    issuer: String,
    audience: String,
}

impl JwtService {
    fn issue_access_token(
        &self,
        user_id: i64,
        lifetime: Duration,
    ) -> Result<String, ApiError> {
        let issued_at = OffsetDateTime::now_utc();
        let expires_at = issued_at
            .checked_add(lifetime)
            .ok_or(ApiError::TokenCreation)?;

        let claims = AccessTokenClaims {
            sub: user_id.to_string(),
            iss: self.issuer.clone(),
            aud: self.audience.clone(),
            iat: issued_at.unix_timestamp(),
            exp: expires_at.unix_timestamp(),
            token_use: "access".to_owned(),
        };

        let mut header = Header::new(Algorithm::EdDSA);
        header.typ = Some("at+jwt".to_owned());

        encode(&header, &claims, &self.encoding_key)
            .map_err(|_| ApiError::TokenCreation)
    }
}
  • Load the Ed25519 private key once at startup from a secret manager; never commit it or read it for every request.
  • The verifier must require the same algorithm, issuer, audience, token_use, and typ values rather than trusting token-provided metadata.
  • Keep the lifetime short. Authorization still belongs to each endpoint, using server-trusted permissions or carefully scoped claims.

Rust: protect an endpoint

Middleware checks the bearer token before the endpoint runs.

api/src/auth_middleware.rsAuthorization
use axum::{
    extract::{Request, State},
    http::{header, StatusCode},
    middleware::Next,
    response::Response,
};

async fn require_access_token(
    State(state): State<AppState>,
    mut request: Request,
    next: Next,
) -> Result<Response, StatusCode> {
    let token = request.headers()
        .get(header::AUTHORIZATION)
        .and_then(|value| value.to_str().ok())
        .and_then(|value| value.strip_prefix("Bearer "))
        .ok_or(StatusCode::UNAUTHORIZED)?;

    let claims = state.jwt.verify(token)
        .map_err(|_| StatusCode::UNAUTHORIZED)?;

    request.extensions_mut().insert(CurrentUser {
        id: claims.user_id,
    });

    Ok(next.run(request).await)
}

The real verifier must check the signature, expiration time, issuer, audience, and expected signing algorithm.

React: keep the access token in memory

The frontend adds the token to API requests. If it receives a 401, it refreshes once and retries once.

src/api.jsReact client
let accessToken = null;
let refreshInProgress = null;

export async function signIn(email, password) {
  const response = await fetch("/auth/login", {
    method: "POST",
    credentials: "include",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ email, password }),
  });

  if (!response.ok) throw new Error("Invalid email or password");
  const body = await response.json();
  accessToken = body.access_token;
}

async function refreshOnce() {
  if (!refreshInProgress) {
    refreshInProgress = fetch("/auth/refresh", {
      method: "POST",
      credentials: "include",
    })
      .then(async (response) => {
        if (!response.ok) throw new Error("Session expired");
        const body = await response.json();
        accessToken = body.access_token;
      })
      .finally(() => { refreshInProgress = null; });
  }

  return refreshInProgress;
}

export async function api(path, options = {}, canRetry = true) {
  const headers = new Headers(options.headers);
  if (accessToken) {
    headers.set("Authorization", `Bearer ${accessToken}`);
  }

  let response = await fetch(path, { ...options, headers });

  if (response.status === 401 && canRetry) {
    await refreshOnce();
    response = await api(path, options, false);
  }

  return response;
}
  • The access token disappears when the page reloads. The app can call refresh on startup to restore the session.
  • Sharing one refresh promise prevents several failed requests from rotating the same refresh token at the same time.
  • The retry happens only once, so a broken session cannot create an infinite loop.
What the examples leave out

A real application also needs database transactions for refresh rotation, rate limiting, password-reset flows, email verification, key rotation, logging, monitoring, and usually multi-factor authentication for sensitive accounts.

4 · Pattern B

Backend-for-Frontend with OAuth

The BFF is a small server-side component dedicated to the React application. It becomes the confidential OAuth client, owns every token, and exposes a cookie-authenticated API designed for that frontend.

The mental model

React has an application session, not an OAuth token. The Rust BFF translates the session cookie into an access token only when it calls an approved downstream API.

OAuth and OpenID Connect are related, but not identical

OAuth 2.0

Delegates access to protected APIs. Its access token answers: “What may this client call?”

OpenID Connect

Adds user authentication to OAuth. Its ID token tells the client who authenticated.

Application session

Lets React remain signed in to the BFF. It is represented by an opaque cookie, not by the ID token.

For “Sign in with an identity provider,” a BFF normally runs the OpenID Connect Authorization Code flow: it requests the openid scope, validates the returned ID token, and also receives OAuth access tokens for APIs.

4A · Architecture graph

Four parties, one browser-safe boundary

4B · Authorization Code flow

From “Sign in” to an API response

1
React checks its application session

It requests GET /bff/session. With no valid session cookie, the BFF returns an unauthenticated result.

2
The BFF starts a secure authorization request

The browser navigates to /oauth/login. Rust creates unpredictable state and nonce values plus a PKCE verifier and S256 challenge. It stores the temporary transaction server-side, then redirects to the identity provider.

3
The identity provider authenticates the user

The provider handles the password, passkey, MFA, and consent screens. Your React application never receives those credentials.

4
The provider returns a short-lived authorization code

The browser is redirected to /oauth/callback?code=…&state=…. The callback belongs to the BFF, not React.

5
The BFF exchanges the code and validates the result

Rust checks the stored state, sends the code with its PKCE verifier and confidential-client authentication, then validates the ID token’s signature, issuer, audience, expiry, and nonce.

6
The BFF creates an application session

Access and refresh tokens stay in the server-side session store. The browser receives only a random cookie such as __Host-session with Secure, HttpOnly, SameSite=Strict, and Path=/.

7
React calls the BFF, and the BFF calls the API

React requests a fixed route such as /bff/api/me. Rust loads the session, refreshes the access token server-side if necessary, adds the bearer token to an allowlisted API request, and returns only the API response.

8
Logout removes the local session

The BFF deletes the server-side session, expires the cookie, and—when required—revokes tokens or initiates identity-provider logout.

Rust: begin Authorization Code + PKCE

bff/src/oauth.rsLogin redirect
async fn oauth_login(
    State(app): State<AppState>,
) -> Result<Redirect, ApiError> {
    let csrf_state = CsrfToken::new_random();
    let nonce = Nonce::new_random();
    let (challenge, verifier) = PkceCodeChallenge::new_random_sha256();

    // Short expiry; remove it as soon as the callback uses it.
    app.login_transactions.insert(
        csrf_state.secret(),
        LoginTransaction {
            pkce_verifier: verifier.secret().to_owned(),
            nonce: nonce.secret().to_owned(),
        },
    ).await?;

    let (authorization_url, _) = app.oidc
        .authorize_url(|| csrf_state)
        .add_scope(Scope::new("openid".into()))
        .add_scope(Scope::new("profile".into()))
        .set_pkce_challenge(challenge)
        .add_extra_param("nonce", nonce.secret())
        .url();

    Ok(Redirect::temporary(authorization_url.as_str()))
}

Use the provider’s discovery document and exact registered redirect URI. Use the S256 PKCE method; never send the verifier in the authorization request.

Rust: exchange the code and create a session

bff/src/oauth.rsCallback
#[derive(Deserialize)]
struct CallbackQuery { code: String, state: String }

async fn oauth_callback(
    State(app): State<AppState>,
    jar: CookieJar,
    Query(query): Query<CallbackQuery>,
) -> Result<impl IntoResponse, ApiError> {
    // "take" makes the state one-time use.
    let tx = app.login_transactions.take(&query.state).await?
        .ok_or(ApiError::InvalidOAuthCallback)?;

    let tokens = app.oidc
        .exchange_code(
            AuthorizationCode::new(query.code),
            PkceCodeVerifier::new(tx.pkce_verifier),
        )
        .await?; // Uses confidential-client authentication.

    let identity = app.oidc
        .validate_id_token(&tokens.id_token, &tx.nonce)
        .await?; // signature, issuer, audience, expiry, nonce

    // Store access and refresh tokens only on the server.
    let session_id = app.sessions
        .create(identity.subject, tokens)
        .await?;

    let cookie = Cookie::build(("__Host-session", session_id))
        .path("/")
        .secure(true)
        .http_only(true)
        .same_site(SameSite::Strict)
        .build();

    Ok((jar.add(cookie), Redirect::to("/")))
}

The helper names make the security boundary visible. In production, use a maintained OAuth/OIDC library rather than implementing discovery, token exchange, or ID-token verification yourself.

Rust: call one approved downstream endpoint

bff/src/proxy.rsAPI forwarding
async fn proxy_me(
    State(app): State<AppState>,
    SessionId(session_id): SessionId,
) -> Result<impl IntoResponse, ApiError> {
    // Refreshes server-side when the access token is near expiry.
    let access_token = app.sessions
        .valid_access_token(&session_id)
        .await?;

    // Fixed host, fixed path, fixed method: never proxy an arbitrary URL.
    let response = app.http
        .get("https://api.example.com/v1/me")
        .bearer_auth(access_token)
        .send()
        .await?;

    Ok((response.status(), response.bytes().await?))
}

React: use the BFF without handling tokens

src/bff.jsReact client
export function signIn() {
  // OAuth is a navigation flow, not an AJAX login request.
  window.location.assign("/oauth/login");
}

export async function getSession() {
  const response = await fetch("/bff/session", {
    credentials: "same-origin",
  });
  if (!response.ok) return null;
  return response.json(); // safe user fields, never tokens
}

export async function bff(path, options = {}) {
  const headers = new Headers(options.headers);
  headers.set("X-CSRF", "1");

  return fetch(`/bff/api${path}`, {
    ...options,
    headers,
    credentials: "same-origin",
  });
}

export async function signOut() {
  await fetch("/bff/logout", {
    method: "POST",
    credentials: "same-origin",
    headers: { "X-CSRF": "1" },
  });
}
  • The custom header makes cross-origin scripted requests require a CORS preflight; the BFF must reject unknown origins and requests missing the header.
  • A per-session anti-CSRF token is another good choice, especially when the deployment shares a site with less-trusted subdomains.
  • Even with HttpOnly cookies, XSS can still send requests as the user while the page is open. Keep CSP and output encoding defenses.

5 · Choose between the two

Direct API flexibility or stronger token isolation?

Neither pattern removes the need for secure code. The decision is about where credentials live, who calls the APIs, and how much server infrastructure you want to operate.

QuestionAccess + refresh cookieOAuth BFF
Browser holdsAccess token in memory and an unreadable refresh cookieOnly an opaque HttpOnly session cookie
Who calls the API?React calls APIs directlyReact calls the BFF; the BFF calls APIs
OAuth tokens exposed to JavaScript?The access token is; the refresh token is notNo
Good fitSeveral APIs, mobile and web clients, direct downloads or streaming, and existing bearer-token APIsBusiness, sensitive, or personal-data applications using an identity provider

Main operational costRefresh rotation, CORS, and client-side token lifecycleA stateful security proxy on every browser-to-API request
A practical default
  • Choose the BFF when React is the primary client, you use OAuth/OIDC, the data is valuable, and proxying requests is acceptable.
  • Choose access + refresh when direct API calls are an important requirement, especially when the same API serves browser and non-browser clients.
  • Choose a plain server-side cookie session when one same-site web application owns both frontend and backend and OAuth access to separate resource servers is unnecessary.

6 · Production checklist

Before calling the system secure

  • Use HTTPS everywhere.Credentials and tokens must be encrypted while travelling over the network.
  • Use maintained security libraries.Do not handwrite password hashing, OAuth discovery, PKCE, JWT verification, or OpenID Connect validation.
  • Protect application cookies.Use Secure, HttpOnly, the narrowest workable SameSite setting, Path=/, no Domain attribute, and an unpredictable value.
  • Protect cookie-authenticated routes from CSRF.Validate origins and require a custom header or anti-CSRF token in addition to an appropriate SameSite setting.
  • Keep access tokens short-lived.For pattern A, a stolen browser token should stop working quickly. For a BFF, refresh and expiry handling stays server-side.
  • Rotate and detect refresh-token reuse.Pattern A must invalidate the old token transactionally. A BFF should follow the provider’s rotation and revocation behavior.
  • Validate every OAuth callback.Use Authorization Code + PKCE S256 and verify state, ID-token signature, issuer, audience, expiry, and nonce.
  • Restrict the BFF proxy.Map fixed BFF routes to allowlisted hosts, paths, and methods so an attacker cannot redirect a user’s token elsewhere.
  • Keep CORS narrow and deploy a CSP.Allow only the real frontend origin and reduce the chance that untrusted JavaScript can execute.
  • Do not log secrets.Passwords, cookies, authorization codes, client secrets, and complete tokens should never appear in application logs.

Remember the two mental models

  1. Access + refresh: React carries a short-lived API credential; Rust validates it and protects the longer-lived refresh session.
  2. OAuth BFF: React carries only a session cookie; Rust owns OAuth and attaches tokens only to approved server-to-server requests.

Redis Field Notes

How Redis works, and how to use it for seven common jobs. In the examples, lines starting with > are commands you can type into redis-cli. Grey text is a note or a reply.

What Redis is

Redis is a server that keeps data in memory and lets you work with it over the network. Your app connects on port 6379, sends a command like GET user:42, and gets a reply, usually in well under a millisecond on a local network.

A plain cache only stores values. Redis stores data structures: lists, sets, sorted sets, streams and more. Each one has its own commands that run on the server. You can ask "what is this player's rank?" without downloading the whole leaderboard. Nearly every usage below comes from picking the right structure.

How it works

Redis is fast for two reasons. Memory is far quicker than disk, and commands run one at a time on a single main thread. With no locks to manage and no two commands running together, every single command is atomic.

Newer versions use extra threads for network reads and writes and some background work, but commands still execute one by one. That one fact explains most Redis advice: keep commands short.

Data types

Keys are strings, usually named with colons, like user:42:cart. The value can be any of these types.

Expiry and eviction

Memory is limited, so Redis gives you two ways to remove data.

Expiry is your choice: SET key value EX 60 deletes the key after 60 seconds. Redis removes expired keys when they are next accessed, and also samples random keys in the background. An expired key is never returned, but it can hold memory for a short while.

Eviction is what happens when Redis reaches maxmemory. The default policy, noeviction, rejects new writes with an error. For a cache, set allkeys-lru or allkeys-lfu so that the least useful keys are dropped. Other policies, such as volatile-lru, only touch keys that have a TTL.

Persistence

Data lives in memory, but Redis can save it to disk so that it survives a restart.

RestartFastSlower, though the log is compacted over time

You can run both. If you only use Redis as a cache, you may not need either. Out of the box, RDB is on and AOF is off.

Atomic operations

A single command is atomic. Many real tasks need several commands, and there are three tools for that.

  • Pipeline: send many commands in one network trip. This is only for speed. Other clients' commands can run in between.
  • MULTI / EXEC: queue commands and run them as one block. There is no rollback: if one fails at runtime, the others still apply. Add WATCH to abort when a key changes first.
  • Lua script (EVAL): runs logic on the server as one atomic step, including "read, decide, then write", which MULTI cannot do. Keep scripts short, because nothing else runs until they finish.

Pros and cons

Pros

  • Very fast: most commands finish in well under a millisecond.
  • Useful data structures: the server does the ranking, counting and searching, so your app has less code to write.
  • Atomic commands: many concurrency problems go away, because commands never overlap.
  • Built-in expiry: short-lived data cleans itself up.
  • One tool, many jobs: a single Redis can handle caching, rate limiting and messaging.
  • Easy to start: the commands are simple, and nearly every language has a client library.

Cons

  • Memory is expensive: your whole dataset has to fit in RAM, which costs far more than disk.
  • Weaker durability: a crash or failover can lose recent writes, even with persistence turned on.
  • Limited querying: you mostly fetch data by key, so you design keys around your questions up front. There are no SQL joins, and ad-hoc questions are hard to answer.
  • One slow command hurts everyone: all clients wait behind it on the main thread.
  • No rollback: MULTI cannot undo commands, so it does not give you database-style transactions.
  • One more system to run: you have to monitor it, plan its memory and keep it in sync with your database. Cluster adds further limits on multi-key commands.

When to use it, and when not to

A good rule of thumb: Redis fits when you can find the data by key, it fits in memory, and losing the last second of it would be a small problem.

Use Redis when

  • The same data is read very often, and your database is too slow or too busy to serve it.
  • Data is short-lived or can be rebuilt, like sessions, cached results and rate limit counters.
  • Several servers need to share fast state, like counters, locks or online status.
  • The problem matches a data structure, like rankings, nearby search or queues.
  • You need live messaging between servers without running a separate message broker.

Choose something else when

You needBetter choice
The main record of orders, payments or usersA relational database, like PostgreSQL

Redis usually sits next to your main database and rarely replaces it. The database keeps the data safe, and Redis makes it fast.

Replication

A replica is a copy of the primary that stays up to date. Writes go to the primary only. Replicas give you backups, a standby for failover, and extra capacity for reads.

When a replica first connects, the primary takes an RDB snapshot and sends it over. After that, the primary streams every write command to the replica as it happens. If the connection drops for a moment, the replica asks to continue from its last position, using a buffer of recent writes on the primary called the backlog. If the replica was away too long and the backlog has moved on, it needs a full sync again, which is slow on a big dataset. Size repl-backlog-size (1 MB by default) to cover a few minutes of writes.

The key detail is that the primary replies to the client before any replica has the write.

This is also why a lock can disappear during failover, as the lock section explains. You can shrink this gap, but not remove it:

  • WAIT 1 100 after a write blocks until at least 1 replica confirms it, or 100 ms pass, and returns how many confirmed. Loss becomes less likely, but Redis does not become strongly consistent.
  • min-replicas-to-write 1 with min-replicas-max-lag 10 makes the primary refuse writes when no replica has checked in for 10 seconds. A primary cut off from the network then stops accepting writes that would be thrown away later.

Watch out: reads from a replica can be slightly old. A user who saves their profile and reloads the page might see the old version. Read from the primary right after a write, and send reads that can be a little stale, like product pages, to replicas.

Failover and Cluster

Replicas alone do not replace a failed primary. Something has to notice the failure and promote a replica.

Sentinel

Sentinel is a separate process that watches your primary. Run at least three of them on different machines. When enough of them agree the primary is down (the quorum), they promote the most up-to-date replica and point the other replicas at it. Your app asks Sentinel for the current primary address instead of hardcoding it. Failover takes a few seconds, and writes fail during that time, so clients need retries.

Cluster

Cluster splits your data across several primaries, each with its own replicas. Every key belongs to one of 16,384 hash slots, found with CRC16(key) % 16384, and each primary owns a range of slots. Nodes watch each other and fail over on their own, so Cluster does not need Sentinel. Start with at least three primaries, each with one replica.

Clients keep a map of which node owns which slot. A client that asks the wrong node gets a redirect and updates its map:

> GET foo
(error) MOVED 12182 10.0.0.5:6379   slot 12182 lives on 10.0.0.5

You can move slots between nodes while the cluster runs, to add capacity. During a move, clients may see temporary ASK redirects. Multi-key commands only work when all keys share a slot. Force this with hash tags: only the part inside {} is hashed, so {user:42}:cart and {user:42}:orders land together. In Rust, enable the redis crate's cluster-async feature for a cluster-aware client.

SetupGives youPick it when
Primary + replicasRead capacity and backups, with manual failoverLearning, or some downtime is acceptable
SentinelAutomatic failoverData and writes fit on one server
ClusterAutomatic failover, plus more memory and write capacityData or writes outgrow one server

Handling heavy load

Before changing anything, find out which limit you are hitting. Adding replicas does nothing for a write problem, and Cluster does nothing for one hot key.

SymptomLikely causeFirst fix
Main thread CPU near 100%, latency risingToo many commands, or slow onesPipeline, replace slow commands, then shard with Cluster
Memory near maxmemory, evictions or OOM errorsMore data than one server holdsTTLs, compact types like Hashes, Cluster
One node much busier than the restA hot key or a big keySee the list below
Timeouts while Redis CPU is lowNetwork trips or too many connectionsPipelining, connection reuse, sensible client timeouts
Replicas keep doing full syncsBacklog too small for the write rateLarger repl-backlog-size

Ways to take more load

  • Send fewer round trips. Pipeline batches, and use multi-value commands like MGET or HSET with many fields. Network trips usually cost more than the commands.
  • Reuse connections. Use a pool or one multiplexed connection. Thousands of short-lived connections waste memory and CPU.
  • Scale reads with replicas when slightly stale data is fine. Scale writes and memory with Cluster.
  • Spread hot keys. One very popular key lives on one node, even in a Cluster. Cache it inside your app for a second or two (with CLIENT TRACKING, Redis tells your app when it changes), or store several copies under different keys and read a random one.
  • Split big keys into smaller ones, and read large collections in pieces with HSCAN, SSCAN or ZSCAN.
  • Turn on I/O threads (io-threads 4) when reading and writing network data, not running commands, is what keeps the CPU busy.
  • Protect Redis from your app. Set client timeouts, and retry with exponential backoff and random jitter. Without that, a slow Redis receives a flood of retries and gets slower.

Measure it

> INFO stats                ops/sec, hits, misses, evictions
> INFO replication          replica offsets and lag
> SLOWLOG GET 10            slowest recent commands
redis-cli --latency         round-trip latency from your machine
redis-cli --bigkeys         largest key of each type

Redis as a cache

Built on: String or Hash, plus TTL

The most common pattern is cache-aside. The app checks Redis first. On a miss, it reads the database and stores the result with a TTL. On an update, it writes to the database and deletes the cached copy.

# read path
> GET product:7
(nil)                     miss, so load it from the database
> SET product:7 "{...}" EX 300

# write path, after updating the database
> DEL product:7

Deleting is safer than updating the cached value, because two concurrent updates can write to the cache in the wrong order.

Watch out: when a popular key expires, thousands of requests can hit the database at once. This is a cache stampede. Let one request rebuild the value behind a short lock, and add random jitter to TTLs so that keys do not all expire together. Always set a TTL, so any stale data fixes itself eventually.

Redis as a distributed lock

Built on: String with SET NX, plus Lua

A lock stops two servers from doing the same work at the same time. SET with NX only succeeds if the key does not exist, so exactly one client wins. The TTL frees the lock if the holder crashes. The value is a random token that proves who owns it.

> SET lock:order:42 8f3a91c2 NX PX 30000
OK                        you hold it for 30 seconds
> SET lock:order:42 b71e04d9 NX PX 30000
(nil)                     someone else is refused

To release it, check the token and delete in one atomic step. A plain DEL could remove a lock that has already expired and now belongs to someone else.

-- KEYS[1] = lock key, ARGV[1] = your token
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
end
return 0

Watch out: this lock is not perfectly safe. A paused process can outlive its TTL, and a failover can lose the lock because replication is asynchronous. Redlock uses several independent Redis nodes to reduce this risk, but its safety is debated. Use Redis locks to avoid duplicate work. If two holders would corrupt data, also protect the data itself, for example with a database constraint or a fencing token.

Redis for leaderboards

Built on: Sorted Set

A Sorted Set keeps members ordered by score at all times. Updates and rank lookups cost O(log N), so they stay fast with millions of players. A SQL ORDER BY on a busy score table struggles with the same job.

> ZADD game:scores 1200 ada 950 linus 1500 grace
> ZINCRBY game:scores 100 linus      add points
> ZRANGE game:scores 0 9 REV WITHSCORES  top 10
> ZREVRANK game:scores ada           ada's rank, 0 is first
> ZSCORE game:scores ada

Watch out: equal scores are ordered alphabetically by member, which is rarely fair. To reward whoever got there first, encode a timestamp in the score. Scores are 64-bit floats, so integers are only exact up to 253. For daily or weekly boards, use one key per period, like scores:2026-w45, and give it a TTL.

Redis for rate limiting

Built on: String counter, or Sorted Set, or Hash with Lua

Every API server shares the same counter in Redis, so a limit holds across all of them. The simplest version is a fixed window: one counter per user per minute.

> MULTI
> INCR rate:user42:1430
> EXPIRE rate:user42:1430 60 NX   only sets a TTL if none exists
> EXEC
1) (integer) 7                   7th request this minute
2) (integer) 0                   TTL was already set

If the count is above your limit, reject the request. Running both commands in MULTI matters: if a crash landed between them, the key would never expire and the user could stay blocked. EXPIRE ... NX needs Redis 7 or newer.

AlgorithmHowTrade-off
Fixed windowINCR per time windowTiny and fast, but allows up to double the limit around a window edge
Sliding logSorted Set of request timestamps. Trim old ones, then countAccurate, but stores one entry per request
Token bucketHash of tokens and last refill time, updated by LuaAllows short bursts with a steady average rate

Watch out: decide what happens when Redis is down. Most public APIs let requests through ("fail open"). Login and payment endpoints may be safer rejecting them ("fail closed").

Redis for proximity search

Built on: Geo, which is a Sorted Set

Redis turns each longitude and latitude into a single number called a geohash and uses it as the Sorted Set score. Nearby places get similar numbers, so finding them is a matter of scanning a few score ranges.

> GEOADD stores 13.361389 38.115556 palermo 15.087269 37.502669 catania
> GEOSEARCH stores FROMLONLAT 15 37 BYRADIUS 200 km ASC WITHDIST
1) 1) "catania"
   2) "56.4413"
2) 1) "palermo"
   2) "190.4424"

Watch out: longitude comes before latitude, the reverse of most map tools. Members cannot have their own TTL, so moving objects like drivers need regular updates, and old entries must be removed with ZREM. For large datasets, use one key per city or region so that no single key grows too big. Use GEOSEARCH in new code, not the older GEORADIUS.

Redis for event sourcing

Built on: Stream

Event sourcing stores what happened instead of only the current state. An order's status comes from replaying its events: created, paid, shipped. A Stream fits because it is an append-only log. Every entry gets an ordered ID made of a millisecond timestamp and a sequence number.

> XADD order:42 * type created total 99
"1793577600000-0"
> XADD order:42 * type paid
"1793577600412-0"
> XRANGE order:42 - +            replay all events, oldest first

Consumer groups share the work among workers. Each entry goes to one worker in the group, and it stays pending until that worker confirms it. If a worker crashes, another can claim its entries with XAUTOCLAIM.

> XGROUP CREATE order:42 billing 0
> XREADGROUP GROUP billing worker-1 COUNT 10 BLOCK 5000 STREAMS order:42 >
> XACK order:42 billing 1793577600000-0

Watch out: in event sourcing, the log is your source of truth, and Redis keeps it all in memory. Long histories get expensive, and with default settings a crash can lose recent events. Enable AOF if you depend on the log. Trimming with MAXLEN saves memory but deletes history you may need to replay. Streams are a great fit for learning and for short-lived event pipelines. For permanent records, teams often keep the full log in a database or Kafka. Delivery is at-least-once, so make your workers safe to run twice.

Redis for Pub/Sub

Built on: channels, which store nothing

Publishers send a message to a named channel, and Redis instantly pushes it to everyone subscribed at that moment. Senders and receivers do not need to know each other. It suits live updates such as chat, notifications, and telling other servers to clear a local cache.

# terminal 1
> SUBSCRIBE chat:room1
# terminal 2
> PUBLISH chat:room1 "hello"
(integer) 1               number of subscribers who received it
# pattern subscribe
> PSUBSCRIBE chat:*

Messages are fire and forget. If a subscriber is offline, or is too slow and gets disconnected, its messages are gone. Choose by how much a lost message matters.

Pub/SubStreamList
StoredNoYesUntil popped
ReceiversAll subscribersEach group, or one worker within itOne worker
Replay historyNoYesNo
Best forLive signalsEvents you must not loseSimple job queues

Watch out: a connection in subscribe mode is normally dedicated to that job, so open a separate one for other commands. In a Cluster, regular Pub/Sub messages travel to every node. Sharded Pub/Sub (SPUBLISH, SSUBSCRIBE, Redis 7+) scales better.

Know before production

  • Never run KEYS * in production. It walks every key and blocks everyone. Use SCAN, which works in small steps.
  • Avoid big keys. A Hash with millions of fields makes commands slow and deletes painful. Split it up, and delete large keys with UNLINK, which frees memory in the background.
  • Watch slow commands. SLOWLOG GET shows them. Avoid fetching whole collections with commands like SMEMBERS or HGETALL on large keys.
  • Reuse connections. Use a pool or a shared connection, and pipeline batches. Most of a request's time is the network trip.
  • Leave spare memory. Snapshots and log rewrites fork the process, and memory use can grow while writes continue during the fork.
  • Secure it. Keep Redis on a private network and use passwords or ACLs, plus TLS where traffic crosses networks. Never expose port 6379 to the internet.
  • Be careful treating it as your main database. Check your persistence settings and how much data loss you can accept. All data also has to fit in memory, which is expensive.
  • Know the licensing. Redis left its BSD license in 2024, which led to Valkey, a Linux Foundation fork that remains BSD. Redis 8 added AGPLv3 as an option. Core commands in this guide work on both.

Start with Rust

Run a local server with Docker, then add the redis crate.

docker run --rm -p 6379:6379 redis:8
cargo add redis
use redis::Commands;

fn main() -> redis::RedisResult<()> {
    let client = redis::Client::open("redis://127.0.0.1:6379/")?;
    let mut con = client.get_connection()?;

    let _: () = con.set_ex("greeting", "hello", 60)?;
    let value: Option<String> = con.get("greeting")?;
    println!("{value:?}");

    Ok(())
}

A good way to practice is to build the usages in this order: cache, rate limiter, leaderboard, lock, Pub/Sub, geo, then streams. Each one adds a new data type or idea. For real services, enable the crate's Tokio support and use get_multiplexed_async_connection.

# Defining and Instantiating Structs

Structs are similar to tuples in that they hold multiple related values, which can be of different types. However, structs require you to name each piece of data, making them more flexible than tuples because you do not have to rely on order to access values.

## Defining a Struct

To define a struct, use the `struct` keyword followed by a name for the entire struct. Inside curly brackets, define the names and types of the fields.

```rust
struct User {
    active: bool,
    username: String,
    email: String,
    sign_in_count: u64,
}

fn main() {}

```

## Instantiating and Accessing Data

To use a struct, create an instance by specifying concrete values for each field using `key: value` pairs. The fields do not need to be in the same order as the definition.

```rust
fn main() {
    let user1 = User {
        email: String::from("someone@example.com"),
        username: String::from("someusername123"),
        active: true,
        sign_in_count: 1,
    };
}

```

### Accessing and Modifying Fields

Use dot notation to access values (e.g., `user1.email`). If the instance is mutable, you can change a value using dot notation. Note that the entire instance must be mutable; Rust does not allow marking only specific fields as mutable.

```rust
fn main() {
    let mut user1 = User {
        email: String::from("someone@example.com"),
        username: String::from("someusername123"),
        active: true,
        sign_in_count: 1,
    };

    user1.email = String::from("anotheremail@example.com");
}

```

## Field Init Shorthand

When variables used to instantiate a struct have the same name as the struct fields, you can use the _field init shorthand_ to avoid repetition.

```rust
fn build_user(email: String, username: String) -> User {
    User {
        active: true,
        username, // shorthand for username: username
        email,    // shorthand for email: email
        sign_in_count: 1,
    }
}

```

## Struct Update Syntax

This syntax allows you to create a new instance of a struct that uses most of the values from an existing instance. The syntax `..user1` specifies that remaining fields not explicitly set should take their values from `user1`.

```rust
fn main() {
    // --snip--
    let user1 = User {
        email: String::from("someone@example.com"),
        username: String::from("someusername123"),
        active: true,
        sign_in_count: 1,
    };

    let user2 = User {
        email: String::from("another@example.com"),
        ..user1
    };
}

```

_Note: This moves data for fields that do not implement the `Copy` trait (like `String`), potentially invalidating the original instance (e.g., `user1` may no longer be valid if `username` was moved)._

## Tuple Structs

Tuple structs have the naming benefit of structs but look like tuples (fields have types but no names). They are useful for creating distinct types from other tuples.

```rust
struct Color(i32, i32, i32);
struct Point(i32, i32, i32);

fn main() {
    let black = Color(0, 0, 0);
    let origin = Point(0, 0, 0);
}

```

## Unit-Like Structs

You can define structs with no fields, called _unit-like structs_. These behave similarly to the unit type `()` and are useful when implementing traits on a type that doesn't need to store data.

```rust
struct AlwaysEqual;

fn main() {
    let subject = AlwaysEqual;
}

```

## Ownership of Struct Data

The examples typically use owned types (like `String`) rather than references (`&str`). This ensures the struct owns its data and the data remains valid as long as the struct does. Storing references in structs requires the use of **lifetimes** (discussed in later chapters) to ensure the referenced data remains valid.

## Borrowing Fields of a Struct

Rust's borrow checker tracks ownership permissions at both the struct level and the field level.

- If you borrow a field mutably, you cannot access the parent struct while that borrow is active.
- However, borrowing one field does not necessarily prevent you from accessing _other_ fields of the same struct, though the borrow checker sometimes assumes more fields are borrowed than they actually are (requiring careful management of permissions).

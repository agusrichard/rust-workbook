# 20.1 - Unsafe Rust

## High-Level Overview

Rust contains an "unsafe" sublanguage that permits operations the compiler cannot verify as memory-safe. This feature exists because:

1. Static analysis is inherently conservative — the compiler rejects some valid programs when it can't be confident they're safe.
2. Underlying hardware is inherently unsafe — systems programming, OS interaction, and FFI require low-level operations that Rust's normal guarantees would prohibit.

The key mental model: `unsafe` **does not disable the borrow checker or other safety mechanisms**. It only unlocks five specific additional capabilities ("superpowers") that the compiler cannot verify.

---

## The Five Unsafe Superpowers

Inside an `unsafe` block or function, you gain access to:

1. **Dereference raw pointers**
2. **Call unsafe functions or methods**
3. **Access or modify mutable static variables**
4. **Implement unsafe traits**
5. **Access union fields**

```
Safe Rust
┌────────────────────────────────────────────┐
│  Borrow checker, type system, lifetimes    │
│  ┌──────────────────────────────────────┐  │
│  │  unsafe { ... }                      │  │
│  │  + raw pointer deref                 │  │
│  │  + unsafe fn calls                   │  │
│  │  + mutable static access             │  │
│  │  + unsafe trait impl                 │  │
│  │  + union field access                │  │
│  └──────────────────────────────────────┘  │
└────────────────────────────────────────────┘
```

> Best practice: keep `unsafe` blocks as small as possible and document safety invariants.

## Raw Pointers

Raw pointers come in two flavors:
- `*const T` — immutable raw pointer
- `*mut T` — mutable raw pointer

### Creating Raw Pointers (safe code)

```rust
fn main() {
    let mut num = 5;

    let r1 = &raw const num;
    let r2 = &raw mut num;
}
```

You can also create raw pointers from arbitrary addresses (dangerous — only useful in very low-level contexts):

```rust
fn main() {
    let address = 0x012345usize;
    let r = address as *const i32;
}
```

### Dereferencing Raw Pointers (requires `unsafe`)

```rust
fn main() {
    let mut num = 5;

    let r1 = &raw const num;
    let r2 = &raw mut num;

    unsafe {
        println!("r1 is: {}", *r1);
        println!("r2 is: {}", *r2);
    }
}
```

### Raw Pointer Characteristics

Unlike references and smart pointers, raw pointers:
- **Ignore borrowing rules** — you can have multiple mutable raw pointers simultaneously
- Are **not guaranteed** to point to valid memory
- **May be null**
- Lack **automatic cleanup** (no `Drop`)

## Unsafe Functions and Methods

Unsafe functions are declared and must be called within `unsafe` blocks:

```rust
fn main() {
    unsafe fn dangerous() {}

    unsafe {
        dangerous();
    }
}
```

Calling an unsafe function outside an `unsafe` block is a compile error.

### Safe Abstractions Over Unsafe Code

A key pattern: wrap unsafe internals in a safe public API. `split_at_mut` is a standard library example that *cannot* be implemented in safe Rust alone, because the borrow checker can't prove two non-overlapping mutable slices are safe:

```rust
use std::slice;

fn split_at_mut(values: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    let len = values.len();
    let ptr = values.as_mut_ptr();

    assert!(mid <= len);

    unsafe {
        (
            slice::from_raw_parts_mut(ptr, mid),
            slice::from_raw_parts_mut(ptr.add(mid), len - mid),
        )
    }
}

fn main() {
    let mut vector = vec![1, 2, 3, 4, 5, 6];
    let (left, right) = split_at_mut(&mut vector, 3);
}
```

The function is safe to call from safe code — the unsafety is contained and justified.

## Foreign Function Interface (FFI)

The `extern` keyword enables calling functions from other languages. The `"C"` specifies the ABI (Application Binary Interface).

### Calling C from Rust

```rust
unsafe extern "C" {
    fn abs(input: i32) -> i32;
}

fn main() {
    unsafe {
        println!("Absolute value of -3 according to C: {}", abs(-3));
    }
}
```

If a foreign function is actually safe to call, you can annotate it explicitly:

```rust
unsafe extern "C" {
    safe fn abs(input: i32) -> i32;
}

fn main() {
    println!("Absolute value of -3 according to C: {}", abs(-3));
}
```

### Exposing Rust Functions to Other Languages

Use `#[unsafe(no_mangle)]` to prevent Rust from mangling the function name, making it callable from C:

```rust
#[unsafe(no_mangle)]
pub extern "C" fn call_from_c() {
    println!("Just called a Rust function from C!");
}
```

## Mutable Static Variables

Global variables in Rust are called **static variables**. Immutable statics are fine in safe code:

```rust
static HELLO_WORLD: &str = "Hello, world!";

fn main() {
    println!("value is: {HELLO_WORLD}");
}
```

**Mutable** statics require `unsafe` to access, because concurrent mutation from multiple threads is undefined behavior:

```rust
static mut COUNTER: u32 = 0;

/// SAFETY: Calling this from more than a single thread at a time is undefined
/// behavior, so you *must* guarantee you only call it from a single thread at
/// a time.
unsafe fn add_to_count(inc: u32) {
    unsafe {
        COUNTER += inc;
    }
}

fn main() {
    unsafe {
        // SAFETY: This is only called from a single thread in `main`.
        add_to_count(3);
        println!("COUNTER: {}", *(&raw const COUNTER));
    }
}
```

> Convention: write a `// SAFETY:` comment on every `unsafe` block explaining *why* it is actually safe.

## Unsafe Traits

A trait is `unsafe` when it contains invariants the compiler cannot verify. Implementing it requires `unsafe impl`:

```rust
unsafe trait Foo {
    // methods go here
}

unsafe impl Foo for i32 {
    // method implementations go here
}

fn main() {}
```

A real-world example: manually implementing `Send` or `Sync` for a type that contains raw pointers, where you must manually prove thread-safety.

---

## Accessing Union Fields

A `union` is like a `struct` but only one field is active at a time (similar to C unions). Accessing fields is unsafe because the compiler cannot know which field is currently valid:

```rust
union MyUnion {
    f1: u32,
    f2: f32,
}
```

Unions are primarily used for interoperability with C code.

## Miri: Detecting Undefined Behavior

**Miri** is an official Rust tool that detects undefined behavior in unsafe code through *runtime* analysis (as opposed to compile-time). It requires nightly Rust.

### Installation

```bash
rustup +nightly component add miri
```

### Usage

```bash
cargo +nightly miri run
cargo +nightly miri test
```

### Example: Miri catching UB

```rust
fn main() {
    use std::slice;

    let address = 0x01234usize;
    let r = address as *mut i32;

    let values: &[i32] = unsafe { slice::from_raw_parts_mut(r, 10000) };
}
```

Miri will flag this as undefined behavior (creating a slice from a garbage address).

## Key Takeaways

| Concept | Summary |
|---|---|
| `unsafe` block | Opts into 5 superpowers; doesn't disable borrow checker |
| Raw pointers | No lifetime/null/alias guarantees; must deref in `unsafe` |
| Safe abstractions | Wrap unsafe internals in safe APIs to limit exposure |
| FFI (`extern "C"`) | Call C from Rust or expose Rust to C |
| Mutable statics | Global mutable state; requires `unsafe` due to data race risk |
| Unsafe traits | Traits with invariants the compiler can't verify |
| Miri | Runtime UB detector for unsafe code |

For deeper guidance, see [The Rustonomicon](https://doc.rust-lang.org/nomicon/).

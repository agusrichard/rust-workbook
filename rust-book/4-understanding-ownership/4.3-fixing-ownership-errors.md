# Fixing Ownership Errors

Learning to fix ownership errors involves understanding **why** the borrow checker rejected the code. The key is to determine if the program is **unsafe** (could lead to undefined behavior) or **safe** (but the compiler doesn't understand it).

## Case 1: Returning a Reference to the Stack (Unsafe)

A common error is trying to return a reference to a variable created within the function. This is unsafe because the variable is dropped when the function returns, leaving the reference pointing to invalid memory.

**Problem:**

```rust
fn return_a_string() -> &String {
    let s = String::from("Hello world");
    &s // Error: `s` is dropped here, so `&s` would be invalid
}

```

**Solutions:**

1. **Return Ownership:** Change the return type to `String` to move ownership out of the function.
2. **Return a String Literal:** If the string is constant, return `&'static str`.
3. **Use Reference Counting:** Use `Rc<String>` to share ownership (runtime check).
4. **Caller Provides Slot:** Pass a mutable reference (`&mut String`) as an argument for the function to fill.

## Case 2: Not Enough Permissions (Unsafe)

Errors often occur when trying to mutate data that is only borrowed immutably.

**Problem:**

```rust
fn stringify_name_with_title(name: &Vec<String>) -> String {
    name.push(String::from("Esq.")); // Error: `name` is &Vec (read-only)
    let full = name.join(" ");
    full
}

```

This is unsafe because `push` could reallocate the vector, invalidating other references to `name` held by the caller.

**Solutions:**

1. **Change the Function Body (Recommended):** Avoid mutating the input. Clone the data or construct a new result locally.

```rust
// Example: Clone first, then mutate the local copy
let mut name_clone = name.clone();
name_clone.push(String::from("Esq."));

```

2. **Change Input Type:** Changing to `&mut Vec` (mutable reference) or `Vec` (taking ownership) fixes the error but might be API-unfriendly if the caller doesn't expect their data to be modified or consumed.

## Case 3: Aliasing and Mutating (Unsafe)

Rust prevents using a reference to a collection while simultaneously mutating that collection (e.g., pushing to a vector).

**Problem:**

```rust
let largest = &dst[0]; // Immutable borrow
dst.push(src[0].clone()); // Mutable borrow (Error: `largest` is still active)
println!("{}", largest);

```

This is unsafe because `push` might reallocate `dst`, causing `largest` to point to freed memory.

**Solutions:**

1. **Shorten the Lifetime:** Ensure the immutable borrow (`largest`) is no longer needed before the mutation (`push`) occurs.
2. **Clone Data:** Clone `largest` so it owns its data and isn't tied to `dst`.

## Case 4: Mutating Different Tuple Fields (Safe)

Rust's borrow checker tracks permissions at a fine-grained level (fields), but sometimes it gets confused if it can't prove fields are separate.

**Safe Example:**
Rust _can_ handle splitting borrows on struct/tuple fields if the compiler sees them directly.

```rust
let mut name = (String::from("Ferris"), String::from("Rustacean"));
let first = &name.0; // Borrows only field 0
name.1.push_str(", Esq."); // Mutates field 1 (Safe!)
println!("{first} {}", name.1);

```

**Unsafe-Looking Safe Example (Arrays/Slices):**
Rust _cannot_ easily track individual elements of an array or slice at compile time.

```rust
let mut a = [0, 1, 2, 3];
let x = &mut a[0];
let y = &a[1]; // Error: Rust treats `a` as a single unit being borrowed mutably

```

**Solution:** Use standard library functions like `split_at_mut` which use `unsafe` blocks internally to verify safety that the compiler cannot deduce.

## Summary Strategy

- **Is it actually unsafe?**
- **Yes:** Change the design (ownership, lifetimes, API) to ensure memory safety.
- **No:** Work around the borrow checker's limitations (e.g., use `split_at_mut`, reorder code).

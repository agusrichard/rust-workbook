# 15.6 - Reference Cycles Can Leak Memory

## High-Level Overview

Rust's memory safety guarantees make it *difficult*, but **not impossible**, to accidentally create memory leaks. Using `Rc<T>` combined with `RefCell<T>` can produce **reference cycles** — situations where two or more values hold references to each other, preventing their reference counts from ever reaching zero. The values are never dropped, causing a memory leak.

The solution is to use **weak references** via `Weak<T>`, which allow non-owning references that don't prevent values from being cleaned up.

---

## Key Concepts

| Concept | Description |
|---|---|
| `Rc<T>` | Reference-counted smart pointer; value dropped when `strong_count` reaches 0 |
| `RefCell<T>` | Enables interior mutability at runtime |
| Reference Cycle | Two or more `Rc<T>` values pointing to each other; counts never reach 0 → memory leak |
| `Weak<T>` | A non-owning reference that increments `weak_count`, not `strong_count` |
| `Rc::downgrade()` | Creates a `Weak<T>` from an `Rc<T>` |
| `weak.upgrade()` | Attempts to get `Option<Rc<T>>`; returns `None` if the value was dropped |

---

## Creating a Reference Cycle

### The Setup

```rust
use crate::List::{Cons, Nil};
use std::cell::RefCell;
use std::rc::Rc;

#[derive(Debug)]
enum List {
    Cons(i32, RefCell<Rc<List>>),
    Nil,
}

impl List {
    fn tail(&self) -> Option<&RefCell<Rc<List>>> {
        match self {
            Cons(_, item) => Some(item),
            Nil => None,
        }
    }
}
```

The second element of `Cons` is now `RefCell<Rc<List>>`, allowing us to **mutate** which `List` a `Cons` variant points to at runtime.

### Creating the Cycle

```rust
fn main() {
    let a = Rc::new(Cons(5, RefCell::new(Rc::new(Nil))));

    println!("a initial rc count = {}", Rc::strong_count(&a));
    println!("a next item = {:?}", a.tail());

    let b = Rc::new(Cons(10, RefCell::new(Rc::clone(&a))));

    println!("a rc count after b creation = {}", Rc::strong_count(&a));
    println!("b initial rc count = {}", Rc::strong_count(&b));
    println!("b next item = {:?}", b.tail());

    if let Some(link) = a.tail() {
        *link.borrow_mut() = Rc::clone(&b); // a now points to b
    }

    println!("b rc count after changing a = {}", Rc::strong_count(&b));
    println!("a rc count after changing a = {}", Rc::strong_count(&a));

    // Uncommenting the next line would cause a stack overflow
    // println!("a next item = {:?}", a.tail());
}
```

### What Happens

- `a` is created pointing to `Nil`.
- `b` is created pointing to `a`. → `a.strong_count = 2`
- `a`'s tail is changed to point to `b`. → `b.strong_count = 2`
- When `main` ends, `b` is dropped first → `b.strong_count` goes to 1 (not 0).
- Then `a` is dropped → `a.strong_count` goes to 1 (not 0).
- **Neither value is ever fully dropped. Memory is leaked.**

---

## Preventing Reference Cycles with `Weak<T>`

### The Distinction

- **Strong references** (`Rc<T>`) express **ownership**. The value lives as long as there is at least one strong reference.
- **Weak references** (`Weak<T>`) express **non-owning** relationships. They don't affect when the value is dropped.

You call `Rc::downgrade(&rc_value)` to get a `Weak<T>`. This increments `weak_count`, **not** `strong_count`. A value is dropped when its `strong_count` reaches 0, regardless of `weak_count`.

To use a `Weak<T>`, you must call `.upgrade()`, which returns `Option<Rc<T>>`:
- `Some(Rc<T>)` if the value still exists.
- `None` if the value has already been dropped.

## Example: A Tree with Parent References

### Goal

Build a tree where:
- **Parents own children** — if a parent is dropped, its children are too.
- **Children reference their parent** — but don't own it (using `Weak<T>`).

### Node Definition

```rust
use std::cell::RefCell;
use std::rc::{Rc, Weak};

#[derive(Debug)]
struct Node {
    value: i32,
    parent: RefCell<Weak<Node>>,
    children: RefCell<Vec<Rc<Node>>>,
}
```

- `children: RefCell<Vec<Rc<Node>>>` — parent owns children via strong references.
- `parent: RefCell<Weak<Node>>` — child references parent weakly (no ownership).

### Building the Tree

```rust
fn main() {
    let leaf = Rc::new(Node {
        value: 3,
        parent: RefCell::new(Weak::new()),
        children: RefCell::new(vec![]),
    });

    println!(
        "leaf strong = {}, weak = {}",
        Rc::strong_count(&leaf),
        Rc::weak_count(&leaf),
    );

    {
        let branch = Rc::new(Node {
            value: 5,
            parent: RefCell::new(Weak::new()),
            children: RefCell::new(vec![Rc::clone(&leaf)]),
        });

        // Make leaf's parent point weakly to branch
        *leaf.parent.borrow_mut() = Rc::downgrade(&branch);

        println!(
            "branch strong = {}, weak = {}",
            Rc::strong_count(&branch),
            Rc::weak_count(&branch),
        );

        println!(
            "leaf strong = {}, weak = {}",
            Rc::strong_count(&leaf),
            Rc::weak_count(&leaf),
        );
    }
    // branch goes out of scope here. strong_count = 0 → dropped.
    // leaf.parent.upgrade() now returns None.

    println!("leaf parent = {:?}", leaf.parent.borrow().upgrade());
    println!(
        "leaf strong = {}, weak = {}",
        Rc::strong_count(&leaf),
        Rc::weak_count(&leaf),
    );
}
```

### Reference Counts Step by Step

| Event | `leaf` strong | `leaf` weak | `branch` strong | `branch` weak |
|---|---|---|---|---|
| After `leaf` created | 1 | 0 | — | — |
| After `branch` created (owns `leaf`) | 2 | 0 | 1 | 0 |
| After `leaf.parent = Rc::downgrade(&branch)` | 2 | 0 | 1 | 1 |
| After inner `{}` scope ends (branch dropped) | 1 | 0 | 0 (dropped) | — |

When `branch` is dropped:
- `branch.strong_count` reaches 0 → `branch` is deallocated.
- `branch.weak_count` (from `leaf.parent`) goes to 0, but this does NOT block deallocation.
- `leaf.parent.upgrade()` now returns `None`.
- `leaf` itself is unaffected and still valid.

---

## Important Points

- **Rust does not guarantee prevention of memory leaks.** The type system prevents data races and dangling pointers, but `Rc<T>` cycles are a programmer responsibility.
- Use `Weak<T>` for **back-references**, **parent pointers**, or any relationship that should not imply ownership.
- `Rc::downgrade()` creates a `Weak<T>` (increments `weak_count`).
- `Weak::upgrade()` returns `Option<Rc<T>>` — always handle the `None` case.
- If you are unsure whether to use `Rc` or `Weak`, ask: *"Should this relationship keep the value alive?"* If yes → `Rc`. If no → `Weak`.

---

## Summary

| | `Rc<T>` (strong) | `Weak<T>` |
|---|---|---|
| Ownership | Yes | No |
| Affects `strong_count` | Yes | No |
| Prevents drop | Yes | No |
| Allows access | Direct | Via `upgrade()` → `Option<Rc<T>>` |
| Risk | Reference cycles → memory leak | Safe for back-references |

Reference cycles are a logical bug, not a compiler error. The compiler won't catch them. Use `Weak<T>` intentionally in data structures where bidirectional references are needed (trees, graphs, observer patterns) to break potential cycles.

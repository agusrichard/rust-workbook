# 15.5 - `RefCell<T>` and the Interior Mutability Pattern

## Overview

**Interior mutability** is a design pattern in Rust that allows you to mutate data even when there are only immutable references to it. To achieve this, the pattern uses `unsafe` code inside a data structure to bend Rust's usual borrowing rules — but wraps it in a safe API so consumers don't need to think about it.

`RefCell<T>` is the standard library type that implements interior mutability. Unlike `Box<T>`, which enforces borrowing rules at **compile time**, `RefCell<T>` enforces them at **runtime**. Breaking the rules causes a `panic!` instead of a compile error.

> **Important**: `RefCell<T>` is only for use in **single-threaded** scenarios. For multi-threaded interior mutability, use `Mutex<T>`.

---

## Enforcing Borrowing Rules at Runtime with `RefCell<T>`

Rust's core borrowing rules:
1. At any given time, you can have *either* one mutable reference *or* any number of immutable references.
2. References must always be valid.

With `Box<T>`, these are checked at compile time. With `RefCell<T>`, they are checked at runtime. If you violate them, the program panics and exits.

**When to choose `RefCell<T>`**: when you know the borrowing rules are satisfied but the compiler cannot verify it (e.g., the logic depends on runtime state). It trades a compile error for a potential runtime panic, but it enables patterns that are otherwise impossible.

---

## Interior Mutability: A Mutable Borrow to an Immutable Value

Normally, the compiler prevents borrowing an immutable value mutably:

```rust
fn main() {
    let x = 5;
    let y = &mut x; // ERROR: cannot borrow `x` as mutable, as it is not declared as mutable
}
```

`RefCell<T>` provides a way around this for cases where you — the programmer — can guarantee safety even when the compiler cannot.

## A Use Case for Interior Mutability: Mock Objects

### The Problem

Consider a library that tracks how close a value is to a quota and sends messages via a `Messenger` trait:

**Listing 15-20 — Library code:**
```rust
pub trait Messenger {
    fn send(&self, msg: &str);
}

pub struct LimitTracker<'a, T: Messenger> {
    messenger: &'a T,
    value: usize,
    max: usize,
}

impl<'a, T> LimitTracker<'a, T>
where
    T: Messenger,
{
    pub fn new(messenger: &'a T, max: usize) -> LimitTracker<'a, T> {
        LimitTracker {
            messenger,
            value: 0,
            max,
        }
    }

    pub fn set_value(&mut self, value: usize) {
        self.value = value;

        let percentage_of_max = self.value as f64 / self.max as f64;

        if percentage_of_max >= 1.0 {
            self.messenger.send("Error: You are over your quota!");
        } else if percentage_of_max >= 0.9 {
            self.messenger
                .send("Urgent warning: You've used up over 90% of your quota!");
        } else if percentage_of_max >= 0.75 {
            self.messenger
                .send("Warning: You've used up over 75% of your quota!");
        }
    }
}
```

To test `LimitTracker`, we need a mock `Messenger` that records sent messages. The `send` method takes `&self` (immutable self), but we need to push to a `Vec` — which requires mutation.

### First Attempt (Fails to Compile)

**Listing 15-21 — Attempted mock object:**
```rust
#[cfg(test)]
mod tests {
    use super::*;

    struct MockMessenger {
        sent_messages: Vec<String>,
    }

    impl MockMessenger {
        fn new() -> MockMessenger {
            MockMessenger {
                sent_messages: vec![],
            }
        }
    }

    impl Messenger for MockMessenger {
        fn send(&self, message: &str) {
            self.sent_messages.push(String::from(message)); // ERROR: cannot borrow as mutable
        }
    }

    #[test]
    fn it_sends_an_over_75_percent_warning_message() {
        let mock_messenger = MockMessenger::new();
        let mut limit_tracker = LimitTracker::new(&mock_messenger, 100);

        limit_tracker.set_value(80);

        assert_eq!(mock_messenger.sent_messages.len(), 1);
    }
}
```

The compiler rejects this: `send` receives `&self`, so we cannot mutate `sent_messages` through it.

### Solution: Wrap in `RefCell<T>`

**Listing 15-22 — Using `RefCell<T>` in the mock object:**
```rust
#[cfg(test)]
mod tests {
    use super::*;
    use std::cell::RefCell;

    struct MockMessenger {
        sent_messages: RefCell<Vec<String>>,
    }

    impl MockMessenger {
        fn new() -> MockMessenger {
            MockMessenger {
                sent_messages: RefCell::new(vec![]),
            }
        }
    }

    impl Messenger for MockMessenger {
        fn send(&self, message: &str) {
            self.sent_messages.borrow_mut().push(String::from(message));
        }
    }

    #[test]
    fn it_sends_an_over_75_percent_warning_message() {
        let mock_messenger = MockMessenger::new();
        let mut limit_tracker = LimitTracker::new(&mock_messenger, 100);

        limit_tracker.set_value(80);

        assert_eq!(mock_messenger.sent_messages.borrow().len(), 1);
    }
}
```

Key changes:
- `sent_messages` is now `RefCell<Vec<String>>`.
- `borrow_mut()` returns a `RefMut<T>` smart pointer that allows mutation.
- `borrow()` returns a `Ref<T>` smart pointer for read access.

## Keeping Track of Borrows at Runtime with `RefCell<T>`

`RefCell<T>` tracks active borrows internally:
- Each call to `borrow()` increments an immutable borrow count; the count decrements when the returned `Ref<T>` goes out of scope.
- Each call to `borrow_mut()` acquires the single mutable borrow slot; it releases when the returned `RefMut<T>` goes out of scope.

If you violate the rules (e.g., calling `borrow_mut()` twice in the same scope), the program **panics at runtime**:

**Listing 15-23 — Causing a runtime borrow panic:**
```rust
impl Messenger for MockMessenger {
    fn send(&self, message: &str) {
        let mut one_borrow = self.sent_messages.borrow_mut();
        let mut two_borrow = self.sent_messages.borrow_mut(); // PANICS here at runtime

        one_borrow.push(String::from(message));
        two_borrow.push(String::from(message));
    }
}
```

Error at runtime:
```
thread 'main' panicked at 'already borrowed: BorrowMutError'
```

## Allowing Multiple Owners of Mutable Data with `Rc<T>` and `RefCell<T>`

`Rc<T>` allows multiple owners but only immutable access. `RefCell<T>` allows mutation through an immutable reference. Combining them — `Rc<RefCell<T>>` — gives you **multiple owners with mutation**:

**Listing 15-24 — Using `Rc<RefCell<i32>>` for shared mutable data:**
```rust
#[derive(Debug)]
enum List {
    Cons(Rc<RefCell<i32>>, Rc<List>),
    Nil,
}

use crate::List::{Cons, Nil};
use std::cell::RefCell;
use std::rc::Rc;

fn main() {
    let value = Rc::new(RefCell::new(5));

    let a = Rc::new(Cons(Rc::clone(&value), Rc::new(Nil)));

    let b = Cons(Rc::new(RefCell::new(3)), Rc::clone(&a));
    let c = Cons(Rc::new(RefCell::new(4)), Rc::clone(&a));

    *value.borrow_mut() += 10;

    println!("a after = {a:?}");
    println!("b after = {b:?}");
    println!("c after = {c:?}");
}
```

Output:
```
a after = Cons(RefCell { value: 15 }, Nil)
b after = Cons(RefCell { value: 3 }, Cons(RefCell { value: 15 }, Nil))
c after = Cons(RefCell { value: 4 }, Cons(RefCell { value: 15 }, Nil))
```

Mutating `value` through `borrow_mut()` is visible to all three lists (`a`, `b`, `c`) because they all share ownership of the same `Rc<RefCell<i32>>`.

## Key Takeaways

| Feature | `Box<T>` | `RefCell<T>` |
|---|---|---|
| Borrow rule enforcement | Compile time | Runtime |
| Violation result | Compile error | `panic!` |
| Allows interior mutability | No | Yes |
| Thread safety | Yes | Single-threaded only |

- `RefCell<T>` is useful when you need to mutate data behind an immutable reference and you can guarantee safety that the compiler cannot verify.
- Use `borrow()` for immutable access (`Ref<T>`) and `borrow_mut()` for mutable access (`RefMut<T>`).
- Combining `Rc<RefCell<T>>` enables the powerful pattern of **multiple-owner mutable data** in single-threaded code.
- For multi-threaded scenarios, use `Arc<Mutex<T>>` instead.

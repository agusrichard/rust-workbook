# 15.3 - Running Code on Cleanup with the `Drop` Trait

## High-Level Overview

The `Drop` trait lets you customize what happens when a value goes out of scope. Rust automatically calls your `drop` method at the end of a value's lifetime — no manual calls needed. This is the second critical trait (alongside `Deref`) that powers smart pointers, and it's also essential for managing any resource that needs cleanup: heap memory, file handles, network connections, mutex locks, etc.

> "You can specify that a particular bit of code be run whenever a value goes out of scope, and the compiler will insert this code automatically."

---

## Implementing the `Drop` Trait

The `Drop` trait lives in the prelude and requires one method: `drop`, which takes `&mut self`.

### Listing 15-14 — Basic `Drop` implementation

```rust
struct CustomSmartPointer {
    data: String,
}

impl Drop for CustomSmartPointer {
    fn drop(&mut self) {
        println!("Dropping CustomSmartPointer with data `{}`!", self.data);
    }
}

fn main() {
    let c = CustomSmartPointer {
        data: String::from("my stuff"),
    };
    let d = CustomSmartPointer {
        data: String::from("other stuff"),
    };
    println!("CustomSmartPointers created.");
}
```

**Output:**
```
CustomSmartPointers created.
Dropping CustomSmartPointer with data `other stuff`!
Dropping CustomSmartPointer with data `my stuff`!
```

### Key observations:

- `drop` is **called automatically** by Rust when variables go out of scope — you never call it yourself
- Variables are dropped in **reverse order of creation**: `d` was created after `c`, so `d` is dropped first
- The `println!` at the end of `main` runs *before* any drops, because drops happen *after* the final statement in the scope

---

## Dropping a Value Early with `std::mem::drop`

Sometimes you need to release a resource before the end of the scope — e.g., releasing a lock so another thread can proceed. The instinct is to call `c.drop()` directly, but Rust forbids this.

### Listing 15-15 — Calling `.drop()` directly (compile error)

```rust
fn main() {
    let c = CustomSmartPointer {
        data: String::from("some data"),
    };
    println!("CustomSmartPointer created.");
    c.drop();  // ERROR!
    println!("CustomSmartPointer dropped before the end of main.");
}
```

**Compiler error:**
```
error[E0040]: explicit use of destructor method
  --> src/main.rs:16:7
   |
16 |     c.drop();
   |       ^^^^ explicit destructor calls not allowed
   |
help: consider using `drop` function
   |
16 |     drop(c);
   |     +++++ ~
```

**Why is this forbidden?** Rust would still call `drop` automatically at the end of scope, resulting in a **double free** — the value's memory would be freed twice, which is undefined behavior.

### Listing 15-16 — Correct approach: `std::mem::drop`

```rust
fn main() {
    let c = CustomSmartPointer {
        data: String::from("some data"),
    };
    println!("CustomSmartPointer created.");
    drop(c);  // moves c into drop(), Rust knows not to drop it again
    println!("CustomSmartPointer dropped before the end of main.");
}
```

**Output:**
```
CustomSmartPointer created.
Dropping CustomSmartPointer with data `some data`!
CustomSmartPointer dropped before the end of main.
```

`std::mem::drop` is in the prelude — you can call `drop(value)` without any `use` statement. It **moves** the value in, taking ownership, so Rust knows the value has been dropped and won't drop it again at end of scope.

---

## Key Concepts Summary

| Concept | Detail |
|---|---|
| `Drop` trait | Implement `fn drop(&mut self)` to run cleanup logic |
| Automatic invocation | Rust inserts the `drop` call automatically when a value exits scope |
| Drop order | Reverse order of creation (LIFO) |
| Cannot call `.drop()` directly | Compiler error E0040 — prevents double free |
| `std::mem::drop(value)` | The correct way to force early cleanup; moves ownership in |
| Prelude inclusion | Both `Drop` trait and `drop()` function are in the prelude |

---

## Why This Matters

In languages like C++, forgetting to call a destructor or calling it at the wrong time leads to memory leaks or use-after-free bugs. Rust eliminates this entire class of bugs:

- You implement *what* to clean up in `drop`
- Rust guarantees *when* it happens (end of scope, or explicit `std::mem::drop`)
- No double-free possible: ownership ensures `drop` is called exactly once

This is a core part of Rust's **RAII** (Resource Acquisition Is Initialization) pattern — resources are tied to ownership and automatically released when the owner is done.

# 9.3 - To `panic!` or Not to `panic!`

## Overview

This section provides guidance on when to call `panic!` versus returning a `Result`. The core principle: returning `Result` gives the caller a choice; calling `panic!` makes the decision for them. `Result` is the better default for functions that might fail, but there are well-defined situations where `panic!` is the right call.

---

## General Rule

| Situation | Preferred Approach |
|---|---|
| Failure is possible and recoverable | Return `Result` |
| Failure is impossible or a programmer bug | `panic!` |
| Examples, prototypes, tests | `unwrap` / `expect` are fine |

---

## When `panic!` / `unwrap` / `expect` Are Appropriate

### 1. Examples, Prototype Code, and Tests

- In examples, error handling boilerplate obscures the concept being illustrated — `unwrap` acts as a placeholder.
- In prototypes, `unwrap`/`expect` leave clear markers to revisit for robustness later.
- In tests, panicking is exactly how a test signals failure — using `unwrap`/`expect` is idiomatic.

### 2. When You Know More Than the Compiler

If logic guarantees a `Result` is always `Ok` but the compiler can't verify it, use `expect` with an explanatory message:

```rust
use std::net::IpAddr;

let home: IpAddr = "127.0.0.1"
    .parse()
    .expect("Hardcoded IP address should be valid");
```

The `parse` method always returns `Result`, but the hardcoded string is provably valid. The `expect` message documents the assumption — and will prompt you to add proper error handling if the string ever comes from a dynamic source.

---

## Guidelines for Error Handling

### Panic when your code reaches a **bad state**:

A bad state is when an assumption, guarantee, contract, or invariant has been broken. Panic is appropriate if:

- The bad state is **unexpected** (not a routine occurrence like invalid user input).
- Downstream code **relies on** the bad state not existing (can't check at every step).
- There is **no good way to encode** the invalidity in the type system.

Common examples:
- A caller passes contradictory or missing values that violate a function's contract.
- External code returns an invalid state you cannot fix.
- Out-of-bounds memory access (the standard library panics here for security reasons).

> Contract violations are always caller-side bugs. There's no reasonable way for the calling code to recover — the programmer needs to fix it.

### Return `Result` when failure is **expected**:

- A parser receives malformed data.
- An HTTP request hits a rate limit.
- A file is not found (and the caller can decide what to do).

## Using the Type System for Validation

Rust's type system can eliminate many runtime checks. For example:
- Using a concrete type instead of `Option` means you always have a value — no `None` case to handle.
- Using `u32` ensures a parameter is never negative.

### Custom Validation Types

Instead of repeating range checks in every function, encode the invariant into a type:

```rust
pub struct Guess {
    value: i32,
}

impl Guess {
    pub fn new(value: i32) -> Guess {
        if value < 1 || value > 100 {
            panic!("Guess value must be between 1 and 100, got {value}.");
        }

        Guess { value }
    }

    pub fn value(&self) -> i32 {
        self.value
    }
}
```

Key design points:
- The `value` field is **private** — external code cannot set it directly.
- `Guess::new` is the only way to construct a `Guess`, so the invariant (1–100) is always enforced.
- A `value()` getter provides read access.
- Functions that accept a `Guess` can trust the value is valid without additional checks.
- The panic conditions should be documented in the public API docs.

---

## Key Takeaways

- **Return `Result` by default** from functions that might fail — it gives callers the ability to recover.
- **Use `panic!`** for unrecoverable states, programmer errors, and contract violations.
- **`unwrap`/`expect` are fine** in examples, prototypes, and tests — or when you can reason that failure is impossible.
- **Prefer `expect` over `unwrap`** with a message explaining why failure shouldn't occur.
- **Leverage the type system**: encode invariants into custom types so callers don't need runtime checks.

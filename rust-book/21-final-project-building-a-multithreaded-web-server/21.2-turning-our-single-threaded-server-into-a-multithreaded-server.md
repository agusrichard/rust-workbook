# 21.2 - Turning Our Single-Threaded Server into a Multithreaded Server

## Overview

This chapter transforms the single-threaded web server from section 21.1 into a multithreaded one using a **thread pool** pattern. The core problem is that a single-threaded server processes requests sequentially — one slow request blocks all others. The solution is a fixed-size pool of worker threads that can handle multiple requests concurrently.

---

## The Problem: Sequential Blocking

With the original server, adding a `/sleep` endpoint (that pauses for 5 seconds) demonstrates the issue: any request received while `/sleep` is running must wait, even if it could be served instantly.

**Filename: src/main.rs** — Simulating a slow request:
```rust
use std::{
    fs,
    io::{BufReader, prelude::*},
    net::{TcpListener, TcpStream},
    thread,
    time::Duration,
};

fn main() {
    let listener = TcpListener::bind("127.0.0.1:7878").unwrap();

    for stream in listener.incoming() {
        let stream = stream.unwrap();
        handle_connection(stream);
    }
}

fn handle_connection(mut stream: TcpStream) {
    let buf_reader = BufReader::new(&stream);
    let request_line = buf_reader.lines().next().unwrap().unwrap();

    let (status_line, filename) = match &request_line[..] {
        "GET / HTTP/1.1" => ("HTTP/1.1 200 OK", "hello.html"),
        "GET /sleep HTTP/1.1" => {
            thread::sleep(Duration::from_secs(5));
            ("HTTP/1.1 200 OK", "hello.html")
        }
        _ => ("HTTP/1.1 404 NOT FOUND", "404.html"),
    };

    let contents = fs::read_to_string(filename).unwrap();
    let length = contents.len();

    let response =
        format!("{status_line}\r\nContent-Length: {length}\r\n\r\n{contents}");

    stream.write_all(response.as_bytes()).unwrap();
}
```

**Explanation:**
- `listener.incoming()` is an iterator that yields a `Result<TcpStream>` for each new TCP connection. The `for` loop blocks waiting for the next one.
- `stream.unwrap()` extracts the `TcpStream` from the `Result`, panicking on OS-level errors.
- `handle_connection(stream)` is called directly on the main thread — so while the `/sleep` branch is sleeping, no other connections are accepted or processed.

---

## Naive Fix: Spawning a Thread Per Request

One approach is to spawn a new thread for every incoming connection:

**Filename: src/main.rs**
```rust
fn main() {
    let listener = TcpListener::bind("127.0.0.1:7878").unwrap();

    for stream in listener.incoming() {
        let stream = stream.unwrap();

        thread::spawn(|| {
            handle_connection(stream);
        });
    }
}
```

**Explanation:**
- `thread::spawn(|| { ... })` creates a new OS thread for each request. `stream` is *moved* into the closure, transferring ownership to the new thread.
- This solves the blocking problem — each request now runs independently — but it introduces a new one: under heavy load, unlimited thread creation exhausts memory and CPU, and a malicious client could intentionally send many requests to crash the server (DoS).

**Why this is problematic**: A **thread pool** with a fixed size is safer and more predictable.

---

## The Solution: Thread Pool

### Architecture

```
                        ┌───────────────────────────────────────┐
                        │              ThreadPool                │
  Incoming requests ──► │  sender ──► [channel queue] ──►        │
                        │                           receiver     │
                        │         ┌─────────────────────────┐   │
                        │         │        workers           │   │
                        │         │  W0, W1, W2, W3          │   │
                        │         │  each loops on recv()    │   │
                        └─────────┴─────────────────────────┴───┘
                                          │
                              Arc<Mutex<Receiver>> shared
                              among all workers
```

- **`ThreadPool`**: Holds a `Vec<Worker>` and an `mpsc::Sender<Job>`
- **`Worker`**: Wraps a thread ID and a `JoinHandle<()>`; loops waiting for jobs
- **`Job`**: Type alias for `Box<dyn FnOnce() + Send + 'static>`
- **Channel**: `mpsc::channel()` distributes jobs; receiver is shared via `Arc<Mutex<T>>`

---

## Step-by-Step Implementation

### Step 1: Define the desired interface (compiler-driven development)

Design the API you *want* first, then let compiler errors drive the implementation.

**Filename: src/main.rs**
```rust
use hello::ThreadPool;

fn main() {
    let listener = TcpListener::bind("127.0.0.1:7878").unwrap();
    let pool = ThreadPool::new(4);

    for stream in listener.incoming() {
        let stream = stream.unwrap();

        pool.execute(|| {
            handle_connection(stream);
        });
    }
}
```

**Explanation:**
- `ThreadPool::new(4)` creates a pool with 4 worker threads — a fixed upper bound on concurrency.
- `pool.execute(|| { handle_connection(stream); })` submits a closure as a job. The closure *captures* `stream` by move, because it will run on a different thread.
- This call returns immediately; the main thread never handles the connection itself.

### Step 3: Add `new()` and `execute()` with correct trait bounds

```rust
pub struct ThreadPool;

impl ThreadPool {
    pub fn new(size: usize) -> ThreadPool {
        ThreadPool
    }

    pub fn execute<F>(&self, f: F)
    where
        F: FnOnce() + Send + 'static,
    {
    }
}
```

**Explanation of the trait bounds on `F`:**

| Bound | Reason |
|---|---|
| `FnOnce()` | The closure is called exactly once, consuming any captured values (like `stream`) |
| `Send` | The closure crosses a thread boundary — Rust requires it to be safe to transfer |
| `'static` | The closure can't hold references to stack data that might be dropped before the thread runs |

These are the same bounds as `thread::spawn` — for the same reason.

- The doc comment uses the `# Panics` section — idiomatic Rust documentation convention for documenting panic conditions.

### Step 5: Store threads in a `Vec`

```rust
use std::thread;

pub struct ThreadPool {
    threads: Vec<thread::JoinHandle<()>>,
}

impl ThreadPool {
    pub fn new(size: usize) -> ThreadPool {
        assert!(size > 0);

        let mut threads = Vec::with_capacity(size);

        for _ in 0..size {
            // create some threads and store them in the vector
        }

        ThreadPool { threads }
    }
}
```

**Explanation:**
- `Vec::with_capacity(size)` pre-allocates memory for exactly `size` elements. This avoids repeated heap reallocations as workers are pushed in. It's an optimization — the `Vec` knows upfront how many items it will hold.
- `thread::JoinHandle<()>` is the handle returned by `thread::spawn`. Holding it lets you later `.join()` the thread (wait for it to finish) and detect panics.

---

### Step 6: Introduce the `Worker` struct

```rust
pub struct ThreadPool {
    workers: Vec<Worker>,
}

struct Worker {
    id: usize,
    thread: thread::JoinHandle<()>,
}

impl Worker {
    fn new(id: usize) -> Worker {
        let thread = thread::spawn(|| {});
        Worker { id, thread }
    }
}
```

**Explanation:**
- Why a separate `Worker` instead of storing `JoinHandle` directly? Because a thread that runs a closure assigned at creation is different from a thread that *waits for work*. `Worker` represents the latter — a thread that will loop, pull jobs from a queue, and execute them.
- The `id` field makes debugging easier: you can log which worker picked up which job.
- Right now the thread does nothing (`|| {}`). The next steps will give it real work.

---

### Step 7: Add a channel to `ThreadPool`

```rust
use std::{sync::mpsc, thread};

pub struct ThreadPool {
    workers: Vec<Worker>,
    sender: mpsc::Sender<Job>,
}

struct Job; // placeholder type for now
```

**Explanation:**
- `mpsc::channel()` creates a **multi-producer, single-consumer** channel. It returns `(Sender, Receiver)`.
- `ThreadPool` keeps the `Sender` — it will call `.send(job)` whenever `execute()` is called.
- `mpsc` = multi-producer because you could have multiple `Sender` clones. Here only the main thread sends, but `Sender` is `Clone` by design.
- The `Receiver` end needs to reach all workers — that's the next problem.

---

### Step 8: Share the receiver with `Arc<Mutex<T>>`

```rust
use std::{
    sync::{Arc, Mutex, mpsc},
    thread,
};

impl ThreadPool {
    pub fn new(size: usize) -> ThreadPool {
        let (sender, receiver) = mpsc::channel();

        let receiver = Arc::new(Mutex::new(receiver));

        let mut workers = Vec::with_capacity(size);

        for id in 0..size {
            workers.push(Worker::new(id, Arc::clone(&receiver)));
        }

        ThreadPool { workers, sender }
    }
}

impl Worker {
    fn new(id: usize, receiver: Arc<Mutex<mpsc::Receiver<Job>>>) -> Worker {
        let thread = thread::spawn(|| {
            receiver; // not used yet
        });
        Worker { id, thread }
    }
}
```

**Why `Arc`?**

`mpsc::Receiver` has a single owner. You can't move it into 4 workers:

```rust
workers.push(Worker::new(id, receiver)); // moves receiver into worker 0
workers.push(Worker::new(id, receiver)); // ERROR: already moved!
```

`Arc` (Atomically Reference Counted) gives each worker a *shared pointer* to the same receiver on the heap. Each `Arc::clone` increments an atomic counter; when all clones drop, the data is freed.

```
Arc::clone → ptr ─┐
Arc::clone → ptr ─┤──► [ count: 4 | Mutex<Receiver> ]
Arc::clone → ptr ─┤
Arc::clone → ptr ─┘
```

> Why not `Rc`? Because `Rc` uses non-atomic reference counting and is not `Send` — it cannot cross thread boundaries. `Arc` uses atomic operations, making it safe.

**Why `Mutex`?**

`Arc` solves ownership, but now all 4 workers share the same receiver. If two workers call `.recv()` simultaneously, that's a **data race** — undefined behavior. `Mutex` (mutual exclusion) ensures only one thread can access the inner value at a time:

```
Worker 0: lock() → acquires guard → .recv() → gets job → guard drops → lock released
Worker 1:          blocked...                                         → now acquires lock
Worker 2:          blocked...
Worker 3:          blocked...
```

> `mpsc::Receiver` is also not `Sync` — it was designed for single-threaded access. `Mutex<Receiver>` wraps it and provides the synchronization that makes it safe to share.

**`Arc<Mutex<T>>` together:**

| Wrapper | Solves |
|---|---|
| `Arc<T>` | Multiple threads can *own* the receiver |
| `Mutex<T>` | Only one thread accesses the receiver *at a time* |

### Step 9: Implement `execute()` with `Job` type alias and the worker loop

This is the **final working implementation**:

**Filename: src/lib.rs**
```rust
use std::{
    sync::{Arc, Mutex, mpsc},
    thread,
};

pub struct ThreadPool {
    workers: Vec<Worker>,
    sender: mpsc::Sender<Job>,
}

type Job = Box<dyn FnOnce() + Send + 'static>;

impl ThreadPool {
    /// Create a new ThreadPool.
    ///
    /// The size is the number of threads in the pool.
    ///
    /// # Panics
    ///
    /// The `new` function will panic if the size is zero.
    pub fn new(size: usize) -> ThreadPool {
        assert!(size > 0);

        let (sender, receiver) = mpsc::channel();

        let receiver = Arc::new(Mutex::new(receiver));

        let mut workers = Vec::with_capacity(size);

        for id in 0..size {
            workers.push(Worker::new(id, Arc::clone(&receiver)));
        }

        ThreadPool { workers, sender }
    }

    pub fn execute<F>(&self, f: F)
    where
        F: FnOnce() + Send + 'static,
    {
        let job = Box::new(f);

        self.sender.send(job).unwrap();
    }
}

struct Worker {
    id: usize,
    thread: thread::JoinHandle<()>,
}

impl Worker {
    fn new(id: usize, receiver: Arc<Mutex<mpsc::Receiver<Job>>>) -> Worker {
        let thread = thread::spawn(move || {
            loop {
                let job = receiver.lock().unwrap().recv().unwrap();

                println!("Worker {id} got a job; executing.");

                job();
            }
        });

        Worker { id, thread }
    }
}
```

**Explanation of `execute()`:**
- `Box::new(f)` wraps the closure in a heap allocation, erasing its concrete type into `Box<dyn FnOnce()>`. This is necessary because every closure has a unique compile-time type — the channel needs a single consistent type for all jobs.
- `self.sender.send(job).unwrap()` moves the boxed job into the channel queue. The main thread's work is done here.

**Explanation of the worker loop:**
- `move ||` — the closure takes ownership of the `Arc<Mutex<Receiver>>` clone.
- `receiver.lock().unwrap()` — acquires the mutex. Returns a `MutexGuard`. The second `unwrap()` handles *mutex poisoning* (another thread panicked while holding the lock).
- `.recv().unwrap()` — blocks until a job arrives. Returns `Err` only if the sender was dropped (channel closed), so `unwrap()` is fine during normal operation.
- The `MutexGuard` is dropped at the end of the `let` statement — **before** `job()` runs — so other workers can immediately acquire the lock and pull their own jobs.
- `job()` executes the closure (i.e., runs `handle_connection(stream)`) on this worker thread.

---

## Key Concept: `let` vs `while let` and Lock Scope

There is a subtle but critical difference between using `let` and `while let` in the worker loop.

### Correct: `let` binding (lock released before job runs)

```rust
loop {
    let job = receiver.lock().unwrap().recv().unwrap();
    // MutexGuard drops HERE — end of the let statement
    job(); // other workers can now acquire the lock
}
```

### Incorrect: `while let` (lock held during job execution)

```rust
while let Ok(job) = receiver.lock().unwrap().recv() {
    println!("Worker {id} got a job; executing.");
    job(); // MutexGuard is still alive — no other worker can proceed!
}
```

With `while let`, the temporary `MutexGuard` lives until the **end of the block** (`}`), meaning the lock is held for the entire duration of `job()`. This prevents all other workers from picking up new jobs while any one worker is busy — effectively making a 4-worker pool behave like a single-threaded server.

With `let job = ...`, the guard is dropped at the **end of the statement** (the `;`), releasing the lock immediately so other workers can proceed concurrently.

## The Full Journey of a Request

```
main thread                            worker thread (e.g. W2)
───────────────                        ─────────────────────────────
accept TcpStream
  └─► pool.execute(|| handle_connection(stream))
         │
         ├── Box::new(closure)         ← type-erased into Job
         └── sender.send(job)          ← pushed into channel queue
                    │
               [mpsc channel]
                    │
                    └──────────────►  receiver.lock() → acquires mutex
                                      .recv()         → pulls Job
                                      // MutexGuard dropped here
                                      job()           → handle_connection(stream)
```

---

## Important Concepts Summary

| Concept | Explanation |
|---|---|
| `Arc<T>` | Shared ownership across threads via atomic reference counting |
| `Mutex<T>` | Exclusive access — only one thread enters at a time |
| `Arc<Mutex<T>>` | The standard pattern for shared mutable state across threads |
| `mpsc::channel` | Job queue: main thread sends, workers receive |
| `Box<dyn FnOnce()>` | Type-erased heap closure — lets the channel hold any job |
| `FnOnce() + Send + 'static` | Bounds required for a closure to be sent safely to another thread |
| `Vec::with_capacity` | Pre-allocates memory, avoiding reallocations during worker creation |
| Lock scope / drop timing | `let` drops temporaries at end of statement; `while let` drops at end of block |
| Compiler-driven development | Write the desired API first, use compiler errors to guide implementation |

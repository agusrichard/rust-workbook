# 21.1 - Building a Single-Threaded Web Server

## High-Level Overview

This chapter walks through building a basic HTTP web server from scratch using only Rust's standard library. The goal is to understand how TCP and HTTP work together, and how Rust handles low-level networking primitives. The server is intentionally single-threaded, which sets up the motivation for the next chapter on multithreading.

---

## Key Concepts

### Protocols: TCP and HTTP

Web servers rely on two layered protocols:

- **TCP (Transmission Control Protocol)**: The transport layer. Handles how data is reliably transmitted between machines (connection setup, packet ordering, retransmission).
- **HTTP (HyperText Transfer Protocol)**: The application layer. Defines the structure and meaning of messages (requests and responses) sent over TCP.

Both are request-response protocols where clients initiate and servers respond. HTTP always sends its data over TCP in practice, though it is technically possible to use HTTP with other protocols.

```
┌──────────────────────────┐
│        HTTP              │  ← Application layer (what is said)
├──────────────────────────┤
│        TCP               │  ← Transport layer (how it's delivered)
└──────────────────────────┘
```

HTTP is built on top of TCP: a browser opens a TCP connection, then sends an HTTP-formatted message through it.

---

### HTTP Request Format

The formal structure of an HTTP request is:

```
Method Request-URI HTTP-Version CRLF
headers CRLF
message-body
```

A real example looks like:

```
GET / HTTP/1.1\r\n
Host: 127.0.0.1:7878\r\n
User-Agent: Mozilla/5.0 ...\r\n
Accept: text/html,...\r\n
\r\n
```

- **Request line**: `METHOD URI HTTP_VERSION` — e.g., `GET / HTTP/1.1`
- **Headers**: Key-value pairs, each ending with `\r\n`
- **Blank line**: `\r\n` signals end of headers
- **Body**: Optional — GET requests have no body

> **URI vs URL**: A URI (Uniform Resource Identifier) is almost, but not quite, the same as a URL (Uniform Resource Locator). The difference isn't important for this project.

> **CRLF**: Stands for _carriage return_ and _line feed_ — terms from the typewriter era. Written as `\r\n` in code: `\r` is carriage return, `\n` is line feed. HTTP uses CRLF as line endings in its message format.

### HTTP Response Format

```
HTTP/1.1 200 OK\r\n
Content-Length: 1234\r\n
\r\n
<html>...</html>
```

- **Status line**: `HTTP_VERSION STATUS_CODE REASON_PHRASE`
- **Headers**: e.g., `Content-Length` — required so the browser knows when the body ends
- **Blank line**: separates headers from body
- **Body**: the actual content (HTML, JSON, etc.)

> **Why `Content-Length` matters**: Without it, the browser cannot distinguish between an incomplete response and a completed one, potentially causing the connection to hang or pages to render incorrectly.

## Implementation Steps

### Step 1: Listening for TCP Connections

`TcpListener::bind("127.0.0.1:7878")` creates a listener on localhost port 7878. Port 7878 is chosen because:
- It's not a privileged port (below 1024)
- It humorously spells "rust" on a telephone keypad

The word "bind" comes from networking terminology: "connecting to a port to listen to is known as binding to a port."

`bind` returns `Result<T, E>` because binding can fail (e.g., if another program is already listening on that port, or if ports below 1024 require OS-level privileges). Here `unwrap()` is used for simplicity since this is a learning exercise.

`incoming()` returns an iterator of connection **attempts** (`Result<TcpStream>`), not guaranteed connections. Errors can occur due to OS limits on simultaneous open connections.

```rust
use std::net::TcpListener;

fn main() {
    let listener = TcpListener::bind("127.0.0.1:7878").unwrap();

    for stream in listener.incoming() {
        let stream = stream.unwrap();

        println!("Connection established!");
    }
}
```

> **Variable Shadowing**: `let stream = stream.unwrap()` uses Rust's shadowing to rebind `stream` from `Result<TcpStream>` to `TcpStream`. This is idiomatic when unwrapping — it avoids naming the two things differently (`stream_result` and `stream`) and keeps the intent clear.

> **`TcpStream` and `Drop`**: A `TcpStream` represents an open connection between the client and the server. When `stream` goes out of scope at the end of each loop iteration, it is dropped, and the connection is automatically closed via the `Drop` trait implementation. This prevents resource leaks without requiring explicit close calls.

> **Why you may see multiple connections per browser request**: Browsers often make additional requests alongside the main page request (e.g., for `favicon.ico`). Browsers may also retry closed connections (since the problem might be temporary) or preemptively open multiple connections before sending any requests, to speed up future requests.

### Step 2: Reading the HTTP Request

`BufReader` wraps the stream to add buffering by managing calls to the `std::io::Read` trait methods internally. This makes line-by-line reading efficient. HTTP headers end with a blank line (two consecutive `\r\n`), so `take_while(|line| !line.is_empty())` stops at that boundary.

```rust
use std::{
    io::{BufReader, prelude::*},
    net::{TcpListener, TcpStream},
};

fn main() {
    let listener = TcpListener::bind("127.0.0.1:7878").unwrap();

    for stream in listener.incoming() {
        let stream = stream.unwrap();

        handle_connection(stream);
    }
}

fn handle_connection(mut stream: TcpStream) {
    let buf_reader = BufReader::new(&stream);
    let http_request: Vec<_> = buf_reader
        .lines()
        .map(|result| result.unwrap())
        .take_while(|line| !line.is_empty())
        .collect();

    println!("Request: {http_request:#?}");
}
```

> **`mut stream`**: The parameter must be `mut` because reading from the stream changes its internal cursor/state, even though we pass `&stream` (an immutable reference) to `BufReader`. The `mut` is needed for the later `write_all` call on the stream itself.

> **`BufReader::new(&stream)`**: Takes an immutable borrow of the stream. `BufReader` implements `Read` for `&TcpStream` because `TcpStream` implements `Read` for shared references.

#### Iterator Chain Breakdown

```
buf_reader
    .lines()                         // Iterator<Item = Result<String>>
                                     //   splits on newline bytes
    .map(|result| result.unwrap())   // Iterator<Item = String>
                                     //   panics on I/O error
    .take_while(|line| !line.is_empty()) // Iterator<Item = String>
                                     //   stops at the blank line (end of headers)
    .collect()                       // Vec<String>
                                     //   collects all header lines
```

The browser signals the end of an HTTP request by sending two consecutive newline characters. `take_while` stops before collecting that blank line, giving us only the populated header lines.

### Step 3: Writing a Minimal HTTP Response

`write_all` sends all bytes over the stream (it may make multiple underlying `write` calls to ensure everything is transmitted). The response string must follow the HTTP format with `\r\n` line endings. `as_bytes()` converts the `&str` to `&[u8]` since `write_all` works on byte slices, not strings.

```rust
use std::{
    io::{BufReader, prelude::*},
    net::{TcpListener, TcpStream},
};

fn main() {
    let listener = TcpListener::bind("127.0.0.1:7878").unwrap();

    for stream in listener.incoming() {
        let stream = stream.unwrap();

        handle_connection(stream);
    }
}

fn handle_connection(mut stream: TcpStream) {
    let buf_reader = BufReader::new(&stream);
    let http_request: Vec<_> = buf_reader
        .lines()
        .map(|result| result.unwrap())
        .take_while(|line| !line.is_empty())
        .collect();

    let response = "HTTP/1.1 200 OK\r\n\r\n";

    stream.write_all(response.as_bytes()).unwrap();
}
```

### Step 4: Serving an HTML File

Read the HTML file with `fs::read_to_string`, compute its byte length for the `Content-Length` header, and include it in the response body.

**hello.html** (place in project root):
```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <title>Hello!</title>
  </head>
  <body>
    <h1>Hello!</h1>
    <p>Hi from Rust</p>
  </body>
</html>
```

```rust
use std::{
    fs,
    io::{BufReader, prelude::*},
    net::{TcpListener, TcpStream},
};

fn main() {
    let listener = TcpListener::bind("127.0.0.1:7878").unwrap();

    for stream in listener.incoming() {
        let stream = stream.unwrap();

        handle_connection(stream);
    }
}

fn handle_connection(mut stream: TcpStream) {
    let buf_reader = BufReader::new(&stream);
    let http_request: Vec<_> = buf_reader
        .lines()
        .map(|result| result.unwrap())
        .take_while(|line| !line.is_empty())
        .collect();

    let status_line = "HTTP/1.1 200 OK";
    let contents = fs::read_to_string("hello.html").unwrap();
    let length = contents.len();

    let response =
        format!("{status_line}\r\nContent-Length: {length}\r\n\r\n{contents}");

    stream.write_all(response.as_bytes()).unwrap();
}
```

### Step 5: Validating the Request Path

Instead of collecting all headers, we only need the first line to determine what to serve. `.next()` fetches just the first item from the iterator, avoiding reading the whole request into a vector.

```rust
use std::{
    fs,
    io::{BufReader, prelude::*},
    net::{TcpListener, TcpStream},
};

fn main() {
    let listener = TcpListener::bind("127.0.0.1:7878").unwrap();

    for stream in listener.incoming() {
        let stream = stream.unwrap();

        handle_connection(stream);
    }
}

fn handle_connection(mut stream: TcpStream) {
    let buf_reader = BufReader::new(&stream);
    let request_line = buf_reader.lines().next().unwrap().unwrap();

    if request_line == "GET / HTTP/1.1" {
        let status_line = "HTTP/1.1 200 OK";
        let contents = fs::read_to_string("hello.html").unwrap();
        let length = contents.len();

        let response = format!(
            "{status_line}\r\nContent-Length: {length}\r\n\r\n{contents}"
        );

        stream.write_all(response.as_bytes()).unwrap();
    } else {
        // some other request
    }
}
```

> **Why double `unwrap()`?** `buf_reader.lines().next()` returns `Option<Result<String>>`:
> - `.next()` → `Option<Result<String>>`
> - `.unwrap()` → `Result<String>` — handles the `Option`; panics if the iterator had no items
> - `.unwrap()` → `String` — handles the `Result`; panics on I/O error

> **Comparison `request_line == "GET / HTTP/1.1"`**: compares the owned `String` with a `&str` literal. Rust's `PartialEq` implementation for `String` handles this automatically.

### Step 6: Returning a 404 Response

Add a 404 HTML file and serve it when the path doesn't match `/`.

**404.html** (place in project root):
```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <title>Hello!</title>
  </head>
  <body>
    <h1>Oops!</h1>
    <p>Sorry, I don't know what you're asking for.</p>
  </body>
</html>
```

```rust
use std::{
    fs,

    net::{TcpListener, TcpStream},

fn main() {
    let listener = TcpListener::bind("127.0.0.1:7878").unwrap();

fn handle_connection(mut stream: TcpStream) {
    let buf_reader = BufReader::new(&stream);

    if request_line == "GET / HTTP/1.1" {
        let status_line = "HTTP/1.1 200 OK";
        let contents = fs::read_to_string("hello.html").unwrap();
        let length = contents.len();

        let response = format!(

        stream.write_all(response.as_bytes()).unwrap();
    } else {
        let status_line = "HTTP/1.1 404 NOT FOUND";
        let contents = fs::read_to_string("404.html").unwrap();
        let length = contents.len();

        let response = format!(
            "{status_line}\r\nContent-Length: {length}\r\n\r\n{contents}"
        );

        stream.write_all(response.as_bytes()).unwrap();
    }
}
```

### Step 7: Refactoring to Eliminate Duplication

Both branches share identical response-building logic — only the status line and filename differ. Extracting just those differences into variables leaves a single path for reading files and writing the response. This makes it easier to see what differs between the two cases, and means there's only one place to update if the response-writing logic needs to change.

This is idiomatic Rust: `if` is an **expression** that returns a value. Here it returns a `(&str, &str)` tuple, which is immediately destructured with `let (status_line, filename) = ...`.

```rust
use std::{
    fs,
    io::{BufReader, prelude::*},
    net::{TcpListener, TcpStream},
};

fn main() {
    let listener = TcpListener::bind("127.0.0.1:7878").unwrap();

    for stream in listener.incoming() {
        let stream = stream.unwrap();

        handle_connection(stream);
    }
}

fn handle_connection(mut stream: TcpStream) {
    let buf_reader = BufReader::new(&stream);
    let request_line = buf_reader.lines().next().unwrap().unwrap();

    let (status_line, filename) = if request_line == "GET / HTTP/1.1" {
        ("HTTP/1.1 200 OK", "hello.html")
    } else {
        ("HTTP/1.1 404 NOT FOUND", "404.html")
    };

    let contents = fs::read_to_string(filename).unwrap();
    let length = contents.len();

    let response =
        format!("{status_line}\r\nContent-Length: {length}\r\n\r\n{contents}");

    stream.write_all(response.as_bytes()).unwrap();
}
```

## Request Flow Diagram

```
Browser                        Rust Server
   |                               |
   |--- TCP connect --------------->|
   |                               |
   |--- HTTP GET / HTTP/1.1 ------->|
   |                               | ← BufReader reads lines
   |                               | ← parse request_line
   |                               | ← if "GET / HTTP/1.1"
   |                               |     read hello.html
   |                               |   else
   |                               |     read 404.html
   |                               | ← format response string
   |<-- HTTP/1.1 200 OK + body ----|
   |    (or 404 NOT FOUND)         |
```

## Important Concepts Summary

| Concept | Details |
|---|---|
| `TcpListener::bind` | Opens a socket on an address:port; called "bind" because attaching to a port is called "binding to a port" |
| `bind` returns `Result` | Fails if port is already in use or requires elevated privileges |
| `listener.incoming()` | Iterator of **connection attempts** (`Result<TcpStream>`), not guaranteed connections |
| `TcpStream` | Represents an open connection; automatically closed via `Drop` when it goes out of scope |
| Variable shadowing on `stream` | `let stream = stream.unwrap()` rebinds from `Result<TcpStream>` to `TcpStream` — idiomatic unwrapping |
| Multiple browser connections | Browsers request `favicon.ico`, retry closed connections, and preemptively open idle connections |
| `BufReader` | Wraps a stream to add buffering via the `std::io::Read` trait; enables `lines()` |
| `lines()` | Returns `Iterator<Item = Result<String>>`; splits on newline bytes |
| `.take_while(\|l\| !l.is_empty())` | Stops at the blank line that signals end of HTTP headers (the browser sends two consecutive `\r\n`) |
| `next().unwrap().unwrap()` | First `unwrap`: `Option` from `next()`; second `unwrap`: `Result` from the `lines()` iterator |
| `write_all` | Writes all bytes (may make multiple OS-level `write` calls); takes `&[u8]` |
| `as_bytes()` | Converts `&str`/`String` to `&[u8]` for writing to the stream |
| `fs::read_to_string` | Reads an entire file into an owned `String` |
| `Content-Length` header | Tells the browser the exact size of the body so it knows when the response ends |
| CRLF (`\r\n`) | HTTP line ending; historically from typewriter carriage return + line feed |
| URI vs URL | Nearly identical for this purpose; URL is a type of URI |
| `if` as expression | Returns a value; used here to destructure a `(&str, &str)` tuple for status line and filename |
| `String == &str` comparison | Works via `PartialEq` implementation; no explicit conversion needed |

## Ownership and Borrowing Notes

- `BufReader::new(&stream)` — borrows `stream` immutably; `TcpStream` implements `Read` for `&TcpStream`
- `mut stream: TcpStream` — ownership is moved into `handle_connection`; `mut` is needed for `write_all` later
- `fs::read_to_string(filename)` — returns an owned `String`; `len()` then borrows it immutably
- `format!` — creates a new owned `String` from borrowed parts
- The refactored `(status_line, filename)` tuple holds `&str` values (string literals with `'static` lifetime), so they can be used safely after the `if` expression

---

## Limitation: Single-Threaded

This server handles one connection at a time. If a slow request is being processed, all other incoming connections must wait. The next chapter addresses this by introducing a thread pool to handle requests concurrently.

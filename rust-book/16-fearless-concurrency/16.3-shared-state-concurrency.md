# 16.3 - Shared-State Concurrency

## High-Level Overview

Shared-state concurrency is an alternative to message-passing: instead of communicating data between threads, multiple threads access the same piece of data simultaneously. Rust's type system and ownership model make this safer than in most languages by enforcing correct locking discipline at compile time. The primary tools are `Mutex<T>` for mutual exclusion and `Arc<T>` for thread-safe reference counting.

---

## Key Concepts

### 1. Mutexes (Mutual Exclusion)

A **mutex** allows only one thread to access some data at any given time. A thread must *acquire the lock* before accessing the data, and *release the lock* when done so other threads can proceed.

Two rules to keep in mind:
1. You must acquire the lock before using the data.
2. When done, you must unlock the data so other threads can acquire the lock.

**Analogy**: A conference panel with a single microphone — speakers must request the mic, use it, then pass it on.

---

### 2. The `Mutex<T>` API

```rust
use std::sync::Mutex;

fn main() {
    let m = Mutex::new(5);

    {
        let mut num = m.lock().unwrap();
        *num = 6;
    }

    println!("m = {m:?}");
}
```

**How it works:**
- `Mutex::new(5)` wraps the value `5` inside a `Mutex`.
- `m.lock()` blocks the current thread until the lock is acquired. It returns a `LockResult<MutexGuard<T>>`.
- `.unwrap()` panics if another thread panicked while holding the lock (the mutex is then "poisoned").
- `MutexGuard<T>` implements `Deref` to access the inner value and `Drop` to automatically release the lock when it goes out of scope — no manual unlock needed.

This prevents the common bug of forgetting to unlock.

---

### 3. Sharing `Mutex<T>` Across Multiple Threads

#### Why `Rc<T>` Fails

A naive attempt to share a `Mutex<T>` using `Rc<T>`:

```rust
use std::rc::Rc;
use std::sync::Mutex;
use std::thread;

fn main() {
    let counter = Rc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        let counter = Rc::clone(&counter);
        let handle = thread::spawn(move || {
            let mut num = counter.lock().unwrap();
            *num += 1;
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("Result: {}", *counter.lock().unwrap());
}
```

**Compiler error:**
```
`Rc<Mutex<i32>>` cannot be sent between threads safely
the trait `Send` is not implemented for `Rc<Mutex<i32>>`
```

`Rc<T>` is not thread-safe because its reference count is not updated atomically — two threads modifying it simultaneously could corrupt the count.

---

#### Solution: `Arc<T>` (Atomically Reference Counted)

`Arc<T>` works like `Rc<T>` but uses **atomic operations** for reference count updates, making it safe to share across threads. It implements the `Send` and `Sync` traits.

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        let counter = Arc::clone(&counter);
        let handle = thread::spawn(move || {
            let mut num = counter.lock().unwrap();
            *num += 1;
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("Result: {}", *counter.lock().unwrap());
}
```

**Output:**
```
Result: 10
```

**How it works:**
- `Arc::new(Mutex::new(0))` wraps the counter in both a `Mutex` (for exclusive access) and an `Arc` (for shared ownership across threads).
- `Arc::clone(&counter)` increments the atomic reference count and gives each thread its own pointer to the same data.
- Each thread acquires the lock, increments the counter by 1, then releases the lock automatically when `num` goes out of scope.
- `handle.join().unwrap()` waits for each thread to finish before printing the result.

---

## Important Distinctions

### `Mutex<T>` and Interior Mutability

`Mutex<T>` provides **interior mutability** — it allows mutation of data even through a shared (immutable) reference. This is similar to `RefCell<T>`, but:

| Feature | `RefCell<T>` | `Mutex<T>` |
|---|---|---|
| Thread-safe | No | Yes |
| Borrow checked | At runtime | At runtime (via lock) |
| Used with | `Rc<T>` | `Arc<T>` |

Just as `Rc<T>` + `RefCell<T>` gives shared ownership with interior mutability in single-threaded code, `Arc<T>` + `Mutex<T>` gives the same in multi-threaded code.

---

### Deadlock Risk

Rust's compiler **cannot** prevent deadlocks. A deadlock occurs when two threads each hold a lock the other needs:

- Thread A holds lock 1, waiting for lock 2.
- Thread B holds lock 2, waiting for lock 1.

Both threads block forever. This is a logic-level bug that must be avoided through careful design (e.g., always acquire locks in the same order).

---

### Performance Trade-off

Atomic operations (used by `Arc<T>`) are more expensive than non-atomic operations (used by `Rc<T>`). Use `Arc<T>` only when you actually need cross-thread sharing; prefer `Rc<T>` for single-threaded scenarios.

---

## Summary of Types

| Type | Purpose | Thread-safe |
|---|---|---|
| `Mutex<T>` | Mutual exclusion lock around data | Yes |
| `Arc<T>` | Atomically reference-counted shared pointer | Yes |
| `Rc<T>` | Reference-counted shared pointer (single-threaded) | No |
| `RefCell<T>` | Interior mutability (single-threaded) | No |
| `MutexGuard<T>` | Smart pointer returned by `lock()`, auto-unlocks on drop | — |

---

## Conclusions

- Use `Mutex<T>` to protect shared data from concurrent modification.
- Use `Arc<T>` instead of `Rc<T>` when sharing ownership across threads.
- Combining `Arc<Mutex<T>>` is the idiomatic pattern for shared mutable state in multi-threaded Rust.
- Rust's type system prevents data races at compile time, but deadlocks remain a runtime concern that requires careful design.

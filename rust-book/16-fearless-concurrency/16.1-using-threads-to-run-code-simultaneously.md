# Using Threads to Run Code Simultaneously

## Overview

This section explores how to execute independent code concurrently using **threads** in Rust. It covers creating threads, waiting for them to finish, and safely sharing data between them — all while leveraging Rust's ownership system to eliminate common threading bugs at compile time.

---

## Key Concepts

### What Is a Thread?

A thread is an independent unit of execution within a program. Multiple threads can run concurrently, enabling programs to do more than one thing at a time (e.g., handle UI events while computing in the background).

### Rust's Threading Model: 1:1

Rust's standard library uses a **1:1 threading model**: each Rust-level thread maps directly to one OS thread. This trades some flexibility (vs. green threads) for predictable performance and a thin runtime.

### Challenges of Multithreading

1. **Race conditions** — two threads access data in an unpredictable order
2. **Deadlocks** — two threads wait on each other indefinitely
3. **Hard-to-reproduce bugs** — timing-dependent bugs that only appear occasionally

Rust catches many of these at **compile time** through its ownership and type systems.

---

## Creating a Thread with `thread::spawn`

`thread::spawn` takes a closure and runs it in a new OS thread. When the **main thread ends**, all spawned threads are killed immediately, even if they haven't finished.

```rust
use std::thread;
use std::time::Duration;

fn main() {
    thread::spawn(|| {
        for i in 1..10 {
            println!("hi number {i} from the spawned thread!");
            thread::sleep(Duration::from_millis(1));
        }
    });

    for i in 1..5 {
        println!("hi number {i} from the main thread!");
        thread::sleep(Duration::from_millis(1));
    }
}
```

The spawned thread may not finish all 9 iterations because the main thread ends after 5 iterations and takes the spawned thread down with it.

## Waiting for Threads with `join`

`thread::spawn` returns a `JoinHandle<T>`. Calling `.join()` on it **blocks** the current thread until the spawned thread finishes.

```rust
use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..10 {
            println!("hi number {i} from the spawned thread!");
            thread::sleep(Duration::from_millis(1));
        }
    });

    for i in 1..5 {
        println!("hi number {i} from the main thread!");
        thread::sleep(Duration::from_millis(1));
    }

    handle.join().unwrap(); // wait here until spawned thread finishes
}
```

Now the spawned thread is guaranteed to complete all 9 iterations before the program exits.

### Placement of `join` Matters

Moving `handle.join()` **before** the main thread's loop causes the main thread to wait for the spawned thread to finish *first*, making them run sequentially rather than concurrently:

```rust
use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..10 {
            println!("hi number {i} from the spawned thread!");
            thread::sleep(Duration::from_millis(1));
        }
    });

    handle.join().unwrap(); // blocks here until spawned thread finishes

    for i in 1..5 {
        println!("hi number {i} from the main thread!");
        thread::sleep(Duration::from_millis(1));
    }
}
```

## Using `move` Closures with Threads

### The Problem: Borrowing Across Thread Boundaries

If a closure passed to `thread::spawn` tries to **borrow** data from the enclosing scope, the compiler rejects it:

```rust
use std::thread;

fn main() {
    let v = vec![1, 2, 3];

    let handle = thread::spawn(|| {
        println!("Here's a vector: {v:?}"); // borrows v
    });

    handle.join().unwrap();
}
```

**Compiler error:** `closure may outlive the current function, but it borrows 'v', which is owned by the current function`

The compiler can't guarantee `v` will live long enough — the main thread could drop `v` before the spawned thread uses it.

### Why This Is a Real Risk

```rust
use std::thread;

fn main() {
    let v = vec![1, 2, 3];

    let handle = thread::spawn(|| {
        println!("Here's a vector: {v:?}");
    });

    drop(v); // drops v while spawned thread might still need it!

    handle.join().unwrap();
}
```

If borrowing were allowed, this code could cause the spawned thread to reference **freed memory** — a use-after-free bug.

### The Solution: `move` Closures

The `move` keyword forces the closure to **take ownership** of the captured variables, rather than borrowing them:

```rust
use std::thread;

fn main() {
    let v = vec![1, 2, 3];

    let handle = thread::spawn(move || {
        println!("Here's a vector: {v:?}"); // v is moved into the closure
    });

    handle.join().unwrap();
}
```

Now `v` is owned by the closure (and thus by the spawned thread). The main thread can no longer use or drop `v` after the `move`, making the program safe.

---

## Summary

| Concept | Key Point |
|---------|-----------|
| `thread::spawn` | Creates a new OS thread running a closure |
| `JoinHandle::join` | Blocks until the thread finishes; placement determines concurrency |
| Borrowing in threads | Rejected by the compiler — lifetime cannot be guaranteed |
| `move` closures | Transfer ownership into the thread, enabling safe data access |

Rust's ownership model transforms what would be runtime threading bugs in other languages into **compile-time errors**, giving you confidence that your concurrent code is safe before it ever runs.

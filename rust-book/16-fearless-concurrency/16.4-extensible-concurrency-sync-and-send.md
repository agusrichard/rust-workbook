# 16.4 - Extensible Concurrency with `Send` and `Sync`

## High-Level Overview

Most of Rust's concurrency features are part of the standard library, not the language itself. But two concurrency concepts *are* baked into the language: the `Send` and `Sync` marker traits. These traits are what allow Rust's type system to enforce thread safety at compile time. Understanding them explains *why* types like `Arc<T>` work across threads and types like `Rc<T>` do not — and how you can extend thread-safety guarantees to your own types.

---

## Key Concept 1: The `Send` Trait

```
std::marker::Send
```

A type that implements `Send` can have its **ownership transferred to another thread**.

- Almost all Rust types implement `Send`.
- The main exception is `Rc<T>` — cloning it and sending the clone to another thread would let two threads update the reference count simultaneously without synchronization, causing a data race.
- Raw pointers also do not implement `Send` (covered in Chapter 20).

**Composability rule**: Any type composed entirely of `Send` types is automatically `Send`. This means most user-defined structs are `Send` as long as all their fields are.

```
Thread 1                        Thread 2
┌─────────────────────┐        ┌─────────────────────┐
│  owns: T (Send)     │ ──────▶│  receives: T        │
│                     │ move   │                     │
└─────────────────────┘        └─────────────────────┘
✅ Safe — ownership fully transferred, no shared state
```

---

## Key Concept 2: The `Sync` Trait

```
std::marker::Sync
```

A type that implements `Sync` can be **referenced from multiple threads simultaneously**.

Formally: **`T` is `Sync` if and only if `&T` is `Send`** — meaning a shared reference to `T` can safely be sent to another thread.

- Primitive types are `Sync`.
- `Mutex<T>` is `Sync` (that's the whole point — it coordinates shared access safely).
- `RefCell<T>` is **not** `Sync` because its runtime borrow checking is not thread-safe.
- `Rc<T>` is **not** `Sync` for the same reason it is not `Send`.

```
Thread 1                        Thread 2
┌─────────────────────┐        ┌─────────────────────┐
│  holds: &T (Sync)   │        │  holds: &T (Sync)   │
│                     │        │                     │
└─────────────────────┘        └─────────────────────┘
✅ Safe — read-only shared references, no mutation conflict
```

---

## The Relationship Between `Send` and `Sync`

```
         ┌───────────────────────────────────────┐
         │           Rust Type System             │
         │                                       │
         │  T is Sync  ←→  &T is Send            │
         │                                       │
         │  T is Send  = ownership can move      │
         │               across thread boundary  │
         └───────────────────────────────────────┘
```

These two traits together form Rust's compile-time thread-safety guarantee. If a type cannot safely be sent to or shared with another thread, the compiler refuses to let you do so.

---

## Type Reference Table

| Type | `Send` | `Sync` | Reason |
|---|---|---|---|
| `i32`, `f64`, etc. | ✅ | ✅ | Primitive, no shared state |
| `String` | ✅ | ✅ | Owned, no shared state |
| `Rc<T>` | ❌ | ❌ | Non-atomic ref count — race condition risk |
| `Arc<T>` | ✅ (if T: Send+Sync) | ✅ (if T: Send+Sync) | Atomic ref count, safe for threads |
| `Mutex<T>` | ✅ (if T: Send) | ✅ (if T: Send) | Lock guarantees exclusive access |
| `MutexGuard<'a, T>` | ❌ | ✅ (if T: Sync) | Must be unlocked on the same thread that locked |
| `RefCell<T>` | ✅ (if T: Send) | ❌ | Runtime borrow check is not atomic |
| `Cell<T>` | ✅ (if T: Send) | ❌ | Interior mutability without synchronization |
| Raw pointers `*mut T` | ❌ | ❌ | No safety guarantees |

## Why `Rc<T>` Is Neither `Send` Nor `Sync`

```rust
// This would NOT compile:
use std::rc::Rc;
use std::thread;

let rc = Rc::new(5);
let rc_clone = Rc::clone(&rc);

thread::spawn(move || {
    // ERROR: `Rc<i32>` cannot be sent between threads safely
    println!("{rc_clone}");
});
```

The issue: both `rc` and `rc_clone` point to the same reference count. If two threads clone or drop simultaneously, the count can be corrupted. `Arc<T>` solves this by using atomic CPU instructions for count updates.

## Manually Implementing `Send` and `Sync`

Because `Send` and `Sync` are **marker traits** (they have no methods), implementing them manually is done with empty `impl` blocks. However, this requires `unsafe`:

```rust
// Example of what manual implementation looks like (use with extreme care)
unsafe impl Send for MyType {}
unsafe impl Sync for MyType {}
```

The `unsafe` keyword is required because **the compiler cannot verify the safety guarantees** — you are asserting them yourself. If you get it wrong, you can introduce data races that Rust would normally prevent at compile time.

This is an advanced topic covered further in Chapter 20 (Unsafe Rust) and the [Rustonomicon](https://doc.rust-lang.org/nomicon/).

**Rule of thumb**: If your type is composed entirely of `Send` and `Sync` types, you never need to implement these traits manually — the compiler derives them automatically.

---

## The Bigger Picture: Fearless Concurrency

Rust's concurrency model is built on a simple guarantee: **if it compiles, it won't data-race**. This is possible because:

1. Ownership rules prevent two threads from holding mutable access simultaneously without synchronization.
2. `Send` prevents moving non-thread-safe types across thread boundaries.
3. `Sync` prevents sharing references to non-thread-safe types across threads.
4. Standard library types like `Mutex<T>` and `Arc<T>` are built on these guarantees.

```
 Source of unsafety      Rust's defense
 ─────────────────       ─────────────────────────────────
 Data race               Ownership + Send/Sync traits
 Use-after-free          Ownership + lifetimes
 Dangling reference      Borrow checker + lifetimes
 Deadlock                ⚠️  NOT prevented — design carefully
```

The chapter title "Fearless Concurrency" refers to this property: you can write concurrent code and lean on the compiler to catch the hard bugs, leaving you to focus on logic-level issues like deadlocks.

---

## Conclusions

- `Send` and `Sync` are the **language-level foundation** of Rust's thread safety — everything else (channels, mutexes, atomic types) is built on top of them.
- You rarely need to think about these traits directly; the compiler enforces them automatically.
- Manually implementing `Send`/`Sync` requires `unsafe` and signals that you are taking on responsibility for correctness that the compiler cannot verify.
- The combination of ownership, `Send`, `Sync`, and the borrow checker makes Rust's concurrency model uniquely safe without a runtime garbage collector or special threading primitives baked into the language.

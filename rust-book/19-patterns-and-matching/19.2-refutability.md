# 19.2 - Refutability: Whether a Pattern Might Fail to Match

## Overview

Patterns in Rust are classified into two categories based on whether they can ever fail to match a value. Understanding this distinction is essential because different language constructs have strict rules about which kind of pattern they accept.

---

## The Two Kinds of Patterns

| Kind | Definition | Example |
|---|---|---|
| **Irrefutable** | Always matches for any possible value | `let x = 5` — `x` accepts anything |
| **Refutable** | May fail to match for some values | `Some(x)` — fails when value is `None` |

---

## Where Each Pattern Kind Is Allowed

```
┌─────────────────────────────────┬─────────────┬────────────┐
│ Construct                       │ Irrefutable │ Refutable  │
├─────────────────────────────────┼─────────────┼────────────┤
│ let PATTERN = expr              │     ✅      │    ❌ error │
│ for PATTERN in iter             │     ✅      │    ❌ error │
│ fn foo(PATTERN: Type)           │     ✅      │    ❌ error │
│ let PATTERN = expr else { ... } │  ⚠️ warning │    ✅      │
│ if let PATTERN = expr           │  ⚠️ warning │    ✅      │
│ while let PATTERN = expr        │  ⚠️ warning │    ✅      │
│ match arms (non-final)          │     ✅      │    ✅      │
│ match arms (final/catch-all)    │     ✅      │  ❌ error  │
└─────────────────────────────────┴─────────────┴────────────┘
```

**Why the restriction?**  
`let`, `for`, and function parameters cannot do anything meaningful when a value doesn't match — there is no else branch to fall back to. So the compiler requires patterns that are guaranteed to succeed.

---

## Case 1: Refutable Pattern in `let` — Compiler Error

Attempting to use a refutable pattern (`Some(x)`) in a plain `let` binding fails to compile because `let` has no way to handle the `None` case.

```rust
fn main() {
    let some_option_value: Option<i32> = None;
    let Some(x) = some_option_value; // ERROR
}
```

**Compiler output:**
```
error[E0005]: refutable pattern in local binding
 --> src/main.rs:3:9
  |
3 |     let Some(x) = some_option_value;
  |         ^^^^^^^ pattern `None` not covered
  |
  = note: `let` bindings require an "irrefutable pattern"
```

**Fix — use `let...else`** to provide a branch for when the pattern fails:

```rust
fn main() {
    let some_option_value: Option<i32> = None;
    let Some(x) = some_option_value else {
        return;
    };
}
```

The `else` block handles the non-matching case (it must diverge — `return`, `panic!`, `break`, etc.), and `x` is then available after the statement.

---

## Case 2: Irrefutable Pattern in `let...else` — Compiler Warning

The opposite problem: using an irrefutable pattern with `let...else` makes the `else` branch unreachable, which the compiler warns about.

```rust
fn main() {
    let x = 5 else { // WARNING
        return;
    };
}
```

**Compiler output:**
```
warning: irrefutable `let...else` pattern
 --> src/main.rs:2:5
  |
2 |     let x = 5 else {
  |     ^^^^^^^^^
  |
  = note: this pattern will always match, so the `else` clause is useless
```

Just use a plain `let x = 5;` here — the `else` branch adds nothing.

---

## `match` Arms and Refutability

- **Non-final arms** can be either refutable or irrefutable.
- **The final arm** should be irrefutable (a catch-all like `_` or a variable) to ensure exhaustiveness.
- If a `match` arm uses a pattern that can never fail, the compiler warns that subsequent arms are unreachable.

---

## Summary

The refutability rules boil down to a simple principle:

> Use refutable patterns where the code has a place to go when the match fails (`if let`, `while let`, `let...else`). Use irrefutable patterns where there is no such escape hatch (`let`, `for`, function params).

When the compiler raises a refutability error, the fix is almost always to switch to `if let` or `let...else` so that the non-matching case is explicitly handled.

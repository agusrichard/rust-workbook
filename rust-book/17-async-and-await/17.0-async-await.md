# 17.0 - Fundamentals of Asynchronous Programming: Async, Await, Futures, and Streams

## High-Level Overview

Chapter 17 introduces **asynchronous programming** in Rust as a powerful alternative to threading for handling concurrent operations. Rather than blocking a thread while waiting for slow operations (like network I/O), async code can *pause* at well-defined points and allow other work to proceed — without the overhead of spawning dedicated threads.

The chapter covers Rust's `async`/`await` syntax, the `Future` and `Stream` traits, and how a **runtime** drives async code to completion.

---

## Key Concepts

### 1. Synchronous vs. Asynchronous Execution

In **synchronous** code, each operation blocks until it completes before the next one starts. This is simple but wasteful when a task is just *waiting* (e.g., for a file to load or a server to respond).

In **asynchronous** code, operations can be suspended at specific *await points*, freeing the thread to do other work. The runtime resumes the task when it is ready to make progress.

> Async is "an abstraction that lets us express our code in terms of potential pausing points and eventual results."

---

### 2. CPU-Bound vs. I/O-Bound Operations

| Type        | Limited by        | Example               |
|-------------|-------------------|-----------------------|
| CPU-bound   | Processor speed   | Exporting a video     |
| I/O-bound   | Input/output speed| Downloading a file    |

- **CPU-bound** tasks benefit from **parallelism** (more cores doing more work simultaneously).
- **I/O-bound** tasks benefit from **concurrency** (one thread switching between many waiting tasks).

Async is especially effective for **I/O-bound** work.

---

### 3. Concurrency vs. Parallelism

These are related but distinct concepts:

```
Concurrency:
  One worker switches between multiple tasks before any single one finishes.
  [ Task A --> pause --> Task B --> pause --> Task A --> ... ]

Parallelism:
  Multiple workers each handle a separate task at the same time.
  [ Worker 1: Task A ]
  [ Worker 2: Task B ]
  [ Worker 3: Task C ]
```

- **Concurrency** = structure (interleaving tasks on one or more threads)
- **Parallelism** = execution (literally simultaneous computation)

Concurrency *may* use parallelism under the hood, depending on the hardware and the async runtime. In practice, real programs are often a mix: some parts serial, some parallel, some concurrent.

---

### 4. The Problem with Blocking APIs

Without async, handling multiple I/O operations typically requires spawning one thread per operation. This has drawbacks:

- Threads are relatively expensive (memory, OS scheduling overhead).
- Managing many threads introduces complexity.
- Blocking a thread wastes its capacity while it just waits.

Async solves this by defining tasks declaratively and letting the **runtime** schedule them efficiently — choosing the best order and manner to run them.

---

### 5. What Async Gives You

- Express code with `async fn` and `await` that *looks* sequential but is non-blocking.
- Define *what* to do and *where* it can pause; let the runtime handle *when* to resume.
- Compose many concurrent operations without spawning many threads.

## Conceptual Diagram

```
Traditional blocking model:
  Thread 1: [===Task A (waiting)=========] [===Task B===]

Async / concurrent model (single thread):
  Thread 1: [Task A start] [.pause.] [Task B start] [Task A resume] [Task B resume...]
             ^--- await point here lets other work run while Task A waits
```

## Summary

This introductory section sets the stage for Chapter 17 by motivating *why* async programming exists and *what problem* it solves. The core insight is:

> For I/O-bound work, we don't need more CPU power — we need smarter *waiting*. Async lets a single thread handle many tasks by yielding control at await points rather than blocking.

The rest of the chapter builds on this foundation with Rust's concrete tools: `async`/`await` syntax, `Future`, `Stream`, and runtime integration.

# 17.5 - A Closer Look at the Traits for Async

## Overview

This chapter dives into the underlying traits that power async Rust: `Future`, `Pin`, `Unpin`, and `Stream`. Understanding these gives you a clearer mental model of what the compiler and runtime are doing under the hood when you write `async`/`await` code.

---

## 1. The `Future` Trait

Every `async` function or block produces a type that implements the `Future` trait. Its definition:

```rust
use std::pin::Pin;
use std::task::{Context, Poll};

pub trait Future {
    type Output;

    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
```

- `Output` — the associated type, analogous to `Iterator::Item`. It's the value the future resolves to.
- `poll` — the method the async runtime calls repeatedly to drive the future toward completion.

### The `Poll` Enum

```rust
pub enum Poll<T> {
    Ready(T),
    Pending,
}
```

- `Ready(T)` — the future has finished and produced a value.
- `Pending` — the future is not done yet; the caller should poll again later.

### How `.await` Works Under the Hood

When you write `some_future.await`, Rust compiles it into a polling loop managed by the async runtime:

```rust
let mut page_title_fut = page_title(url);
loop {
    match page_title_fut.poll() {
        Ready(value) => match page_title {
            Some(title) => println!("The title for {url} was {title}"),
            None => println!("{url} had no title"),
        }
        Pending => {
            // yield control, come back later
        }
    }
}
```

The runtime handles yielding between futures (enabling concurrency) rather than busy-looping.

## 2. The `Pin` Type and the `Unpin` Trait

### Why Pinning Exists

Futures created from `async` blocks are state machines that can contain **self-referential data** — internal fields that hold pointers to other fields in the same struct. If such a future is moved in memory, those internal pointers become dangling/invalid.

```
Before move:               After move (BROKEN):
┌──────────────────┐       ┌──────────────────┐
│  field_a  [val]  │       │  field_a  [val]  │
│  field_b  ──────►│──┐    │  field_b  ──────►│ ─ ─ ─ ─ ─ ► INVALID
└──────────────────┘  │    └──────────────────┘
                      └──► old memory address
```

### `Pin<P>`

`Pin` is a wrapper around pointer types (like `&mut T`, `Box<T>`) that **guarantees the pointed-to value will not move in memory**. Once a value is pinned, you cannot get a `&mut T` from it without going through `unsafe`, preventing accidental moves.

```rust
use std::pin::Pin;
```

### `Unpin` Trait

`Unpin` is a **marker trait** that tells the compiler: "this type is safe to move even if it's behind a `Pin` pointer."

- Most types (`String`, `Vec`, primitives, etc.) automatically implement `Unpin` — the compiler derives it.
- Types that are **not** safe to move (e.g., self-referential futures) implement `!Unpin`.

Key rule: `Pin`/`Unpin` only matter when you're using a **pinned pointer** to a type. If you have a regular `&mut T`, pinning is irrelevant.

### Practical Problem: Heterogeneous Futures in a Vec

When you try to collect futures of different types into a `Vec` using trait objects, this fails to compile:

```rust
// ERROR: dyn Future<Output = ()> does not implement Unpin
let futures: Vec<Box<dyn Future<Output = ()>>> =
    vec![Box::new(tx1_fut), Box::new(rx_fut), Box::new(tx_fut)];

trpl::join_all(futures).await;
```

**Why?** `join_all` needs to poll futures, which requires `Pin`. Boxed trait objects don't automatically provide pinning guarantees.

### Fix: Use `pin!` Macro and `Pin<&mut dyn Future>`

```rust
use std::pin::{Pin, pin};
use std::time::Duration;

fn main() {
    trpl::block_on(async {
        let (tx, mut rx) = trpl::channel();

        let tx1 = tx.clone();
        let tx1_fut = pin!(async move {
            let vals = vec![
                String::from("hi"),
                String::from("from"),
                String::from("the"),
                String::from("future"),
            ];

            for val in vals {
                tx1.send(val).unwrap();
                trpl::sleep(Duration::from_secs(1)).await;
            }
        });

        let rx_fut = pin!(async {
            while let Some(value) = rx.recv().await {
                println!("received '{value}'");
            }
        });

        let tx_fut = pin!(async move {
            let vals = vec![
                String::from("more"),
                String::from("messages"),
                String::from("for"),
                String::from("you"),
            ];

            for val in vals {
                tx.send(val).unwrap();
                trpl::sleep(Duration::from_secs(1)).await;
            }
        });

        // Now we use Pin<&mut dyn Future<Output = ()>> instead of Box<dyn Future>
        let futures: Vec<Pin<&mut dyn Future<Output = ()>>> =
            vec![tx1_fut, rx_fut, tx_fut];

        trpl::join_all(futures).await;
    });
}
```

- `pin!` macro pins the future to the **stack** instead of the heap.
- The vector type becomes `Pin<&mut dyn Future<Output = ()>>`, which satisfies pinning requirements.

## 3. The `Stream` Trait

A `Stream` is like a **combination of `Iterator` and `Future`**: it produces a sequence of values asynchronously, one at a time.

### Stream Trait Definition

```rust
use std::pin::Pin;
use std::task::{Context, Poll};

trait Stream {
    type Item;

    fn poll_next(
        self: Pin<&mut Self>,
        cx: &mut Context<'_>
    ) -> Poll<Option<Self::Item>>;
}
```

Comparison:

| Concept       | Sync          | Async                        |
|---------------|---------------|------------------------------|
| Single value  | `T`           | `Future<Output = T>`         |
| Many values   | `Iterator<Item = T>` | `Stream<Item = T>`    |
| Poll method   | `next() -> Option<T>` | `poll_next() -> Poll<Option<T>>` |

- `Poll<Option<T>>` means:
  - `Poll::Ready(Some(T))` — next item is available.
  - `Poll::Ready(None)` — stream is exhausted.
  - `Poll::Pending` — no item yet, check back later.

### `StreamExt` for Ergonomic Use

`poll_next` is the low-level interface. The `StreamExt` trait provides the ergonomic `next()` method:

```rust
trait StreamExt: Stream {
    async fn next(&mut self) -> Option<Self::Item>
    where
        Self: Unpin;

    // other convenience methods...
}
```

- `StreamExt` is **automatically implemented** for every type that implements `Stream`.
- It is defined as a separate trait so the community can iterate on convenience APIs independently of the core `Stream` trait.
- This lets you write `while let Some(item) = stream.next().await { ... }` naturally.

## Key Relationships Diagram

```
Iterator ──────────────────────────► Stream
(sync, many values)                 (async, many values)
next() -> Option<T>                 poll_next() -> Poll<Option<T>>

Future ─────────────────────────────┐
(async, one value)                  │
poll() -> Poll<T>                   │
                                    │
                        Stream combines both ◄──┘
```

```
Pin<P>
  └── guarantees: data at P will NOT move in memory
        └── required for: self-referential futures (impl !Unpin)
        └── irrelevant for: most normal types (impl Unpin)
```

## Summary

| Trait/Type | Purpose |
|------------|---------|
| `Future`   | Represents an async computation that eventually produces a value. Driven by `poll()`. |
| `Poll<T>`  | Return type of `poll()`: either `Ready(T)` (done) or `Pending` (not yet). |
| `Pin<P>`   | Wrapper that prevents the pointed-to value from moving in memory. |
| `Unpin`    | Marker trait: "safe to move even behind `Pin`." Automatically derived for most types. |
| `Stream`   | Async iterator: produces multiple values over time via `poll_next()`. |
| `StreamExt`| Extension trait on `Stream` providing the ergonomic async `next()` method. |

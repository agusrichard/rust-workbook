# 17.6 - Futures, Tasks, and Threads

## Overview

This final section of chapter 17 ties together the three concurrency primitives in Rust: **threads**, **tasks**, and **futures**. It explains how they relate to each other, when to choose one over another, and how they can be combined in practice.

---

## 1. The Concurrency Hierarchy

Rust has three levels of concurrency, from coarsest to finest:

```
OS / Hardware
  └── Threads         (managed by the OS)
        └── Tasks     (managed by the async runtime's executor)
              └── Futures  (the most granular unit — a tree of async operations)
```

> "Futures are Rust's most granular unit of concurrency, and each future may represent a tree of other futures. The runtime — specifically, its executor — manages tasks, and tasks manage futures."

- **Threads** — OS-managed. Concurrency happens *between* threads.
- **Tasks** — Runtime-managed lightweight units. Concurrency happens *between* tasks **and** *within* a task (by switching between futures).
- **Futures** — The building blocks. A single task can drive a tree of futures.

## 2. Threads vs. Async: When to Choose

| Situation | Prefer |
|-----------|--------|
| CPU-bound, highly parallelizable work | **Threads** |
| I/O-bound, highly concurrent work (many sources, variable timing) | **Async** |
| Both needs | **Combine them** |

**Why threads for CPU-bound?**
Threads run truly in parallel across CPU cores. A future that does heavy computation without yielding would block the entire async runtime's thread.

**Why async for I/O-bound?**
I/O operations spend most of their time waiting. Async lets you handle thousands of concurrent I/O operations on a small number of threads without the memory overhead of one thread per connection.

**Threads have costs:**
- Significant memory overhead per thread
- Not available on all platforms (e.g., some embedded systems)
- OS scheduling overhead

**Async has costs:**
- Requires a runtime
- More complex mental model
- Not suitable for blocking/CPU-heavy work without `spawn_blocking`

---

## 3. Work-Stealing Runtimes

Modern async runtimes (like Tokio) use a **work-stealing** strategy:

> "Transparently move tasks around between threads, based on how the threads are currently being utilized."

This means:
- The runtime is **multithreaded by default**
- Tasks are automatically distributed across threads for optimal CPU utilization
- You get parallelism "for free" without manually managing threads

Functions like `spawn_blocking` and `spawn_task` operate within this multithreaded runtime.

---

## 4. Combining Threads and Async

The two models work well together. A common real-world pattern: use a thread for CPU-heavy or blocking work, and communicate results back to async code via a channel.

```rust
extern crate trpl;

use std::{thread, time::Duration};

fn main() {
    let (tx, mut rx) = trpl::channel();

    // Blocking thread: does work synchronously, sends results
    thread::spawn(move || {
        for i in 1..11 {
            tx.send(i).unwrap();
            thread::sleep(Duration::from_secs(1));
        }
    });

    // Async receiver: handles results as they arrive
    trpl::block_on(async {
        while let Some(message) = rx.recv().await {
            println!("{message}");
        }
    });
}
```

**What's happening:**
- `thread::spawn` — creates an OS thread that sends numbers with 1-second delays (blocking)
- `trpl::block_on` — runs an async block on the current thread
- `rx.recv().await` — asynchronously waits for each message without blocking the thread

This pattern is common in real applications — e.g., a video encoder running on a thread, sending progress updates to an async UI layer.

---

## 5. Key API Mentions

| API | Purpose |
|-----|---------|
| `thread::spawn` | Spawn an OS thread for blocking/CPU work |
| `trpl::spawn_task` | Spawn an async task on the runtime |
| `spawn_blocking` | Run blocking code inside the async runtime without blocking the executor thread |
| `trpl::block_on` | Bridge sync and async — run an async block from synchronous code |

## Mental Model Summary

```
Need to wait for I/O?
  └── Use async/await + futures

Need true parallelism (CPU work)?
  └── Use threads (or spawn_blocking inside async)

Need both?
  └── Combine: thread sends via channel, async receives

What runtime does under the hood:
  └── Polls futures → Pending? Register Waker, move on
                    → Ready?  Resume, produce value
```

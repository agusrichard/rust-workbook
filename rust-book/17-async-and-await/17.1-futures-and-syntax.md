# 17.1 - Futures and the Async Syntax

## High-Level Overview

This section introduces the two core building blocks of async Rust: **futures** (values that represent work which will complete at some point in the future) and the **`async`/`await` syntax** that makes writing async code feel natural and sequential. It walks through building a small web scraper that fetches page titles concurrently, revealing how the pieces fit together.

---

## Key Concepts

### 1. What Is a Future?

A **future** is a value representing an operation that hasn't completed yet. In Rust, futures implement the `Future` trait from `std::future`. The critical property of Rust futures is:

> **Futures are lazy** — they do nothing until you explicitly drive them forward with the `await` keyword.

This is different from languages like JavaScript where a Promise starts executing immediately on creation. A Rust future just *describes* the computation; the *runtime* is what actually drives it.

---

### 2. The `async` Keyword

Marking a function with `async` transforms it into a function that returns a `Future`. The two forms below are equivalent:

**Syntactic sugar form (what you write):**
```rust
async fn page_title(url: &str) -> Option<String> {
    // ...
}
```

**Desugared form (what the compiler generates):**
```rust
fn page_title(url: &str) -> impl Future<Output = Option<String>> {
    async move {
        // ...
    }
}
```

The return type of an `async fn foo() -> T` is `impl Future<Output = T>`, not `T` directly.

---

### 3. The `await` Keyword — Postfix Style

In Rust, `await` is a **postfix** keyword — it comes *after* the expression, not before it:

```rust
// Rust style (postfix)
let response = trpl::get(url).await;

// NOT like JavaScript (prefix)
// let response = await trpl::get(url);
```

The postfix style is intentional: it enables clean **method chaining** across multiple async calls:

```rust
// Chained await calls read left-to-right
let response_text = trpl::get(url).await.text().await;
```

If `await` were prefix, chaining like this would be awkward or require nested parentheses.

---

### 4. The Runtime Requirement — Why `main` Can't Be `async`

Attempting to mark `main` as `async` produces a compiler error:

```rust
// This does NOT compile:
async fn main() { ... }
```

```
error[E0752]: `main` function is not allowed to be `async`
 --> src/main.rs:6:1
  |
6 | async fn main() {
  | ^^^^^^^^^^^^^^^ `main` function is not allowed to be `async`
```

**Why?** Async code needs a **runtime** — an executor that polls futures and drives them to completion. Rust itself does not bundle a runtime; it is deliberately left to ecosystem crates (like `tokio`, `async-std`). The entry point `main` must be synchronous so it can *set up* that runtime first.

The fix: use `trpl::block_on()` (which wraps `tokio`) to bridge synchronous `main` into async code:

```rust
fn main() {
    trpl::block_on(async {
        // async code goes here
    });
}
```

`block_on` sets up the runtime and *blocks the current thread* until the future passed to it completes.

---

### 5. How the Compiler Implements Async — State Machines

Under the hood, the compiler transforms every `async` block into a **state machine enum**, where each `await` point is a state:

```rust
// Conceptually, for page_title, the compiler generates something like:
enum PageTitleFuture<'a> {
    Initial { url: &'a str },
    GetAwaitPoint { url: &'a str },
    TextAwaitPoint { response: trpl::Response },
}
```

Each time the future is polled by the runtime:
- If it can make progress, it does so and transitions to the next state.
- If it must wait (e.g., for network I/O), it returns `Poll::Pending` and suspends.
- When it finishes, it returns `Poll::Ready(value)`.

This is entirely invisible — you write sequential-looking code, and the compiler generates the state machine automatically.

---

### 6. Concurrency with `trpl::select`

To race two futures and take the result of whichever finishes first, use `trpl::select`. It returns an `Either<A, B>`:

```rust
enum Either<A, B> {
    Left(A),   // first future completed
    Right(B),  // second future completed
}
```

`Either` is similar to `Result` but carries no notion of success/failure — just *which* side won.

## Full Code Examples

### Listing 17-1: Basic `async fn` — fetching a page title

```rust
use trpl::Html;

async fn page_title(url: &str) -> Option<String> {
    let response = trpl::get(url).await;
    let response_text = response.text().await;
    Html::parse(&response_text)
        .select_first("title")
        .map(|title| title.inner_html())
}
```

### Listing 17-2: Chained `await` calls

```rust
use trpl::Html;

async fn page_title(url: &str) -> Option<String> {
    let response_text = trpl::get(url).await.text().await;
    Html::parse(&response_text)
        .select_first("title")
        .map(|title| title.inner_html())
}
```

### Desugared async fn — what the compiler sees

```rust
use std::future::Future;
use trpl::Html;

fn page_title(url: &str) -> impl Future<Output = Option<String>> {
    async move {
        let text = trpl::get(url).await.text().await;
        Html::parse(&text)
            .select_first("title")
            .map(|title| title.inner_html())
    }
}
```

### Listing 17-3: Broken — `main` cannot be `async`

```rust
// ERROR: main function is not allowed to be `async`
async fn main() {
    let args: Vec<String> = std::env::args().collect();
    let url = &args[1];
    match page_title(url).await {
        Some(title) => println!("The title for {url} was {title}"),
        None => println!("{url} had no title"),
    }
}
```

### Listing 17-4: Fixed — using `trpl::block_on`

```rust
use trpl::Html;

fn main() {
    let args: Vec<String> = std::env::args().collect();

    trpl::block_on(async {
        let url = &args[1];
        match page_title(url).await {
            Some(title) => println!("The title for {url} was {title}"),
            None => println!("{url} had no title"),
        }
    })
}

async fn page_title(url: &str) -> Option<String> {
    let response_text = trpl::get(url).await.text().await;
    Html::parse(&response_text)
        .select_first("title")
        .map(|title| title.inner_html())
}
```

**Output:**
```
$ cargo run -- "https://www.rust-lang.org"
The title for https://www.rust-lang.org was
            Rust Programming Language
```

### Listing 17-5: Racing two futures with `trpl::select`

```rust
use trpl::{Either, Html};

fn main() {
    let args: Vec<String> = std::env::args().collect();

    trpl::block_on(async {
        let title_fut_1 = page_title(&args[1]);
        let title_fut_2 = page_title(&args[2]);

        let (url, maybe_title) =
            match trpl::select(title_fut_1, title_fut_2).await {
                Either::Left(left) => left,
                Either::Right(right) => right,
            };

        println!("{url} returned first");
        match maybe_title {
            Some(title) => println!("Its page title was: '{title}'"),
            None => println!("It had no title."),
        }
    })
}

async fn page_title(url: &str) -> (&str, Option<String>) {
    let response_text = trpl::get(url).await.text().await;
    let title = Html::parse(&response_text)
        .select_first("title")
        .map(|title| title.inner_html());
    (url, title)
}
```

## Conceptual Diagram

```
Future lifecycle:
  Created     Pending       Pending       Ready
     |            |             |            |
  page_title() ---.await--> [waiting] ---.await--> Some("Rust...")
                  ^                       ^
             network req             response body
             dispatched               received

State machine (compiler-generated):
  State 0: Initial { url }
      | poll → dispatch HTTP GET
  State 1: GetAwaitPoint { url }
      | poll → if response ready, extract text
  State 2: TextAwaitPoint { response }
      | poll → if body ready, parse HTML → return Poll::Ready(title)
```

## Summary

| Concept | Key Point |
|---|---|
| `Future` | Lazy value representing eventual result; does nothing until polled |
| `async fn` | Desugars to `fn -> impl Future<Output = T>` |
| `await` | Postfix; suspends current future until inner future is ready |
| Runtime | Required to poll futures; Rust doesn't include one — use `tokio`, etc. |
| `block_on` | Bridges sync `main` to async; blocks thread until future completes |
| State machine | Compiler transforms `async` blocks into enums tracking await-point state |
| `select!` | Races two futures; returns `Either::Left` or `Either::Right` for the winner |

The fundamental insight: `async`/`await` lets you write code that *looks* sequential while the runtime handles the interleaving. You define the *what* and *where it can pause*; the runtime handles *when* to resume.

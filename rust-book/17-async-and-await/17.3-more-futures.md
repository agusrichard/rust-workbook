# 17.3 - Working With Any Number of Futures

## High-Level Overview

This section digs into two deeper aspects of async Rust:

1. **Yielding control** — async code in Rust only suspends at explicit `await` points. Synchronous work between `await`s holds the thread and starves other futures. The section shows how to fix this with `trpl::sleep` and the more principled `trpl::yield_now()`.

2. **Building async abstractions** — because futures compose with other futures, you can build powerful utilities (like a `timeout`) from simple primitives. The section walks through designing and implementing a generic `timeout` function from scratch using `trpl::select`.

---

## Key Concepts

### 1. Async Only Yields at `await` Points

> "Rust *only* pauses async blocks and hands control back to a runtime at an `await` point. Everything between `await` points is synchronous."

This means: if you call blocking code (like `thread::sleep`) inside an async block, the **entire runtime thread is blocked** — no other future can run. The runtime has no way to interrupt a future mid-execution; it can only resume a future that previously yielded at an `await`.

This is called **cooperative multitasking**: futures must voluntarily yield control.

```
Preemptive (OS threads):  runtime can interrupt at any time
Cooperative (async):      future runs until it hits an .await — ONLY THEN can runtime switch
```

---

### 2. The Starvation Problem

To demonstrate starvation, a `slow` helper simulates CPU-bound work using `thread::sleep` (which blocks the thread — no `await` inside):

**Listing 17-14: The `slow` helper**

```rust
use std::{thread, time::Duration};

fn main() {
    trpl::block_on(async {
        // We will call `slow` here later
    });
}

fn slow(name: &str, ms: u64) {
    thread::sleep(Duration::from_millis(ms));  // blocks the thread — no await!
    println!("'{name}' ran for {ms}ms");
}
```

Now put two futures that each call `slow` multiple times before hitting their first `.await`:

**Listing 17-15: Starvation — futures run sequentially because blocking calls hold the thread**

```rust
use std::{thread, time::Duration};

fn main() {
    trpl::block_on(async {
        let a = async {
            println!("'a' started.");
            slow("a", 30);
            slow("a", 10);
            slow("a", 20);
            trpl::sleep(Duration::from_millis(50)).await;  // FIRST yield in 'a'
            println!("'a' finished.");
        };

        let b = async {
            println!("'b' started.");
            slow("b", 75);
            slow("b", 10);
            slow("b", 15);
            slow("b", 350);
            trpl::sleep(Duration::from_millis(50)).await;  // FIRST yield in 'b'
            println!("'b' finished.");
        };

        trpl::select(a, b).await;
    });
}
```

**Output** (sequential, not concurrent — `a` monopolises the thread until its first `await`):
```
'a' started.
'a' ran for 30ms
'a' ran for 10ms
'a' ran for 20ms
'b' started.       ← 'b' only gets a turn after 'a' hits its first .await
'b' ran for 75ms
'b' ran for 10ms
'b' ran for 15ms
'b' ran for 350ms
'a' finished.
```

Even though both futures are passed to `trpl::select`, `a` holds the thread through all three `slow()` calls before ever yielding. The runtime is locked out until that first `.await`.

---

### 3. Fix 1 — `trpl::sleep` Between Blocking Calls

Inserting a tiny `trpl::sleep(one_ms).await` between blocking calls gives the runtime a chance to switch to other futures. Each `await` is a yield point.

**Listing 17-16: Add yield points with `trpl::sleep`**

```rust
use std::{thread, time::Duration};

fn main() {
    trpl::block_on(async {
        let one_ms = Duration::from_millis(1);

        let a = async {
            println!("'a' started.");
            slow("a", 30);
            trpl::sleep(one_ms).await;   // yield → runtime can switch to 'b'
            slow("a", 10);
            trpl::sleep(one_ms).await;
            slow("a", 20);
            trpl::sleep(one_ms).await;
            println!("'a' finished.");
        };

        let b = async {
            println!("'b' started.");
            slow("b", 75);
            trpl::sleep(one_ms).await;
            slow("b", 10);
            trpl::sleep(one_ms).await;
            slow("b", 15);
            trpl::sleep(one_ms).await;
            slow("b", 350);
            trpl::sleep(one_ms).await;
            println!("'b' finished.");
        };

        trpl::select(a, b).await;
    });
}
```

**Output** (now interleaved — futures take turns):
```
'a' started.
'a' ran for 30ms
'b' started.        ← 'b' gets in after 'a's first yield
'b' ran for 75ms
'a' ran for 10ms
'b' ran for 10ms
'a' ran for 20ms
'b' ran for 15ms
'a' finished.
```

This works, but is imprecise — the 1ms sleep introduces a real timing delay, and the intent ("I want to yield") is obscured by it looking like intentional timing logic.

---

### 4. Fix 2 — `trpl::yield_now()` (Preferred)

`trpl::yield_now()` is an async function that immediately yields control back to the runtime **without any sleep delay**. It is clearer in intent and faster than a tiny sleep.

```rust
trpl::yield_now().await;   // yield immediately, no timer involved
trpl::sleep(one_ms).await; // yield AND wait ≥1ms before being rescheduled
```

**Listing 17-17: Yield without sleeping using `trpl::yield_now()`**

```rust
use std::{thread, time::Duration};

fn main() {
    trpl::block_on(async {
        let a = async {
            println!("'a' started.");
            slow("a", 30);
            trpl::yield_now().await;   // yield immediately, no delay
            slow("a", 10);
            trpl::yield_now().await;
            slow("a", 20);
            trpl::yield_now().await;
            println!("'a' finished.");
        };

        let b = async {
            println!("'b' started.");
            slow("b", 75);
            trpl::yield_now().await;
            slow("b", 10);
            trpl::yield_now().await;
            slow("b", 15);
            trpl::yield_now().await;
            slow("b", 350);
            trpl::yield_now().await;
            println!("'b' finished.");
        };

        trpl::select(a, b).await;
    });
}
```

Use `yield_now()` whenever you have CPU-heavy synchronous work inside an async block that needs to share the runtime with other futures.

### 5. Building a Custom `timeout` Abstraction

Because `trpl::select` races two futures and returns whichever finishes first, you can build a `timeout` by racing any future against a `trpl::sleep`. This shows how async primitives compose into higher-level tools.

**Listing 17-18: Desired usage — before writing the implementation**

```rust
use std::time::Duration;

fn main() {
    trpl::block_on(async {
        let slow = async {
            trpl::sleep(Duration::from_secs(5)).await;
            "Finally finished"
        };

        match timeout(slow, Duration::from_secs(2)).await {
            Ok(message) => println!("Succeeded with '{message}'"),
            Err(duration) => {
                println!("Failed after {} seconds", duration.as_secs())
            }
        }
    });
}
```

---

### 6. Generic Futures with `F: Future`

The `timeout` function is generic over any future type `F`. `F::Output` is the **associated type** on the `Future` trait — the value the future produces when it completes. This makes `timeout` usable with *any* future, regardless of what it returns.

**Listing 17-19: `timeout` — type signature**

```rust
async fn timeout<F: Future>(
    future_to_try: F,
    max_time: Duration,
) -> Result<F::Output, Duration> {
    // implementation goes here
}
```

The return type `Result<F::Output, Duration>` means:
- `Ok(output)` — the future completed before the deadline.
- `Err(duration)` — the timeout elapsed; returns how long the limit was.

**Listing 17-20: `timeout` — complete implementation**

```rust
use std::time::Duration;
use trpl::Either;

fn main() {
    trpl::block_on(async {
        let slow = async {
            trpl::sleep(Duration::from_secs(5)).await;
            "Finally finished"
        };

        match timeout(slow, Duration::from_secs(2)).await {
            Ok(message) => println!("Succeeded with '{message}'"),
            Err(duration) => {
                println!("Failed after {} seconds", duration.as_secs())
            }
        }
    });
}

async fn timeout<F: Future>(
    future_to_try: F,
    max_time: Duration,
) -> Result<F::Output, Duration> {
    match trpl::select(future_to_try, trpl::sleep(max_time)).await {
        Either::Left(output) => Ok(output),    // future_to_try won the race
        Either::Right(_) => Err(max_time),     // sleep won — timeout elapsed
    }
}
```

**Output:**
```
Failed after 2 seconds
```

The `slow` future needs 5 seconds but the timeout is 2 seconds — `trpl::sleep(max_time)` wins the `select` race, returning `Either::Right`, which maps to `Err(max_time)`.

## Conceptual Diagrams

### Cooperative multitasking — yield points are the only switch points

```
Timeline (without yield points):
  Thread: [=== a: slow(30) ===][=== a: slow(10) ===][=== a: slow(20) ===][a await][b: slow(75)]...
          ^--- 'b' cannot run at all until 'a' reaches its first .await

Timeline (with yield points):
  Thread: [a: slow(30)][yield→b][b: slow(75)][yield→a][a: slow(10)][yield→b][b: slow(10)]...
          ^--- each yield_now().await is a switch point
```

### `timeout` — racing two futures

```
timeout(future_to_try, max_time):

  trpl::select(
    future_to_try          ────────────────────► Either::Left(output)  → Ok(output)
    trpl::sleep(max_time)  ────────────────────► Either::Right(_)      → Err(max_time)
  )

  Whichever future resolves first wins; the other is dropped.
```

---

## Key Comparisons

| Approach | Yields? | Introduces delay? | Intent clarity |
|---|---|---|---|
| No yield points | No | No | N/A — causes starvation |
| `trpl::sleep(1ms).await` | Yes | Yes (≥1ms) | Low — looks like intentional timing |
| `trpl::yield_now().await` | Yes | No | High — clearly signals "give others a turn" |

---

## Summary

| Concept | Key Takeaway |
|---|---|
| Cooperative multitasking | Futures only yield at `await` points; synchronous code between `await`s holds the thread exclusively |
| Task starvation | Blocking code (e.g. `thread::sleep`) inside async blocks starves other futures |
| `yield_now()` | Yields immediately to the runtime with no delay; preferred over tiny sleeps for signalling intent |
| Composing async primitives | `select` + `sleep` → `timeout`; small primitives combine into powerful abstractions |
| `F: Future` generics | `F::Output` is the associated type for the future's resolved value; enables fully generic async APIs |
| `select` return value | `Either::Left` (first future won) or `Either::Right` (second future won) |

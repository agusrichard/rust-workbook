# 17.2 - Applying Concurrency with Async

## High-Level Overview

This section translates the concurrency patterns from Chapter 16 (threads) into async equivalents. It shows that async tasks look and behave similarly to threads — but without spawning OS threads — and walks through increasingly realistic examples: spawning tasks, awaiting their completion, passing messages between tasks, and handling multiple producers. A key theme is the difference between **sequential** execution inside a single async block and **concurrent** execution when multiple futures are joined.

---

## Key Concepts

### 1. Spawning Async Tasks — `trpl::spawn_task`

Just like `thread::spawn` creates a new OS thread, `trpl::spawn_task` creates a new **async task** — a lightweight unit of work managed by the async runtime, not the OS. The spawned task runs concurrently with the surrounding async block.

> If the outer async block finishes before the spawned task, the task is dropped (cancelled). This mirrors the behavior of threads when `main` exits.

---

### 2. Awaiting Task Handles

`spawn_task` returns a handle — a future itself. `.await`-ing it blocks until the task completes, similar to calling `.join()` on a thread handle.

```
thread::spawn  →  handle.join().unwrap()
spawn_task     →  handle.await.unwrap()
```

---

### 3. Sequential vs. Concurrent Execution

**Inside a single `async` block, code is sequential.** Writing two loops one after the other means the second doesn't start until the first finishes:

```rust
// SEQUENTIAL — fut2 only starts after fut1 finishes
let fut1 = async { /* loop */ };
let fut2 = async { /* loop */ };
fut1.await;
fut2.await;
```

**To run concurrently, use `trpl::join` or `trpl::join!`** — these poll both futures alternately, allowing interleaving:

```rust
// CONCURRENT — both loops interleave
trpl::join(fut1, fut2).await;
```

---

### 4. Fair Scheduling with `trpl::join`

Unlike OS thread scheduling (controlled by the OS, non-deterministic), `trpl::join` is **fair** — it alternates between the futures it polls, producing deterministic, interleaved output. This is why the output of `join`-based examples follows the same order every run.

```
fair join output:
  hi number 1 from the first task!
  hi number 1 from the second task!
  hi number 2 from the first task!
  hi number 2 from the second task!
  ...
```

---

### 5. Async Message Passing with `trpl::channel`

Async channels work like the `std::sync::mpsc` channels from Chapter 16, with one key difference: **`recv()` returns a future** and must be `.await`-ed.

```
sync:   rx.recv()        →  blocks the thread
async:  rx.recv().await  →  suspends the future, frees the thread for other work
```

`send()` does **not** need `.await` — it returns immediately.

The channel closes (and `recv()` returns `None`) when **all senders are dropped**. This is what terminates `while let Some(value) = rx.recv().await` loops.

---

### 6. `async move` — Taking Ownership into a Future

By default an `async` block borrows from its environment. Using `async move` causes it to **take ownership** of captured variables — just like a `move` closure.

This is essential for channels: the sender (`tx`) must be moved into the sending future so that it is dropped when the future completes, closing the channel. Without `async move`, `tx` would stay alive in the outer scope and the receiver loop would never see `None`, causing the program to hang.

---

### 7. Multiple Producers — Cloning Senders

Multiple futures can send to the same channel by cloning the sender with `.clone()`. Each clone is an independent sender; the channel closes only when **all** clones are dropped.

For three or more futures, use the `trpl::join!` **macro** (instead of the `trpl::join` function, which only takes two arguments):

```rust
trpl::join!(tx1_fut, tx_fut, rx_fut);
```

## Full Code Examples

### Listing 17-6: Spawning a concurrent task

```rust
use std::time::Duration;

fn main() {
    trpl::block_on(async {
        trpl::spawn_task(async {
            for i in 1..10 {
                println!("hi number {i} from the first task!");
                trpl::sleep(Duration::from_millis(500)).await;
            }
        });

        for i in 1..5 {
            println!("hi number {i} from the second task!");
            trpl::sleep(Duration::from_millis(500)).await;
        }
    });
}
```

**Output** (order may vary across runs):
```
hi number 1 from the second task!
hi number 1 from the first task!
hi number 2 from the first task!
hi number 2 from the second task!
...
hi number 5 from the first task!
```

> The spawned task (first task) is cancelled after the outer async block ends — it only reaches iteration 5, not 9.

---

### Listing 17-7: Awaiting the task handle to let it finish

```rust
use std::time::Duration;

fn main() {
    trpl::block_on(async {
        let handle = trpl::spawn_task(async {
            for i in 1..10 {
                println!("hi number {i} from the first task!");
                trpl::sleep(Duration::from_millis(500)).await;
            }
        });

        for i in 1..5 {
            println!("hi number {i} from the second task!");
            trpl::sleep(Duration::from_millis(500)).await;
        }

        handle.await.unwrap();
    });
}
```

**Output:**
```
hi number 1 from the second task!
hi number 1 from the first task!
...
hi number 4 from the second task!
hi number 5 from the first task!
hi number 6 from the first task!
hi number 7 from the first task!
hi number 8 from the first task!
hi number 9 from the first task!
```

> Now both tasks complete fully because `handle.await` holds the outer block open until the spawned task finishes.

### Listing 17-8: Using `trpl::join` for fair concurrent execution

```rust
use std::time::Duration;

fn main() {
    trpl::block_on(async {
        let fut1 = async {
            for i in 1..10 {
                println!("hi number {i} from the first task!");
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        let fut2 = async {
            for i in 1..5 {
                println!("hi number {i} from the second task!");
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        trpl::join(fut1, fut2).await;
    });
}
```

**Output** (deterministic — same order every run due to fair scheduling):
```
hi number 1 from the first task!
hi number 1 from the second task!
hi number 2 from the first task!
hi number 2 from the second task!
hi number 3 from the first task!
hi number 3 from the second task!
hi number 4 from the first task!
hi number 4 from the second task!
hi number 5 from the first task!
hi number 6 from the first task!
hi number 7 from the first task!
hi number 8 from the first task!
hi number 9 from the first task!
```

### Listing 17-9: Simple async channel — send and receive one message

```rust
fn main() {
    trpl::block_on(async {
        let (tx, mut rx) = trpl::channel();

        let val = String::from("hi");
        tx.send(val).unwrap();

        let received = rx.recv().await.unwrap();
        println!("received '{received}'");
    });
}
```

### Listing 17-10: Sending multiple messages (still sequential — broken concurrency)

```rust
use std::time::Duration;

fn main() {
    trpl::block_on(async {
        let (tx, mut rx) = trpl::channel();

        let vals = vec![
            String::from("hi"),
            String::from("from"),
            String::from("the"),
            String::from("future"),
        ];

        for val in vals {
            tx.send(val).unwrap();
            trpl::sleep(Duration::from_millis(500)).await;
        }

        while let Some(value) = rx.recv().await {
            println!("received '{value}'");
        }
    });
}
```

> This version is **sequential**: the send loop finishes entirely before the receive loop starts. Not truly concurrent.

---

### Listing 17-11: Separating send/receive into distinct async blocks (still broken — `tx` not dropped)

```rust
use std::time::Duration;

fn main() {
    trpl::block_on(async {
        let (tx, mut rx) = trpl::channel();

        let tx_fut = async {
            let vals = vec![
                String::from("hi"),
                String::from("from"),
                String::from("the"),
                String::from("future"),
            ];

            for val in vals {
                tx.send(val).unwrap();
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        let rx_fut = async {
            while let Some(value) = rx.recv().await {
                println!("received '{value}'");
            }
        };

        trpl::join(tx_fut, rx_fut).await;
    });
}
```

> Still a problem: `tx` is borrowed by `tx_fut` but also stays alive in the outer block. The channel never closes, so `rx_fut`'s `while let` loop never ends — the program **hangs**.

---

### Listing 17-12: Fixed with `async move` — sender dropped when future completes

```rust
use std::time::Duration;

fn main() {
    trpl::block_on(async {
        let (tx, mut rx) = trpl::channel();

        let tx_fut = async move {           // <-- move tx into this future
            let vals = vec![
                String::from("hi"),
                String::from("from"),
                String::from("the"),
                String::from("future"),
            ];

            for val in vals {
                tx.send(val).unwrap();
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };  // tx is dropped here when tx_fut completes

        let rx_fut = async {
            while let Some(value) = rx.recv().await {
                println!("received '{value}'");
            }
        };

        trpl::join(tx_fut, rx_fut).await;
    });
}
```

> `async move` gives `tx_fut` ownership of `tx`. When `tx_fut` finishes, `tx` is dropped, the channel closes, `rx.recv()` returns `None`, and the `while let` loop exits cleanly.

---

### Listing 17-13: Multiple producers with cloned senders and `join!`

```rust
use std::time::Duration;

fn main() {
    trpl::block_on(async {
        let (tx, mut rx) = trpl::channel();

        let tx1 = tx.clone();
        let tx1_fut = async move {
            let vals = vec![
                String::from("hi"),
                String::from("from"),
                String::from("the"),
                String::from("future"),
            ];

            for val in vals {
                tx1.send(val).unwrap();
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        let rx_fut = async {
            while let Some(value) = rx.recv().await {
                println!("received '{value}'");
            }
        };

        let tx_fut = async move {
            let vals = vec![
                String::from("more"),
                String::from("messages"),
                String::from("for"),
                String::from("you"),
            ];

            for val in vals {
                tx.send(val).unwrap();
                trpl::sleep(Duration::from_millis(1500)).await;  // slower sender
            }
        };

        trpl::join!(tx1_fut, tx_fut, rx_fut);  // join! macro for 3 futures
    });
}
```

**Output** (messages interleaved by timing):
```
received 'hi'
received 'more'
received 'from'
received 'the'
received 'messages'
received 'future'
received 'for'
received 'you'
```

> `tx1` sends every 500ms, `tx` (original) sends every 1500ms — the interleaving reflects those different cadences.

## Conceptual Diagram

```
Sequential (wrong — fut2 waits for fut1):
  [=== fut1 ===][=== fut2 ===]

Concurrent with join (correct — both interleave):
  [fut1 step][fut2 step][fut1 step][fut2 step]...

Channel lifetime:
  tx_fut (owns tx) ──sends──► channel ──► rx_fut
        ↓ completes
       tx dropped
        ↓
    channel closes
        ↓
  rx.recv() → None → while let exits

Multiple producers:
  tx1_fut (owns tx1) ──500ms──► channel ──► rx_fut
  tx_fut  (owns tx)  ─1500ms──►     ↑
  (channel closes when both tx1 AND tx are dropped)
```

## Comparison: Threads vs. Async Tasks

| Concept              | Threads (Ch 16)           | Async Tasks (Ch 17)             |
|----------------------|---------------------------|---------------------------------|
| Spawn                | `thread::spawn`           | `trpl::spawn_task`              |
| Wait for completion  | `handle.join().unwrap()`  | `handle.await.unwrap()`         |
| Run two concurrently | OS schedules them         | `trpl::join(fut1, fut2).await`  |
| Run N concurrently   | N `join()` calls          | `trpl::join!(f1, f2, ..., fn)` |
| Channels             | `mpsc::channel` + `recv()`| `trpl::channel` + `recv().await`|
| Multiple senders     | `tx.clone()`              | `tx.clone()` (same pattern)     |
| Send ownership in    | `move` closure            | `async move` block              |

---

## Summary

| Topic | Key Takeaway |
|---|---|
| `spawn_task` | Like `thread::spawn` but async; task cancelled if outer block ends first |
| `.await` on handle | Keeps outer block alive until spawned task finishes |
| Sequential vs concurrent | Single `async` block = sequential; `join` = concurrent |
| `trpl::join` | Fair scheduler; polls futures alternately; deterministic output |
| `trpl::join!` | Macro form for 3+ futures |
| `rx.recv().await` | Suspends without blocking the thread; returns `None` when channel closes |
| `async move` | Moves captured vars into the future; essential for dropping senders |
| Multiple producers | Clone the sender; channel closes when all clones are dropped |

# 14.3 - Cargo Workspaces

## High-Level Overview

As projects grow, splitting code into multiple library crates becomes necessary. A **Cargo workspace** is a set of packages that share the same `Cargo.lock` and output (`target`) directory. This ensures all crates in a workspace use consistent dependency versions and avoids duplicate compilation artifacts.

---

## 1. Creating a Workspace

A workspace is defined by a root `Cargo.toml` containing a `[workspace]` section — it has no `[package]` section of its own.

### Setup

```
$ mkdir add
$ cd add
```

**Root `Cargo.toml`:**

```toml
[workspace]
resolver = "3"
```

### Adding the binary crate

```
$ cargo new adder
```

The workspace `Cargo.toml` is updated automatically:

```toml
[workspace]
resolver = "3"
members = ["adder"]
```

### Build output at this point

```
$ cargo build
   Compiling adder v0.1.0 (file:///projects/add/adder)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.22s
```

**Directory structure:**

```
├── Cargo.lock
├── Cargo.toml
├── adder
│   ├── Cargo.toml
│   └── src
│       └── main.rs
└── target
```

There is a single `target` directory at the root — all crates share it. Each member crate also has its own `Cargo.toml` for its own metadata and dependencies, but the compiled output goes to the same place.

## 2. Creating the Second Package in the Workspace

### Add a library crate

```
$ cargo new add_one --lib
```

Updated root `Cargo.toml`:

```toml
[workspace]
resolver = "3"
members = ["adder", "add_one"]
```

**Updated directory structure:**

```
├── Cargo.lock
├── Cargo.toml
├── add_one
│   ├── Cargo.toml
│   └── src
│       └── lib.rs
├── adder
│   ├── Cargo.toml
│   └── src
│       └── main.rs
└── target
```

### Implement the library

**`add_one/src/lib.rs`:**

```rust
pub fn add_one(x: i32) -> i32 {
    x + 1
}
```

### Make `adder` depend on `add_one`

Cargo does **not** assume workspace crates depend on each other — dependencies must be declared explicitly using a path dependency.

**`adder/Cargo.toml`:**

```toml
[dependencies]
add_one = { path = "../add_one" }
```

### Use the library in the binary

**`adder/src/main.rs`:**

```rust
use add_one;

fn main() {
    let num = 10;
    println!("Hello, world! {num} plus one is {}!", add_one::add_one(num));
}
```

### Build and run

```
$ cargo build
   Compiling add_one v0.1.0 (file:///projects/add/add_one)
   Compiling adder v0.1.0 (file:///projects/add/adder)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.22s
```

Run a specific crate with the `-p` flag:

```
$ cargo run -p adder
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.00s
     Running `target/debug/adder`
Hello, world! 10 plus one is 11!
```

## 3. Depending on an External Package in a Workspace

External crates must be added to each member's `Cargo.toml` individually — there is no workspace-level dependency shortcut. However, all members share a **single `Cargo.lock`**, so the same version of an external crate is used across the whole workspace.

### Adding `rand` to `add_one`

**`add_one/Cargo.toml`:**

```toml
[dependencies]
rand = "0.8.5"
```

After `cargo build`, `rand` is recorded in the root `Cargo.lock`. If `adder` also needs `rand`, it must add it to its own `Cargo.toml` — but the shared `Cargo.lock` guarantees both resolve to the same version, avoiding duplication of compiled artifacts.

## 4. Adding Tests to a Workspace

Tests work the same as in single-crate projects. Each crate has its own tests.

### Test in the library — `add_one/src/lib.rs`

```rust
pub fn add_one(x: i32) -> i32 {
    x + 1
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn it_works() {
        assert_eq!(3, add_one(2));
    }
}
```

### Run all workspace tests

```
$ cargo test
   Compiling add_one v0.1.0 (file:///projects/add/add_one)
   Compiling adder v0.1.0 (file:///projects/add/adder)
```

### Run tests for a specific crate only

```
$ cargo test -p add_one
```

---

## 5. Publishing Workspace Crates

Workspace crates are **not** published as a group. Each crate must be published individually using the `-p` flag:

```
$ cargo publish -p add_one
$ cargo publish -p adder
```

---

## Key Concepts Summary

| Concept                   | Detail                                                                              |
|---------------------------|-------------------------------------------------------------------------------------|
| Shared `Cargo.lock`       | All workspace members resolve to the same versions of external dependencies         |
| Shared `target` directory | Compiled artifacts are shared — no redundant recompilation across crates            |
| Explicit dependencies     | Workspace crates do not automatically depend on each other; use `path = ".."` syntax|
| `-p` flag                 | Target a specific workspace member for `cargo build`, `run`, `test`, or `publish`  |
| No workspace-level deps   | Each crate lists its own `[dependencies]`; no shared `[dependencies]` section       |
| Publishing                | Each crate in the workspace must be published separately to crates.io               |

Workspaces help manage multi-crate projects by keeping builds fast (shared cache), dependency versions consistent (shared lock file), and coordination easy when crates are developed and changed together.

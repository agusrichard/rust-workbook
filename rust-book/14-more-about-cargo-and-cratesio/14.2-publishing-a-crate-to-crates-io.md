# 14.2 - Publishing a Crate to Crates.io

## High-Level Overview

This section covers everything needed to publish a Rust crate to [crates.io](https://crates.io): writing good documentation comments, structuring a public API with re-exports, setting up an account, adding required package metadata, publishing, versioning, and yanking old versions. Crates.io is a permanent, open-source registry — once published, code cannot be deleted.

---

## 1. Documentation Comments (`///`)

Rust supports documentation comments using three slashes (`///`). They generate HTML via `cargo doc` and support Markdown formatting. Place them directly above the item being documented.

### Listing 14-1 — Documenting a function

```rust
/// Adds one to the number given.
///
/// # Examples
///
/// ```
/// let arg = 5;
/// let answer = my_crate::add_one(arg);
///
/// assert_eq!(6, answer);
/// ```
pub fn add_one(x: i32) -> i32 {
    x + 1
}
```

Run `cargo doc` to generate the HTML. Run `cargo doc --open` to build and immediately open it in a browser.

### Commonly Used Documentation Sections

| Section    | Purpose                                                                             |
|------------|-------------------------------------------------------------------------------------|
| `# Examples` | Code examples showing how to use the item                                         |
| `# Panics`   | Scenarios where the function panics                                               |
| `# Errors`   | Types and conditions of errors returned (for functions returning `Result`)        |
| `# Safety`   | Why the function is `unsafe` and what invariants callers must uphold              |

### Documentation Comments as Tests

Code examples in `///` doc comments are **automatically run as tests** by `cargo test`. This keeps examples accurate and up to date.

## 2. Crate-Level Documentation (`//!`)

The `//!` comment style documents the *containing* item rather than the item that follows. Use it at the top of `src/lib.rs` to document the crate itself.

### Listing 14-2 — Crate-level docs with `//!`

```rust
//! # My Crate
//!
//! `my_crate` is a collection of utilities to make performing certain
//! calculations more convenient.

/// Adds one to the number given.
///
/// # Examples
///
/// ```
/// let arg = 5;
/// let answer = my_crate::add_one(arg);
///
/// assert_eq!(6, answer);
/// ```
pub fn add_one(x: i32) -> i32 {
    x + 1
}
```

## 3. Exporting a Convenient Public API with `pub use`

The structure of your public API matters. Items buried in deep module hierarchies are hard for users to find. Re-exporting with `pub use` brings items to a more convenient top-level path without changing the internal module structure.

### Listing 14-3 — Library with inconvenient nested structure

```rust
//! # Art
//!
//! A library for modeling artistic concepts.

pub mod kinds {
    /// The primary colors according to the RYB color model.
    pub enum PrimaryColor {
        Red,
        Yellow,
        Blue,
    }

    /// The secondary colors according to the RYB color model.
    pub enum SecondaryColor {
        Orange,
        Green,
        Purple,
    }
}

pub mod utils {
    use crate::kinds::*;

    /// Combines two primary colors in equal amounts to create
    /// a secondary color.
    pub fn mix(c1: PrimaryColor, c2: PrimaryColor) -> SecondaryColor {
        // --snip--
        unimplemented!();
    }
}
```

### Listing 14-4 — User code with the nested structure (verbose `use` paths)

```rust
use art::kinds::PrimaryColor;
use art::utils::mix;

fn main() {
    let red = PrimaryColor::Red;
    let yellow = PrimaryColor::Yellow;
    mix(red, yellow);
}
```

Users must know the internal module layout. This is not ideal.

### Listing 14-5 — Adding `pub use` re-exports to flatten the API

```rust
//! # Art
//!
//! A library for modeling artistic concepts.

pub use self::kinds::PrimaryColor;
pub use self::kinds::SecondaryColor;
pub use self::utils::mix;

pub mod kinds {
    /// The primary colors according to the RYB color model.
    pub enum PrimaryColor {
        Red,
        Yellow,
        Blue,
    }

    /// The secondary colors according to the RYB color model.
    pub enum SecondaryColor {
        Orange,
        Green,
        Purple,
    }
}

pub mod utils {
    use crate::kinds::*;

    /// Combines two primary colors in equal amounts to create
    /// a secondary color.
    pub fn mix(c1: PrimaryColor, c2: PrimaryColor) -> SecondaryColor {
        SecondaryColor::Orange
    }
}
```

### Listing 14-6 — User code after re-exports (simple `use` paths)

```rust
use art::PrimaryColor;
use art::mix;

fn main() {
    let red = PrimaryColor::Red;
    let yellow = PrimaryColor::Yellow;
    mix(red, yellow);
}
```

The re-exported items now appear at the top of the generated documentation under "Re-exports", making the API discoverable without users needing to know the internal structure.

## 4. Setting Up a Crates.io Account

1. Create an account at [crates.io](https://crates.io) using GitHub authentication.
2. Visit account settings at `https://crates.io/me/` to get your API token.
3. Run `cargo login` and paste your token:

```
$ cargo login
abcdefghijklmnopqrstuvwxyz012345
```

This stores the token in `~/.cargo/credentials`. **Keep it secret — do not share it.**

## 5. Adding Required Metadata to `Cargo.toml`

Crate names on crates.io are allocated **first-come, first-served**. Before publishing, search for your desired name. At minimum, `description` and `license` are required fields.

### Minimal required metadata

```toml
[package]
name = "guessing_game"
version = "0.1.0"
edition = "2024"
description = "A fun game where you guess what number the computer has chosen."
license = "MIT OR Apache-2.0"

[dependencies]
```

- `description`: A short explanation of what the crate does. Appears in search results.
- `license`: Must be a valid [SPDX identifier](https://spdx.org/licenses/). Multiple licenses can be combined with `OR` (e.g., `"MIT OR Apache-2.0"`). For custom licenses, use `license-file` instead.

> Many Rust projects use `"MIT OR Apache-2.0"` — the same dual license as Rust itself.

Running `cargo publish` without these fields produces an error:

```
error: missing or empty metadata fields: description, license.
```

## 6. Publishing to Crates.io

```
$ cargo publish
    Updating crates.io index
   Packaging guessing_game v0.1.0 (file:///projects/guessing_game)
   Verifying guessing_game v0.1.0 (file:///projects/guessing_game)
   Compiling guessing_game v0.1.0
(file:///projects/guessing_game/target/package/guessing_game-0.1.0)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.19s
   Uploading guessing_game v0.1.0 (file:///projects/guessing_game)
```

> **Warning**: Publishing is **permanent**. A version can never be overwritten and code cannot be deleted. Crates.io acts as a permanent archive. If you accidentally upload secrets, reset them immediately — yanking a version does not remove the code.

---

## 7. Publishing New Versions

To release a new version:

1. Update the `version` field in `Cargo.toml` following [Semantic Versioning](https://semver.org/) rules.
2. Run `cargo publish` again.

```toml
[package]
version = "0.2.0"
```

---

## 8. Deprecating Versions with `cargo yank`

Yanking a version prevents **new** projects from adding it as a dependency, while existing projects with a `Cargo.lock` pinned to that version continue to work.

### Yank a version

```
$ cargo yank --vers 1.0.1
    Updating crates.io index
        Yank guessing_game@1.0.1
```

### Undo a yank

```
$ cargo yank --vers 1.0.1 --undo
    Updating crates.io index
      Unyank guessing_game@1.0.1
```

> A yank does **not** delete code. It only prevents new `Cargo.lock` files from resolving to that version.

## Key Takeaways

| Topic              | Key Point                                                                 |
|--------------------|---------------------------------------------------------------------------|
| `///` comments     | Generate HTML docs; code examples in them are run as tests by `cargo test`|
| `//!` comments     | Document the crate/module itself, not the item below                      |
| `pub use`          | Re-export items to a flatter, more user-friendly API path                 |
| Required metadata  | `description` and `license` are mandatory before `cargo publish`          |
| Publishing         | Permanent — versions cannot be deleted or overwritten                     |
| Versioning         | Follow Semantic Versioning; bump `version` in `Cargo.toml` for each release|
| `cargo yank`       | Prevents new dependents; existing pinned projects are unaffected          |

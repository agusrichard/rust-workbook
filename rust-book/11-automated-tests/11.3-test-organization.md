# 11.3 - Test Organization

## Overview

Rust recognizes two primary categories of tests: **unit tests** and **integration tests**. Unit tests are small and focused, testing one module in isolation and can access private interfaces. Integration tests are entirely external to the library and exercise only the public API, just like any external consumer would.

---

## Unit Tests

Unit tests live in the `src` directory alongside the code they test. The convention is to create a `tests` module annotated with `#[cfg(test)]`.

### The `#[cfg(test)]` Annotation

This tells Rust to compile and run the test code only when executing `cargo test`, excluding it from regular builds to improve compile time and reduce artifact size.

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn it_works() {
        let result = add(2, 2);
        assert_eq!(result, 4);
    }
}
```

### Testing Private Functions

Rust allows testing private functions. Because the `tests` module is a child of the module under test, it can access private items via `use super::*`:

```rust
fn internal_adder(left: usize, right: usize) -> usize {
    left + right
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn internal() {
        let result = internal_adder(2, 2);
        assert_eq!(result, 4);
    }
}
```

---

## Integration Tests

Integration tests live in a separate `tests/` directory at the project root, next to `src/`. Each file in `tests/` compiles as an independent crate, so no `#[cfg(test)]` annotation is needed.

### Directory Structure

```
adder/
├── Cargo.toml
├── src/
│   └── lib.rs
└── tests/
    └── integration_test.rs
```

### Writing an Integration Test

The library must be imported explicitly since the test file is a separate crate:

```rust
use adder::add_two;

#[test]
fn it_adds_two() {
    let result = add_two(2);
    assert_eq!(result, 4);
}
```

Run a specific integration test file:

```bash
cargo test --test integration_test
```

### Sharing Helpers Across Integration Test Files

To share helper code across multiple test files without Cargo treating it as its own test suite, use the `tests/common/mod.rs` convention:

```
tests/
├── common/
│   └── mod.rs
└── integration_test.rs
```

Then import it in test files:

```rust
mod common;

#[test]
fn it_adds_two() {
    common::setup();
    // ...
}
```

---

## Binary Crate Limitations

Projects with only `src/main.rs` (binary crates) **cannot** have integration tests, because integration tests can only import library crates.

**Solution:** Move logic into `src/lib.rs` and call it from `main.rs`. This allows integration tests to exercise the library, while `main.rs` stays as a thin entry point.

---

## Test Output Structure

Running `cargo test` produces three sections of output:

1. **Unit tests** — from `src/`
2. **Integration tests** — one section per file in `tests/`
3. **Doc-tests** — from documentation examples

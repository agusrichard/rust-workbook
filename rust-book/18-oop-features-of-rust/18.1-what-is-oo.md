# 18.1 - Characteristics of Object-Oriented Languages

## Overview

This section examines whether Rust qualifies as an object-oriented language by analyzing three core OOP characteristics: objects (data + behavior), encapsulation, and inheritance/polymorphism. The conclusion is that Rust satisfies the spirit of OOP while taking its own approach, particularly around inheritance.

---

## Key Points

### 1. Objects Contain Data and Behavior

The Gang of Four's *Design Patterns* book defines an **object** as something that "packages both data and the procedures that operate on that data."

Rust satisfies this through **structs and enums** combined with **`impl` blocks**:
- Structs/enums hold data
- `impl` blocks define methods (behavior) on that data

This is functionally equivalent to objects in traditional OOP languages, just with different terminology.

---

### 2. Encapsulation That Hides Implementation Details

Rust supports encapsulation via the `pub` keyword, which controls visibility of modules, types, functions, and methods. By default, everything is **private**.

**Example — `AveragedCollection`:**

```rust
pub struct AveragedCollection {
    list: Vec<i32>,
    average: f64,
}

impl AveragedCollection {
    pub fn add(&mut self, value: i32) {
        self.list.push(value);
        self.update_average();
    }

    pub fn remove(&mut self) -> Option<i32> {
        let result = self.list.pop();
        match result {
            Some(value) => {
                self.update_average();
                Some(value)
            }
            None => None,
        }
    }

    pub fn average(&self) -> f64 {
        self.average
    }

    fn update_average(&mut self) {
        let total: i32 = self.list.iter().sum();
        self.average = total as f64 / self.list.len() as f64;
    }
}
```

**What this demonstrates:**
- `list` and `average` fields are **private** — external code cannot access or mutate them directly
- `add`, `remove`, and `average` are the **public API**
- `update_average` is private — an internal implementation detail
- If the internal data structure changes (e.g., `Vec<i32>` → `HashSet<i32>`), the public API remains unchanged, so callers are unaffected

This is classic encapsulation: hide the *how*, expose the *what*.

---

### 3. Inheritance as a Type System and Code Sharing

Rust has **no traditional inheritance**. There is no mechanism for a struct to inherit fields and method implementations from a parent struct (without macros).

#### Code Reuse

Traditional OOP uses inheritance for code reuse. Rust achieves this through **default trait method implementations**:

```rust
pub trait Summary {
    fn summarize(&self) -> String {
        String::from("(Read more...)")
    }
}
```

Any type implementing `Summary` gets `summarize` for free unless it overrides it. This provides reuse without inheritance hierarchies.

#### Polymorphism

Traditional OOP uses inheritance for polymorphism (using a subtype where a parent type is expected). Rust uses:

- **Generics with trait bounds** — compile-time (static) polymorphism
- **Trait objects** (`dyn Trait`) — runtime (dynamic) polymorphism

---

## Why Rust Avoids Inheritance

The book notes two key problems with traditional inheritance:

1. **Forced characteristic sharing**: subclasses inherit *everything* from the parent, even things that don't apply to them, risking incorrect behavior
2. **Single-inheritance limitations**: many languages only allow inheriting from one parent, which constrains design

Rust's trait system is more flexible — a type can implement many traits, and trait objects allow runtime polymorphism without locking into a hierarchy.

---

## Concept Diagram

```
Traditional OOP                    Rust Equivalent
─────────────────────────────────────────────────
Class (data + methods)        →    struct/enum + impl block
Access modifiers (private)    →    pub / private (default)
Inheritance (code reuse)      →    Default trait implementations
Inheritance (polymorphism)    →    Generics + trait bounds / trait objects
```

---

## Conclusions

- Rust **is** object-oriented by the most fundamental definition (objects = data + behavior)
- Rust **does** support encapsulation through its visibility system
- Rust **does not** have inheritance, but provides superior alternatives:
  - Default trait methods for code reuse
  - Generics and trait objects for polymorphism
- The next sections explore how to use **trait objects** to achieve runtime polymorphism in idiomatic Rust

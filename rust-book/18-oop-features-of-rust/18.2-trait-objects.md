# 18.2 - Using Trait Objects to Abstract over Shared Behavior

## Overview

Trait objects let you write code that works with values of different concrete types at runtime, as long as those types all implement a shared trait. This enables heterogeneous collections and extensible library designs — the key tool in Rust for achieving one aspect of polymorphism found in OOP languages.

---

## The Problem

A `Vec<T>` can only hold one concrete type. But sometimes you want a collection of different types that share common behavior — for example, a GUI library that can render `Button`, `SelectBox`, `Image`, and any user-defined widget through one unified interface.

---

## Defining a Trait

```rust
pub trait Draw {
    fn draw(&self);
}
```

---

## Trait Objects: `Box<dyn Trait>`

A **trait object** is created by combining a pointer (`&` or `Box<T>`) with the `dyn` keyword. It holds:
1. A pointer to the concrete value.
2. A vtable (virtual method table) for runtime method lookup.

```rust
pub struct Screen {
    pub components: Vec<Box<dyn Draw>>,
}

impl Screen {
    pub fn run(&self) {
        for component in self.components.iter() {
            component.draw();
        }
    }
}
```

`Vec<Box<dyn Draw>>` can hold any mix of types — `Button`, `SelectBox`, or anything else — as long as they implement `Draw`.

---

## Trait Objects vs. Generics

A generic version looks similar but behaves differently:

```rust
pub struct Screen<T: Draw> {
    pub components: Vec<T>,
}

impl<T> Screen<T>
where
    T: Draw,
{
    pub fn run(&self) {
        for component in self.components.iter() {
            component.draw();
        }
    }
}
```

| | Trait Objects (`dyn Draw`) | Generics (`T: Draw`) |
|---|---|---|
| Collection contents | Multiple different types | Only one concrete type per instance |
| Dispatch | **Dynamic** (runtime vtable lookup) | **Static** (monomorphization at compile time) |
| Flexibility | High — open to new types | Lower — type fixed at instantiation |
| Performance | Slight runtime overhead, no inlining | Faster, compiler can inline and optimize |

Use generics when all items in a collection will be the same type. Use trait objects when you need a heterogeneous mix.

---

## Implementing the Trait: Library Side

```rust
pub struct Button {
    pub width: u32,
    pub height: u32,
    pub label: String,
}

impl Draw for Button {
    fn draw(&self) {
        // code to actually draw a button
    }
}
```

---

## Implementing the Trait: User Side (Extensibility)

Library users can define their own types and plug them into `Screen` without modifying the library:

```rust
use gui::Draw;

struct SelectBox {
    width: u32,
    height: u32,
    options: Vec<String>,
}

impl Draw for SelectBox {
    fn draw(&self) {
        // code to actually draw a select box
    }
}
```

---

## Using Mixed Types at Runtime

```rust
use gui::{Button, Screen};

fn main() {
    let screen = Screen {
        components: vec![
            Box::new(SelectBox {
                width: 75,
                height: 10,
                options: vec![
                    String::from("Yes"),
                    String::from("Maybe"),
                    String::from("No"),
                ],
            }),
            Box::new(Button {
                width: 50,
                height: 10,
                label: String::from("OK"),
            }),
        ],
    };

    screen.run();
}
```

Both `SelectBox` and `Button` live in the same `Vec<Box<dyn Draw>>`. Rust resolves which `draw` to call at runtime.

---

## Type Annotations for Trait Object Vectors

When factoring the `vec!` into a separate variable, Rust's type inference needs help:

```rust
// Option 1: annotate the variable type
let components: Vec<Box<dyn Draw>> = vec![
    Box::new(SelectBox { /* .. */ }),
    Box::new(Button { /* .. */ }),
];

// Option 2: cast the first element
let components = vec![
    Box::new(SelectBox { /* .. */ }) as Box<dyn Draw>,
    Box::new(Button { /* .. */ }),
];
```

---

## Compile-Time Safety

If a type doesn't implement `Draw`, the compiler rejects it immediately:

```
error[E0277]: the trait bound `String: Draw` is not satisfied
```

This is Rust's answer to duck typing from dynamic languages: you get the same flexibility ("if it implements `Draw`, it can go in the list") but with compile-time guarantees rather than runtime surprises.

---

## Dynamic Dispatch and Performance

- **Dynamic dispatch**: Rust follows a pointer at runtime to find the correct method in the vtable.
- This prevents the compiler from inlining calls and performing some optimizations.
- Trade-off: flexibility and extensibility at the cost of a small runtime overhead.
- For performance-critical paths, prefer generics (static dispatch). For extensible APIs, prefer trait objects.

---

## Key Takeaways

- Use `Box<dyn Trait>` (or `&dyn Trait`) to store heterogeneous types in a single collection.
- Trait objects enable **open extensibility**: library users can add new types without touching library code.
- Rust enforces trait implementation at compile time, avoiding the runtime errors of duck typing in dynamic languages.
- Generics are faster (static dispatch); trait objects are more flexible (dynamic dispatch). Choose based on your needs.

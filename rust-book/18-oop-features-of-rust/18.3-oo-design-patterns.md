# 18.3 - Implementing an Object-Oriented Design Pattern

## High-Level Overview

This chapter demonstrates how to implement the classic **state pattern** (an OOP design pattern) in Rust, using a blog post workflow as the example. It then contrasts the traditional OOP approach with a more idiomatic Rust approach that encodes state into the type system, exploring the trade-offs between the two.

---

## The Blog Post Workflow

The system has three states a post can move through:

```
[Draft] --request_review()--> [PendingReview] --approve()--> [Published]
```

Rules:
- `content()` returns `""` unless the post is **Published**.
- State transitions are one-way and ordered.
- The caller (e.g., `main.rs`) should not need to manage state logic.

---

## Approach 1: Traditional OOP State Pattern

### Concept

State-specific behavior is encapsulated in separate structs (`Draft`, `PendingReview`, `Published`), all implementing a `State` trait. The `Post` holds a `Box<dyn State>` and delegates behavior to it.

### State Transition Diagram

```
Post.state = Some(Box<Draft>)
    |
    | request_review()
    v
Post.state = Some(Box<PendingReview>)
    |
    | approve()
    v
Post.state = Some(Box<Published>)
    |
    | content() -> &post.content (via trait delegation)
```

### Key Design Choices

- **`self: Box<Self>`** in trait methods — ensures the method consumes the boxed state, forcing a transition and preventing reuse.
- **`Option<Box<dyn State>>`** — uses `take()` to temporarily move the state out, allowing mutation and transition.
- **Default `content()` in trait** — returns `""` by default; only `Published` overrides it to return the real content.

---

### Code: Usage (Listing 18-11)

```rust
use blog::Post;

fn main() {
    let mut post = Post::new();

    post.add_text("I ate a salad for lunch today");
    assert_eq!("", post.content());

    post.request_review();
    assert_eq!("", post.content());

    post.approve();
    assert_eq!("I ate a salad for lunch today", post.content());
}
```

### Code: Post + State Trait (Listing 18-12 → 18-18, final consolidated version)

```rust
pub struct Post {
    state: Option<Box<dyn State>>,
    content: String,
}

impl Post {
    pub fn new() -> Post {
        Post {
            state: Some(Box::new(Draft {})),
            content: String::new(),
        }
    }

    pub fn add_text(&mut self, text: &str) {
        self.content.push_str(text);
    }

    pub fn content(&self) -> &str {
        self.state.as_ref().unwrap().content(self)
    }

    pub fn request_review(&mut self) {
        if let Some(s) = self.state.take() {
            self.state = Some(s.request_review())
        }
    }

    pub fn approve(&mut self) {
        if let Some(s) = self.state.take() {
            self.state = Some(s.approve())
        }
    }
}

trait State {
    fn request_review(self: Box<Self>) -> Box<dyn State>;
    fn approve(self: Box<Self>) -> Box<dyn State>;

    fn content<'a>(&self, post: &'a Post) -> &'a str {
        ""
    }
}

struct Draft {}

impl State for Draft {
    fn request_review(self: Box<Self>) -> Box<dyn State> {
        Box::new(PendingReview {})
    }

    fn approve(self: Box<Self>) -> Box<dyn State> {
        self
    }
}

struct PendingReview {}

impl State for PendingReview {
    fn request_review(self: Box<Self>) -> Box<dyn State> {
        self
    }

    fn approve(self: Box<Self>) -> Box<dyn State> {
        Box::new(Published {})
    }
}

struct Published {}

impl State for Published {
    fn request_review(self: Box<Self>) -> Box<dyn State> {
        self
    }

    fn approve(self: Box<Self>) -> Box<dyn State> {
        self
    }

    fn content<'a>(&self, post: &'a Post) -> &'a str {
        &post.content
    }
}
```

### Notable Points

- `Post::content()` calls `self.state.as_ref().unwrap().content(self)` — it delegates to the current state, passing itself as context.
- The lifetime `'a` in `fn content<'a>(&self, post: &'a Post) -> &'a str` ties the returned string slice to the `Post`'s lifetime, not the state's.
- `approve()` on `Draft` returns `self` — a draft cannot be approved directly, it must go through review first.

## Approach 2: Rust-Idiomatic Type-Encoding

### Concept

Instead of runtime state stored in a field, each state is a **distinct type**. Invalid operations (e.g., calling `content()` on a draft) become **compile-time errors** because those methods simply don't exist on the wrong type.

### State Transition Diagram

```
DraftPost
    |
    | .request_review() -> consumes self, returns PendingReviewPost
    v
PendingReviewPost
    |
    | .approve() -> consumes self, returns Post
    v
Post  (the only type with .content())
```

### Code: Type-Based Library (Listing 18-19 + 18-20)

```rust
pub struct Post {
    content: String,
}

pub struct DraftPost {
    content: String,
}

impl Post {
    pub fn new() -> DraftPost {
        DraftPost {
            content: String::new(),
        }
    }

    pub fn content(&self) -> &str {
        &self.content
    }
}

impl DraftPost {
    pub fn add_text(&mut self, text: &str) {
        self.content.push_str(text);
    }

    pub fn request_review(self) -> PendingReviewPost {
        PendingReviewPost {
            content: self.content,
        }
    }
}

pub struct PendingReviewPost {
    content: String,
}

impl PendingReviewPost {
    pub fn approve(self) -> Post {
        Post {
            content: self.content,
        }
    }
}
```

### Code: Updated Usage (Listing 18-21)

```rust
use blog::Post;

fn main() {
    let mut post = Post::new();

    post.add_text("I ate a salad for lunch today");

    let post = post.request_review();

    let post = post.approve();

    assert_eq!("I ate a salad for lunch today", post.content());
}
```

Note the **variable shadowing** pattern (`let post = post.request_review()`). Each `let post =` rebinds the variable to the new type after a state transition.

## Trade-off Comparison

| Aspect | Trait Object (OOP) Approach | Type-Encoding (Idiomatic Rust) |
|---|---|---|
| State representation | `Box<dyn State>` field at runtime | Separate types at compile time |
| Invalid state prevention | Runtime (logic in state impls) | Compile-time (missing methods) |
| API surface | Single `Post` type for callers | Different types per state |
| Adding a new state | Add a new struct + impl `State` | Add a new struct, update transition methods |
| Encapsulation | Higher — callers see only `Post` | Lower — callers see `DraftPost`, `PendingReviewPost` |
| Logic duplication | Possible (e.g., `request_review` on `PendingReview` returns `self`) | Less — no-op transitions simply don't exist |
| Variable shadowing needed | No | Yes (common Rust pattern) |

---

## Key Concepts

### `self: Box<Self>` receiver
Methods with this signature can only be called on a `Box<T>`. Calling it moves ownership of the box, consuming it. This is the mechanism that enforces "a state transition replaces the old state."

### `Option::take()`
```rust
if let Some(s) = self.state.take() {
    self.state = Some(s.request_review())
}
```
`take()` replaces `self.state` with `None` and returns the old value. This allows moving the state value out of a `&mut self` context — required because you can't move out of a field while the struct is borrowed mutably.

### Lifetime in trait method
```rust
fn content<'a>(&self, post: &'a Post) -> &'a str
```
The returned `&str` borrows from `post`, not from `self`. Without the explicit lifetime, the compiler can't determine this relationship.

### Type-State Pattern
The type-encoding approach is an instance of the **typestate pattern** — encoding object state into the type system so that invalid sequences of operations are rejected at compile time.

---

## Conclusions

- Rust **can** implement OOP patterns like the state pattern, but doing so directly often gives up Rust's key strengths.
- The **type-encoding approach** encodes rules at the type level, making illegal states unrepresentable — a stronger guarantee than runtime checks.
- Neither approach is universally better; the right choice depends on whether compile-time safety or API ergonomics (single type for callers) is more valuable in context.
- The chapter's core lesson: **translate the problem into Rust's strengths** rather than mapping OOP patterns directly.

# 10.3 - Validating References with Lifetimes

## High-Level Overview

Lifetimes are Rust's mechanism for ensuring that references remain valid for as long as they are used. They are a form of generic that, rather than ensuring a type has a certain behavior, ensure that references are valid for the duration they are needed. While most lifetimes are inferred automatically by the compiler (similar to type inference), there are cases where the programmer must annotate lifetimes explicitly to help the borrow checker understand the relationships between references.

---

## Key Concepts

### 1. Preventing Dangling References

The primary goal of lifetimes is to prevent **dangling references** — references that point to data that has already been freed.

```rust
fn main() {
    let r;
    {
        let x = 5;
        r = &x;  // ERROR: `x` does not live long enough
    }
    println!("r: {}", r);
}
```

Here, `x` goes out of scope before `r` is used, so the compiler rejects this code.

### 2. The Borrow Checker

Rust's **borrow checker** compares scopes to determine if all borrows are valid. It annotates variables with their lifetimes and checks that references don't outlive the data they point to.

```rust
fn main() {
    let x = 5;            // ----------+-- 'b
    let r = &x;           // --+-- 'a  |
    println!("r: {}", r); //   |       |
                          // --+       |
}                         // ----------+
```

In this valid example, `'b` (lifetime of `x`) is longer than `'a` (lifetime of `r`), so the reference is valid.

---

## Lifetime Annotation Syntax

Lifetime annotations describe the relationships between the lifetimes of multiple references. They don't change how long references live — they just inform the compiler of the relationships.

- Syntax: lifetime names start with `'` and are usually short lowercase letters (e.g., `'a`)
- Placed after `&` in reference types

```rust
&i32         // a reference
&'a i32      // a reference with explicit lifetime
&'a mut i32  // a mutable reference with explicit lifetime
```

---

## Lifetime Annotations in Function Signatures

When a function takes or returns references, lifetime annotations are needed when the compiler can't infer how input and output lifetimes relate.

### The `longest` Function Problem

```rust
// This won't compile — the compiler can't determine if the return value
// refers to x or y, so it doesn't know which lifetime to use
fn longest(x: &str, y: &str) -> &str {
    if x.len() > y.len() { x } else { y }
}
```

### Correct Version with Lifetime Annotation

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

This tells the compiler: "the returned reference will be valid for at least as long as `'a`", where `'a` is the **shorter** of the two input lifetimes.

### Usage Example

```rust
fn main() {
    let string1 = String::from("long string is long");
    let result;
    {
        let string2 = String::from("xyz");
        result = longest(string1.as_str(), string2.as_str());
        println!("The longest string is: {}", result);
    }
}
```

But this fails because `result` might hold a reference to `string2` which goes out of scope:

```rust
fn main() {
    let string1 = String::from("long string is long");
    let result;
    {
        let string2 = String::from("xyz");
        result = longest(string1.as_str(), string2.as_str());
        // string2 dropped here
    }
    println!("The longest string is: {}", result); // ERROR
}
```

---

## Thinking in Terms of Lifetimes

Lifetime annotations describe *constraints*, not *durations*. When a function always returns the first argument, only that parameter needs to share a lifetime with the return value:

```rust
fn first_arg<'a>(x: &'a str, y: &str) -> &'a str {
    x
}
```

If the return type is not a reference (e.g., a `String`), no lifetime annotation is needed on outputs.

---

## Lifetime Annotations in Struct Definitions

Structs that hold references must annotate those references with lifetimes:

```rust
struct ImportantExcerpt<'a> {
    part: &'a str,
}

fn main() {
    let novel = String::from("Call me Ishmael. Some years ago...");
    let first_sentence = novel.split('.').next().expect("Could not find a '.'");
    let i = ImportantExcerpt { part: first_sentence };
}
```

This ensures the struct cannot outlive the reference it holds.

---

## Lifetime Elision Rules

The compiler applies **lifetime elision rules** to reduce the need for explicit annotations in common patterns. These rules apply to `fn` and `impl` blocks.

**Definitions:**
- *Input lifetimes*: lifetimes on function parameters
- *Output lifetimes*: lifetimes on return values

**Three rules the compiler applies:**

1. Each reference parameter gets its own lifetime parameter.
   - `fn foo(x: &i32)` → `fn foo<'a>(x: &'a i32)`
   - `fn foo(x: &i32, y: &i32)` → `fn foo<'a, 'b>(x: &'a i32, y: &'b i32)`

2. If there is exactly one input lifetime, it is assigned to all output lifetimes.
   - `fn foo<'a>(x: &'a i32) -> &i32` → `fn foo<'a>(x: &'a i32) -> &'a i32`

3. If one of the inputs is `&self` or `&mut self`, its lifetime is assigned to all output lifetimes.

If after applying these rules, output lifetimes are still ambiguous, the compiler will error.

---

## Lifetime Annotations in Method Definitions

For methods on structs with lifetime parameters:

```rust
impl<'a> ImportantExcerpt<'a> {
    fn level(&self) -> i32 {
        3
    }

    fn announce_and_return_part(&self, announcement: &str) -> &str {
        println!("Attention: {}", announcement);
        self.part
    }
}
```

The third elision rule applies in `announce_and_return_part`, so no explicit lifetime annotation is needed on the return value.

---

## The Static Lifetime

`'static` is a special lifetime meaning the reference can live for the entire duration of the program.

```rust
let s: &'static str = "I have a static lifetime.";
```

String literals are stored in the binary and always have the `'static` lifetime.

> **Note**: Before using `'static`, consider whether the reference truly needs to live for the entire program. It's often a sign that you should fix a dangling reference rather than extend the lifetime.

---

## Combining Generic Type Parameters, Trait Bounds, and Lifetimes

All three can be used together in a single function signature:

```rust
use std::fmt::Display;

fn longest_with_an_announcement<'a, T>(
    x: &'a str,
    y: &'a str,
    ann: T,
) -> &'a str
where
    T: Display,
{
    println!("Announcement! {}", ann);
    if x.len() > y.len() { x } else { y }
}
```

---

## Summary

- Every reference in Rust has a **lifetime** — the scope for which the reference is valid.
- **Lifetime annotations** (e.g., `'a`) describe relationships between reference lifetimes; they don't change actual lifetimes.
- The **borrow checker** uses lifetimes to ensure no dangling references exist at compile time.
- **Lifetime elision rules** allow many common patterns to omit explicit annotations.
- Structs that hold references require lifetime annotations to ensure they don't outlive their data.
- `'static` is the special lifetime for references that live for the entire program execution.
- Lifetimes, generics, and trait bounds can all be combined in a single function signature.

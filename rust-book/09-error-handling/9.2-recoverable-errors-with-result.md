# 9.2 - Recoverable Errors with `Result`

## Overview

Not every error warrants stopping the program. Rust's `Result<T, E>` enum provides a way to handle recoverable errors — failures that the calling code can inspect and respond to. This section covers the full spectrum of working with `Result`: from basic `match` handling, to shortcuts like `unwrap`/`expect`, to propagating errors with the `?` operator.

---

## The `Result` Enum

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

- `Ok(T)` — holds the success value of type `T`
- `Err(E)` — holds the error value of type `E`

Both variants are in the prelude, so no `Result::` prefix is needed.

---

## Basic Handling with `match`

```rust
use std::fs::File;

fn main() {
    let greeting_file_result = File::open("hello.txt");

    let greeting_file = match greeting_file_result {
        Ok(file) => file,
        Err(error) => panic!("Problem opening the file: {error:?}"),
    };
}
```

`File::open` returns `Result<std::fs::File, std::io::Error>`.

---

## Matching on Specific Error Kinds

Use `error.kind()` to distinguish between error variants and take different actions:

```rust
use std::fs::File;
use std::io::ErrorKind;

fn main() {
    let greeting_file_result = File::open("hello.txt");

    let greeting_file = match greeting_file_result {
        Ok(file) => file,
        Err(error) => match error.kind() {
            ErrorKind::NotFound => match File::create("hello.txt") {
                Ok(fc) => fc,
                Err(e) => panic!("Problem creating the file: {e:?}"),
            },
            other_error => {
                panic!("Problem opening the file: {other_error:?}");
            }
        },
    };
}
```

### Cleaner Alternative with `unwrap_or_else`

```rust
use std::fs::File;
use std::io::ErrorKind;

fn main() {
    let greeting_file = File::open("hello.txt").unwrap_or_else(|error| {
        if error.kind() == ErrorKind::NotFound {
            File::create("hello.txt").unwrap_or_else(|error| {
                panic!("Problem creating the file: {error:?}");
            })
        } else {
            panic!("Problem opening the file: {error:?}");
        }
    });
}
```

---

## Shortcuts: `unwrap` and `expect`

### `unwrap`

Returns the inner value on `Ok`, panics with a default message on `Err`:

```rust
let greeting_file = File::open("hello.txt").unwrap();
```

### `expect`

Same as `unwrap` but with a custom panic message — preferred in production code:

```rust
let greeting_file = File::open("hello.txt")
    .expect("hello.txt should be included in this project");
```

> Most Rustaceans prefer `expect` over `unwrap` because it makes the intent clear and the panic easier to diagnose.

---

## Propagating Errors

Instead of handling an error inside a function, you can return it to the caller:

```rust
use std::fs::File;
use std::io::{self, Read};

fn read_username_from_file() -> Result<String, io::Error> {
    let username_file_result = File::open("hello.txt");

    let mut username_file = match username_file_result {
        Ok(file) => file,
        Err(e) => return Err(e),
    };

    let mut username = String::new();

    match username_file.read_to_string(&mut username) {
        Ok(_) => Ok(username),
        Err(e) => Err(e),
    }
}
```

The return type `Result<String, io::Error>` signals to callers that they need to handle either outcome.

---

## The `?` Operator

The `?` operator is shorthand for error propagation. On `Ok`, it unwraps the value; on `Err`, it returns the error early from the function (after running it through `From::from` for type conversion).

```rust
use std::fs::File;
use std::io::{self, Read};

fn read_username_from_file() -> Result<String, io::Error> {
    let mut username_file = File::open("hello.txt")?;
    let mut username = String::new();
    username_file.read_to_string(&mut username)?;
    Ok(username)
}
```

### Chaining `?`

```rust
fn read_username_from_file() -> Result<String, io::Error> {
    let mut username = String::new();
    File::open("hello.txt")?.read_to_string(&mut username)?;
    Ok(username)
}
```

### Even Shorter with `fs::read_to_string`

```rust
use std::fs;
use std::io;

fn read_username_from_file() -> Result<String, io::Error> {
    fs::read_to_string("hello.txt")
}
```

### Type Conversion via `From`

The `?` operator calls `From::from` on the error, converting it to the function's declared error return type. This allows a function to return a single error type even when its internals can fail in multiple ways.

---

## Where `?` Can Be Used

`?` can only be used in functions that return `Result` or `Option` (or another type implementing `FromResidual`). Mixing `Result` and `Option` with `?` in the same function is not allowed.

### `?` on `Option`

```rust
fn first_char(s: &str) -> Option<char> {
    s.chars().next()
}
```

If the value is `None`, `?` returns `None` early; if `Some`, it unwraps the inner value.

### `main` Can Return `Result`

```rust
use std::error::Error;
use std::fs::File;

fn main() -> Result<(), Box<dyn Error>> {
    let greeting_file = File::open("hello.txt")?;
    Ok(())
}
```

- `Box<dyn Error>` means "any kind of error" (a trait object).
- Exits with code `0` on `Ok(())`, non-zero on `Err`.
- Any type implementing `std::process::Termination` can be returned from `main`.

---

## Key Takeaways

- Use `Result<T, E>` for errors that callers should be able to handle.
- Use `match` for full control; `unwrap_or_else` for cleaner closure-based handling.
- Prefer `expect` over `unwrap` in real code — custom messages aid debugging.
- Propagate errors up the call stack with the `?` operator for concise, idiomatic code.
- `?` performs automatic type conversion via the `From` trait.
- `?` requires the function return type to be `Result` or `Option`; `main` can return `Result<(), Box<dyn Error>>`.

# 9.1 - Unrecoverable Errors with `panic!`

## Overview

When something goes catastrophically wrong and there's nothing your code can do to recover, Rust provides the `panic!` macro. A panic prints a failure message, cleans up the stack (or aborts), and exits the program. This section covers how panics work, how to trigger them, and how to use backtraces to diagnose them.

---

## How Panics Are Triggered

There are two ways a panic occurs:

1. **Implicitly** — by performing an invalid operation (e.g., accessing a vector out of bounds).
2. **Explicitly** — by calling the `panic!` macro directly.

---

## Unwinding vs. Aborting

By default, when a panic occurs, Rust **unwinds** the stack — walking back up each frame and cleaning up data. This is safe but expensive in binary size.

The alternative is **aborting**: the program ends immediately and the OS cleans up memory. To enable abort-on-panic for release builds, add to `Cargo.toml`:

```toml
[profile.release]
panic = 'abort'
```

---

## Explicit `panic!`

```rust
fn main() {
    panic!("crash and burn");
}
```

Output:

```
thread 'main' panicked at src/main.rs:2:5:
crash and burn
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

The error message includes the file and line/column where the panic occurred (`src/main.rs:2:5`).

---

## Implicit Panic — Out-of-Bounds Access (Listing 9-1)

```rust
fn main() {
    let v = vec![1, 2, 3];

    v[99]; // vector has only 3 elements
}
```

Output:

```
thread 'main' panicked at src/main.rs:4:6:
index out of bounds: the len is 3 but the index is 99
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

In C, this would be **undefined behavior** — a "buffer overread" that can expose arbitrary memory and create security vulnerabilities. Rust instead halts execution immediately, preventing such exploits.

---

## Using `RUST_BACKTRACE` (Listing 9-2)

Set `RUST_BACKTRACE=1` to see the full call stack at the point of panic:

```
$ RUST_BACKTRACE=1 cargo run
thread 'main' panicked at src/main.rs:4:6:
index out of bounds: the len is 3 but the index is 99
stack backtrace:
   0: rust_begin_unwind
   1: core::panicking::panic_fmt
   2: core::panicking::panic_bounds_check
   3: <usize as core::slice::index::SliceIndex<[T]>>::index
   4: core::slice::index::<impl core::ops::index::Index<I> for [T]>::index
   5: <alloc::vec::Vec<T,A> as core::ops::index::Index<I>>::index
   6: panic::main
             at ./src/main.rs:4:6
   7: core::ops::function::FnOnce::call_once
```

### How to read a backtrace:
- Start from the **top** and scan down until you see **your own files**.
- That's where the problem originated.
- Lines above are code your code called; lines below are code that called your code.
- Use `RUST_BACKTRACE=full` for even more verbose output.

> **Note:** Debug symbols must be enabled for backtraces to be meaningful. They are on by default with `cargo build` / `cargo run` (without `--release`).

---

## Key Takeaways

- `panic!` is for **unrecoverable** errors — situations where continuing is impossible or dangerous.
- Rust panics instead of allowing undefined behavior like buffer overreads.
- Use `RUST_BACKTRACE=1` to get a call stack when diagnosing a panic.
- You can configure release builds to **abort** instead of unwind for smaller binaries.
- Panics are not always in your code — use the backtrace to find the first frame pointing to your own files.

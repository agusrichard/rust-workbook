# 13.4 - Comparing Performance: Loops vs. Iterators

## High-Level Overview

This chapter addresses a common concern: *are iterator abstractions slower than hand-written loops?* The answer is no. Rust's compiler optimizes iterator-based code to produce the same (or better) machine code as equivalent imperative loops. This property is called **zero-cost abstractions**.

---

## Benchmark: Loop vs. Iterator

The book benchmarks two implementations of the `search` function from `minigrep` against the text of *The Adventures of Sherlock Holmes*:

The raw benchmark output from the book:

```
test bench_search_for  ... bench:  19,620,300 ns/iter (+/- 915,700)
test bench_search_iter ... bench:  19,234,900 ns/iter (+/- 657,200)
```

| Implementation  | Time (ns/iter) | Variance      |
|-----------------|----------------|---------------|
| `for` loop      | 19,620,300     | ±915,700      |
| Iterator chain  | 19,234,900     | ±657,200      |

The iterator version is **slightly faster** in this benchmark. Both are effectively equivalent — the difference is within noise.

---

## Zero-Cost Abstractions

Rust's design philosophy, borrowed from C++, is captured in this principle by **Bjarne Stroustrup**:

> *"What you don't use, you don't pay for. And further: What you do use, you couldn't hand code any better."*

This means:
- High-level constructs like `map`, `filter`, `zip`, and `sum` compile down to machine code equivalent to the lowest-level manual implementation.
- You get expressiveness and readability **for free** — no runtime penalty.

## Real-World Example: Audio Decoder

The book shows an audio decoder snippet that uses an iterator chain with mathematical operations:

```rust
let buffer: &mut [i32];
let coefficients: [i64; 12];
let qlp_shift: i16;

for i in 12..buffer.len() {
    let prediction = coefficients
        .iter()
        .zip(&buffer[i - 12..i])
        .map(|(&c, &s)| c * s as i64)
        .sum::<i64>() >> qlp_shift;
    let delta = buffer[i];
    buffer[i] = prediction as i32 + delta;
}
```

Despite using multiple chained iterator adapters (`zip`, `map`, `sum`), the compiler optimizes this to:

- **Loop unrolling**: The 12-element loop is unrolled into 12 sequential operations — no loop control overhead at runtime.
- **Register allocation**: All 12 coefficients are loaded into CPU registers for direct, fast access.
- **No bounds checks**: The compiler proves array accesses are safe and eliminates runtime bounds checking.

The resulting assembly is equivalent to what an expert would write by hand.

## Key Takeaways

### Why Iterators Are Not Slower

- **Lazy evaluation** means no intermediate allocations unless you explicitly call `collect()`.
- The compiler sees through the iterator abstraction and generates tightly optimized machine code.
- Iterator chains are a single, composable expression — the compiler can reason about the whole pipeline at once.

### When to Use Which Style

| Situation                            | Preferred Style     |
|--------------------------------------|---------------------|
| Simple transformation/filtering      | Iterator adapters   |
| Complex stateful logic                | `for` loop          |
| Performance-critical hot paths       | Either (equivalent) |
| Readability and composability matter | Iterator adapters   |

There is no performance reason to avoid iterators. Choose based on clarity.

---

## Summary

| Concept               | Detail                                                                 |
|-----------------------|------------------------------------------------------------------------|
| Zero-cost abstraction | Iterator chains compile to the same code as hand-written loops         |
| Benchmark result      | Iterator version is roughly equal to (slightly faster than) `for` loop |
| Loop unrolling        | Compiler eliminates loop overhead for fixed-size iterator operations    |
| Register allocation   | Compiler stores values in CPU registers, not memory, for hot loops     |
| No bounds checks      | Compiler proves safety statically, removing runtime overhead           |

**Bottom line**: Use iterators and closures freely. Rust's compiler ensures you pay no performance cost for the abstraction, and your code becomes more expressive and composable as a result.

# 13.2 - Processing a Series of Items with Iterators

## High-Level Overview

Iterators are a core feature in Rust that allow you to process sequences of items one at a time. Rust's iterator pattern is **lazy**: iterators do nothing until they are consumed. This design enables efficient, expressive code without unnecessary computation and compiles down to zero-cost abstractions — equivalent machine code to hand-written loops.

---

## Key Concepts

### 1. The `Iterator` Trait

All iterators in Rust implement the `Iterator` trait from the standard library. The only required method is `next`, which returns items one at a time wrapped in `Option`:

```rust
pub trait Iterator {
    type Item;

    fn next(&mut self) -> Option<Self::Item>;

    // methods with default implementations elided
}
```

- Returns `Some(item)` for each item in the sequence.
- Returns `None` when the iterator is exhausted.
- `type Item` is an **associated type** — it defines what type the iterator yields.

---

### 2. Creating an Iterator — Listing 13-10

You can create an iterator from a vector using `.iter()`. By itself it does nothing — this is **lazy evaluation**:

```rust
fn main() {
    let v1 = vec![1, 2, 3];

    let v1_iter = v1.iter();
}
```

### Using an Iterator in a `for` Loop — Listing 13-11

A `for` loop takes ownership of the iterator and calls `next` implicitly on each iteration:

```rust
fn main() {
    let v1 = vec![1, 2, 3];

    let v1_iter = v1.iter();

    for val in v1_iter {
        println!("Got: {val}");
    }
}
```

---

### 3. Calling `next` Directly — Listing 13-12

You can call `next` manually. The iterator must be declared `mut` since each call advances its internal state. Values returned by `.iter()` are **immutable references** (`&T`):

```rust
#[cfg(test)]
mod tests {
    #[test]
    fn iterator_demonstration() {
        let v1 = vec![1, 2, 3];

        let mut v1_iter = v1.iter();

        assert_eq!(v1_iter.next(), Some(&1));
        assert_eq!(v1_iter.next(), Some(&2));
        assert_eq!(v1_iter.next(), Some(&3));
        assert_eq!(v1_iter.next(), None);
    }
}
```

> Note: `for` loops don't require `mut` because the loop takes ownership of the iterator internally.

---

## Three Types of Iterators

| Method        | Returns            | Ownership         |
|---------------|--------------------|-------------------|
| `iter()`      | `&T`               | Borrows immutably |
| `iter_mut()`  | `&mut T`           | Borrows mutably   |
| `into_iter()` | `T` (owned values) | Takes ownership   |

---

## Consuming Adapters

Methods that call `next` internally and use up the iterator are called **consuming adapters**. Once consumed, the iterator cannot be used again.

### Example: `sum` — Listing 13-13

```rust
#[cfg(test)]
mod tests {
    #[test]
    fn iterator_sum() {
        let v1 = vec![1, 2, 3];

        let v1_iter = v1.iter();

        let total: i32 = v1_iter.sum();

        assert_eq!(total, 6);
    }
}
```

`sum` takes ownership of `v1_iter` — you cannot use `v1_iter` after calling `sum`.

---

## Iterator Adapters

Methods that transform an iterator into a different iterator are called **iterator adapters**. They are lazy — they produce no work until a consuming adapter is called.

### Example: `map` (without consuming) — Listing 13-14

```rust
fn main() {
    let v1: Vec<i32> = vec![1, 2, 3];

    v1.iter().map(|x| x + 1);
}
```

This produces a **compiler warning**: the iterator adapter `map` is lazy and will never be used unless consumed. The closure never executes.

### Example: `map` with `collect` — Listing 13-15

```rust
fn main() {
    let v1: Vec<i32> = vec![1, 2, 3];

    let v2: Vec<_> = v1.iter().map(|x| x + 1).collect();

    assert_eq!(v2, vec![2, 3, 4]);
}
```

- `map` takes a closure and applies it to each element, producing a new iterator.
- `.collect()` is the consuming adapter that forces the lazy chain to execute and gathers results into a `Vec`.

### Example: `filter` with Closures Capturing Environment — Listing 13-16

`filter` takes a closure that returns a `bool`. It captures values from the environment, keeping only items where the closure returns `true`.

```rust
#[derive(PartialEq, Debug)]
struct Shoe {
    size: u32,
    style: String,
}

fn shoes_in_size(shoes: Vec<Shoe>, shoe_size: u32) -> Vec<Shoe> {
    shoes.into_iter().filter(|s| s.size == shoe_size).collect()
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn filters_by_size() {
        let shoes = vec![
            Shoe {
                size: 10,
                style: String::from("sneaker"),
            },
            Shoe {
                size: 13,
                style: String::from("sandal"),
            },
            Shoe {
                size: 10,
                style: String::from("boot"),
            },
        ];

        let in_my_size = shoes_in_size(shoes, 10);

        assert_eq!(
            in_my_size,
            vec![
                Shoe {
                    size: 10,
                    style: String::from("sneaker")
                },
                Shoe {
                    size: 10,
                    style: String::from("boot")
                },
            ]
        );
    }
}
```

- `into_iter()` takes ownership of the `Vec<Shoe>`.
- The closure `|s| s.size == shoe_size` **captures** `shoe_size` from the enclosing scope.
- `.collect()` gathers the filtered items into a new `Vec<Shoe>`.

---

## Important Points

- **Lazy by default**: Iterator adapters like `map` and `filter` do nothing until a consuming adapter (like `collect` or `sum`) is called. Forgetting this results in a compiler warning about unused iterators.
- **Zero-cost abstraction**: Rust iterators compile down to the same machine code as equivalent hand-written loops — no runtime overhead.
- **Chaining**: Multiple adapter methods can be chained together for expressive, readable transformations.

```rust
let result: Vec<i32> = vec![1, 2, 3, 4, 5]
    .iter()
    .filter(|&&x| x % 2 == 0)
    .map(|&x| x * 10)
    .collect();

assert_eq!(result, vec![20, 40]);
```

---

## Summary

| Concept               | Description                                                   |
|-----------------------|---------------------------------------------------------------|
| `Iterator` trait      | Defines `next` method; returns `Option<Self::Item>`           |
| Lazy evaluation       | Iterators do nothing until consumed                           |
| Consuming adapters    | Call `next` and exhaust the iterator (e.g., `sum`, `collect`) |
| Iterator adapters     | Transform iterators lazily (e.g., `map`, `filter`)            |
| Closure capture       | Iterator adapters can capture variables from their environment |
| Zero-cost abstraction | No runtime overhead compared to manual loops                  |

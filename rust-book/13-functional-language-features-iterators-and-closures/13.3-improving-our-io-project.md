# 13.3 - Improving Our I/O Project

## High-Level Overview

This section applies iterator knowledge to refactor the `minigrep` I/O project from Chapter 12. The goals are:

1. **Remove unnecessary `clone` calls** in `Config::build` by accepting an iterator instead of a slice.
2. **Simplify the `search` function** using iterator adapters instead of a mutable intermediate vector.

Both changes result in cleaner, more idiomatic Rust without any performance cost.

---

## Part 1: Removing `clone` Using an Iterator

### The Problem — Listing 13-17

The original `Config::build` accepted a `&[String]` slice, which meant it only had references. To get owned `String` values for the struct fields, it had to **clone** them:

```rust
impl Config {
    pub fn build(args: &[String]) -> Result<Config, &'static str> {
        if args.len() < 3 {
            return Err("not enough arguments");
        }

        let query = args[1].clone();      // clone because we only have &String
        let file_path = args[2].clone();  // clone because we only have &String

        let ignore_case = env::var("IGNORE_CASE").is_ok();

        Ok(Config {
            query,
            file_path,
            ignore_case,
        })
    }
}
```

And in `main`, the iterator was first collected into a `Vec`, then a slice was passed:

```rust
fn main() {
    let args: Vec<String> = env::args().collect();

    let config = Config::build(&args).unwrap_or_else(|err| {
        eprintln!("Problem parsing arguments: {err}");
        process::exit(1);
    });

    // --snip--

    if let Err(e) = minigrep::run(config) {
        eprintln!("Application error: {e}");
        process::exit(1);
    }
}
```

### The Fix — Step 1: Pass the Iterator Directly (Listing 13-18)

`env::args()` already returns an iterator. Instead of collecting it into a `Vec` first, pass it directly to `Config::build`:

```rust
use std::env;
use std::process;

use minigrep::Config;

fn main() {
    let config = Config::build(env::args()).unwrap_or_else(|err| {
        eprintln!("Problem parsing arguments: {err}");
        process::exit(1);
    });

    // --snip--

    if let Err(e) = minigrep::run(config) {
        eprintln!("Application error: {e}");
        process::exit(1);
    }
}
```

### The Fix — Step 2: Update `Config::build` Signature (Listing 13-19)

Change the parameter from `&[String]` to `impl Iterator<Item = String>`. This accepts any iterator that yields owned `String` values:

```rust
impl Config {
    pub fn build(
        mut args: impl Iterator<Item = String>,
    ) -> Result<Config, &'static str> {
        // body still uses old indexing — will be updated next
        // --snip--
    }
}
```

- `impl Iterator<Item = String>` means: any type that implements `Iterator` and yields `String`.
- `mut args` is needed because calling `next()` on the iterator mutates it to advance its position.
- The standard library's `env::args()` returns `std::env::Args`, which satisfies this bound.

### The Fix — Step 3: Use Iterator Methods Instead of Indexing (Listing 13-20)

Replace index-based access and the length check with calls to `next()`, using `match` on the `Option` result for clear error handling:

```rust
impl Config {
    pub fn build(
        mut args: impl Iterator<Item = String>,
    ) -> Result<Config, &'static str> {
        args.next(); // skip the first value — the program name

        let query = match args.next() {
            Some(arg) => arg,
            None => return Err("Didn't get a query string"),
        };

        let file_path = match args.next() {
            Some(arg) => arg,
            None => return Err("Didn't get a file path"),
        };

        let ignore_case = env::var("IGNORE_CASE").is_ok();

        Ok(Config {
            query,
            file_path,
            ignore_case,
        })
    }
}
```

**Benefits:**
- No `.clone()` calls — `next()` returns owned values directly from the iterator.
- More expressive error messages: "Didn't get a query string" vs. "not enough arguments".
- The first `args.next()` discards the program name (always the first argument from `env::args()`).

        search_case_insensitive(&config.query, &contents)

pub fn search<'a>(query: &str, contents: &'a str) -> Vec<&'a str> {
    let mut results = Vec::new();

    for line in contents.lines() {

## Part 2: Making Code Clearer with Iterator Adapters

### Original `search` — Listing 13-21 (Imperative Style)

The original function used a mutable intermediate vector and an explicit loop:

```rust
pub fn search<'a>(query: &str, contents: &'a str) -> Vec<&'a str> {
    let mut results = Vec::new();

    for line in contents.lines() {
        if line.contains(query) {
            results.push(line);
        }
    }

    results
}
```

### Refactored `search` — Listing 13-22 (Functional Style)

The same logic expressed with iterator adapters — no mutable state:

```rust
pub fn search<'a>(query: &str, contents: &'a str) -> Vec<&'a str> {
    contents
        .lines()
        .filter(|line| line.contains(query))
        .collect()
}
```

The functional style:
- Eliminates the mutable `results` vector — no intermediate state to track.
- Expresses intent directly: "get lines, keep those containing the query, collect them."
- Opens the door to parallelism: no shared mutable state means it could search in parallel.
- Closure `|line| line.contains(query)` **captures** `query` from the enclosing scope.

## Key Concepts Reinforced

### `impl Trait` in Function Parameters

`impl Iterator<Item = String>` accepts any type satisfying the trait bound — more flexible than requiring a concrete `Vec<String>`. This is idiomatic Rust for generic parameters.

### Zero-Cost Abstractions

The iterator-based `search` compiles to the same machine code as the hand-written loop. Expressiveness has no runtime cost.

### Functional vs Imperative Style

| Style       | Pattern                        | Notes                                |
|-------------|--------------------------------|--------------------------------------|
| Imperative  | `for` loop + mutable `Vec`     | Familiar, but more state to track    |
| Functional  | `.filter().collect()`          | Concise, no mutable state, composable|

Most Rust programmers prefer the iterator style once they are comfortable with the adapters, because it focuses on the *what* (filter condition) rather than the *how* (loop mechanics).

---

## Summary of Changes

| Area                    | Before                          | After                                |
|-------------------------|---------------------------------|--------------------------------------|
| `main.rs` arg passing   | `env::args().collect()` → slice | `env::args()` passed directly        |
| `Config::build` param   | `&[String]`                     | `mut args: impl Iterator<Item=String>` |
| Ownership of fields     | `.clone()` to copy values       | `args.next()` transfers ownership    |
| Argument validation     | `args.len() < 3` check          | `match args.next()` on each field    |
| `search` function       | `for` loop + mutable `Vec`      | `.filter().collect()` pipeline       |

The refactoring demonstrates a key Rust principle: **ownership and iterators together eliminate unnecessary copying while making code more expressive and composable.**
